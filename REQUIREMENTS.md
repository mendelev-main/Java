# Требования к Java Interview Notes

> Этот файл — постоянные правила проекта. Перед написанием или редактированием конспекта сначала перечитай его. Если требования меняются, сначала обнови этот файл, затем применяй изменения к конспекту.

## 1. Цель

Создать единый, последовательный и удобный для повторения конспект по Java backend для подготовки к техническим собеседованиям. Это **учебный материал**, а не сборник несвязанных ответов или энциклопедия.

Читатель должен:
- быстро находить нужную тему;
- понимать её с первого прочтения;
- уметь объяснить её своими словами на собеседовании;
- видеть примеры, важные нюансы и типичные ошибки;
- возвращаться к кратким выводам для повторения.

## 2. Файлы и источник истины

- `REQUIREMENTS.md` — требования, структура и правила работы (этот файл).
- `JAVA_NOTES.md` — **единственный Markdown-файл** с чистовым конспектом. Создаётся отдельным следующим шагом; не разбивать конспект на файлы по темам без отдельного решения.
- Исходный большой конспект пользователя «Копия Срез 2–8 Java» (~436 страниц) — основная база для извлечения тем и объяснений.
- Дополнительные источники: знания по Java и проверяемая актуальная документация, прежде всего официальная (OpenJDK, Oracle Java, Spring, Hibernate и др.).

Приоритет при конфликте: корректность и актуальность > ясность > полнота исходника. **Нельзя переносить ошибки исходного конспекта без проверки.** Если исходник расходится с современными версиями Java или с официальной документацией, уточнить версию и явно объяснить отличие. Не выдавать непроверенную информацию за факт.

## 3. Стиль

- Язык — **русский**; технические термины, API, названия классов и методов сохранять на английском.
- Простые, точные предложения. Минимум воды, канцелярита и повторений.
- Объяснять **от простого к сложному**: сначала смысл и назначение, затем устройство и ограничения.
- Термины определять при первом использовании. Не заменять объяснение набором жаргонных слов.
- Абзацы короткие, с визуальными отступами и понятными заголовками.
- Не перегружать очевидное, но не упускать тонкости, важные на собеседованиях.
- Отделять поведение, гарантированное спецификацией, от особенностей конкретной реализации (например, HotSpot) и версий.
- Не дублировать подробный материал из других глав: давать короткую связку или внутреннюю Markdown-ссылку.

## 4. Стандарт подраздела

Не все пункты обязательны для совсем коротких тем; адаптировать шаблон по смыслу.

1. **Что это и зачем нужно** — определение в 1–3 предложениях.
2. **Как работает** — логика и механизм; при необходимости пошагово.
3. **Пример** — небольшой рабочий фрагмент Java/SQL, таблица или схема.
4. **Нюансы и типичные ошибки** — ограничения, контрпримеры, ловушки.
5. **Что запомнить** — 3–6 коротких тезисов.
6. **На собеседовании** — 1–3 типичных вопроса с короткими, точными ответами, которые можно произнести вслух.
7. **Углубление** — только если оно практически полезно; обозначать отдельно.

Не вставлять шаблон механически, если это ухудшает читаемость.

## 5. Оформление Markdown

- Один заголовок `#` для названия конспекта; главы — `##`, подразделы — `###`, вложенные части — `####`.
- В начале конспекта — оглавление с якорными ссылками; поддерживать его по мере добавления глав.
- Использовать списки, таблицы и блоки кода **по назначению**, не превращать весь текст в списки.
- Код в fenced-блоках с указанием языка: ```java`, ```sql`, ```bash`.
- Примеры должны быть минимальными, корректными и объясняющими ровно одну идею. Для важных примеров показывать результат или объяснять, что произойдёт.
- Для сравнений использовать таблицы только тогда, когда они действительно ускоряют понимание.
- Выделять жирным ключевые определения и выводы; не делать жирным каждый второй термин.
- Ссылки на внешние материалы размещать точечно, рядом с соответствующей темой, а не вместо собственного объяснения.

## 8. Итерационный процесс

Для каждой главы:
1. Изучить релевантные разделы исходного конспекта.
2. Составить логичное оглавление подразделов; определить, чего не хватает и что устарело.
3. При необходимости проверить спорные или версионные факты по надёжным источникам.
4. Написать **один законченный небольшой подраздел** в `JAVA_NOTES.md`.
5. Проверить точность, ясность, код, структуру и отсутствие дублей.
6. Зафиксировать изменение в Git с понятным сообщением коммита.
7. Сообщить пользователю, что именно добавлено, и согласовать следующий блок при необходимости.

**Не создавать большие главы одним необозримым куском.** При замечаниях пользователя сначала улучшить стиль/глубину, затем продолжать. Не утверждать, что текст записан в репозиторий, пока запись не подтверждена.

## 9. Критерии готовности подраздела

- Есть понятное определение и ответ «зачем это нужно».
- Механизм объяснён без логических пробелов.
- Пример корректен или обоснованно не нужен.
- Важные ограничения, исключения и версии не скрыты.
- Можно быстро повторить тему по ключевым выводам.
- На типичный вопрос интервью есть короткий внятный ответ.
- Markdown читается на GitHub, заголовки последовательны.
- Нет бессмысленных повторений с другими разделами.
