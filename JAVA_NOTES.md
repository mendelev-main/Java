## 1. Java Core

### 1.1. Java Platform: JDK, JRE, JVM, Bytecode и JIT

**Java** — язык программирования со статической типизацией и платформа для выполнения программ. Одна из главных идей платформы — **Write Once, Run Anywhere (WORA)**: один и тот же скомпилированный код обычно можно запустить на разных операционных системах, если там есть совместимая среда Java.

#### JDK, JRE и JVM — в чём разница?

| Понятие | Что это | Для чего нужно |
| --- | --- | --- |
| **JVM** (Java Virtual Machine) | Виртуальная машина, выполняющая Java-байткод | Запуск кода, управление памятью, выполнение и оптимизация |
| **JRE** (Java Runtime Environment) | Среда выполнения: JVM и необходимые библиотеки | Запуск Java-приложений |
| **JDK** (Java Development Kit) | Набор для разработки: среда выполнения и инструменты | Написание, компиляция, отладка и запуск приложений |

В JDK есть, например, `javac` (компилятор), `java` (запуск), `jar` (работа с архивами), `javadoc` (документация), `javap` (просмотр содержимого class-файлов).

**Нюанс версий:** схема «JDK содержит JRE, а JRE содержит JVM» удобна для понимания, но исторически описывает в том числе отдельные поставки JRE. В современных JDK всё необходимое для выполнения уже включено в JDK; отдельную JRE устанавливать необязательно. Для небольших runtime-образов можно использовать `jlink`.

#### Как Java-программа превращается в выполняемый код?

Рассмотрим минимальный пример:

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Hello, Java!");
    }
}
```

Сохраняем его как `Main.java`, компилируем и запускаем:

```bash
javac Main.java
java Main
```

Результат:

```text
Hello, Java!
```

Что произошло:

1. **`javac`** преобразовал исходный код из `Main.java` в **байткод** — файл `Main.class`.
2. Команда **`java Main`** запустила среду выполнения и JVM.
3. **ClassLoader** загрузил необходимые классы; JVM проверяет и связывает их в процессе подготовки к выполнению.
4. **Execution Engine** начал выполнять байткод. В HotSpot для этого используются интерпретатор и JIT-компиляторы.
5. Программа вывела строку в консоль.

Упрощённая схема:

```text
Main.java
    │  javac — компиляция
    ▼
Main.class (bytecode)
    │
    ▼
JVM → загрузка и подготовка классов
    │
    ▼
Execution Engine
    ├── Interpreter — выполняет байткод
    └── JIT — компилирует выбранные участки в машинный код
                         │
                         ▼
                        CPU
```

**Байткод** — промежуточные инструкции для JVM, а не машинные инструкции конкретного процессора. Именно поэтому один и тот же `.class` может работать на разных системах. **Сама JVM платформозависима:** под конкретную ОС и архитектуру нужна соответствующая реализация.

Это не абсолютная переносимость: приложению могут требоваться нативные библиотеки, особенности ОС или подходящая версия Java.

#### Interpreter и JIT

**Интерпретатор** выполняет инструкции байткода во время работы программы. Это позволяет начать выполнение без предварительной компиляции всего приложения в машинный код.

**JIT (Just-In-Time compiler)** во время выполнения преобразует выбранные участки байткода в машинный код и оптимизирует их. Например, HotSpot анализирует, какие методы и циклы выполняются часто, и может применить к ним оптимизации.

Зачем это нужно? Интерпретация удобна для старта, а многократное выполнение уже скомпилированного машинного кода часто быстрее.

**Важный нюанс:** JIT — не то же самое, что интерпретатор. JIT именно **компилирует** код. Не весь байткод обязан пройти JIT-компиляцию; детали зависят от реализации и настроек JVM.

При измерении производительности это создаёт эффект **прогрева (warm-up)**: первые запуски участка кода могут отличаться по скорости от последующих, когда JVM накопила профиль выполнения и применила оптимизации.

#### Что важно запомнить

- **JDK** — инструменты разработки плюс среда выполнения; **JRE** — среда выполнения; **JVM** — виртуальная машина, выполняющая байткод.
- `javac` обычно компилирует `.java` в `.class`, а не сразу в машинный код конкретной ОС.
- **WORA** обеспечивается байткодом и наличием совместимой JVM на целевой платформе.
- **Интерпретатор** выполняет байткод; **JIT** компилирует выбранные участки в машинный код во время работы.
- Поведение, гарантированное спецификацией JVM, нужно отличать от особенностей **HotSpot**.

#### На собеседовании

**Чем отличаются JDK, JRE и JVM?**

> JVM выполняет байткод. JRE — среда, которая содержит JVM и библиотеки для запуска. JDK — набор для разработки: он включает среду выполнения, компилятор `javac` и другие инструменты. В современных поставках JDK отдельная установка JRE обычно не требуется.

**Почему Java называют платформонезависимой?**

> Компилятор создаёт байткод, который понимает JVM. Поэтому один и тот же `.class` обычно запускается на разных ОС без перекомпиляции, если есть совместимая JVM и нет платформозависимых зависимостей.

**Зачем нужен JIT?**

> JIT во время работы компилирует подходящие участки байткода в машинный код и оптимизирует их. Это позволяет ускорить часто выполняемые части программы, хотя сначала JVM может потребоваться время на прогрев.

### 1.2. Архитектура JVM: ClassLoader и загрузка классов

На верхнем уровне работу JVM удобно представить как несколько связанных частей:

```text
.class-файлы
     │
     ▼
ClassLoader Subsystem
     │
     ▼
Runtime Data Areas
     │
     ▼
Execution Engine
  ├── Interpreter
  ├── JIT
  └── Garbage Collector
     │
     ▼
Native / OS
```

В этом подразделе разберём **ClassLoader Subsystem** — как JVM находит и загружает классы. Память JVM и Garbage Collector рассмотрим отдельно.

#### Зачем нужен ClassLoader?

**ClassLoader** — механизм JVM, который находит байткод класса и создаёт его представление внутри JVM (`Class<?>`).

Классы не обязаны загружаться все сразу при старте приложения. JVM может загружать их **по мере необходимости**.

Например, когда приложение впервые обращается к `com.example.UserService`, JVM должна понять:

1. не загружен ли этот класс ранее;
2. кто должен его загрузить;
3. где найти его байткод;
4. корректен ли найденный class-файл;
5. как связать класс с другими типами.

#### Основные ClassLoader'ы

В современной Java обычно выделяют три основных уровня:

```text
Bootstrap ClassLoader
        ▲
        │
Platform ClassLoader
        ▲
        │
Application ClassLoader
```

**Bootstrap ClassLoader** — самый верхний уровень. Загружает базовые классы и критически важные модули Java, включая `java.base`.

Например:

```java
System.out.println(String.class.getClassLoader());
```

Обычно увидим:

```text
null
```

Это **не означает, что у `String` нет загрузчика**. В Java API Bootstrap ClassLoader исторически представлен как `null`.

**Platform ClassLoader** загружает классы платформы, которые не относятся к базовой части, загружаемой Bootstrap.

**Application (System) ClassLoader** обычно загружает код нашего приложения и его зависимости из classpath.

```java
public class Main {
    public static void main(String[] args) {
        System.out.println(Main.class.getClassLoader());
    }
}
```

Для обычного приложения здесь, как правило, будет Application ClassLoader.

> **Нюанс версий:** до Java 9 существовал **Extension ClassLoader**, связанный с механизмом extensions (`jre/lib/ext`). Начиная с Java 9 его роль в современной модели занимает **Platform ClassLoader**. Поэтому ответ «Bootstrap → Extension → Application» относится к старым версиям Java.

#### Parent Delegation Model

По умолчанию загрузчики используют модель **parent-first delegation**.

Если Application ClassLoader получил запрос на загрузку класса, он не обязательно сразу ищет его среди классов приложения. Сначала запрос делегируется вверх по цепочке.

Упрощённо:

```text
Application
    │
    │ delegate
    ▼
Platform
    │
    │ delegate
    ▼
Bootstrap
    │
    ├── найден → вернуть класс
    │
    └── не найден
           ▲
           │ Platform пробует найти сам
           ▲
           │ Application пробует найти сам
```

Для типичного `ClassLoader.loadClass(name)` логика выглядит примерно так:

1. Проверить, не был ли класс уже загружен.
2. Передать запрос родительскому загрузчику.
3. Если родитель класс не нашёл — попытаться найти его самостоятельно.
4. Если класс нигде не найден — загрузка завершается ошибкой.

Зачем сначала спрашивать родителя? Одна из причин — **предсказуемость и защита базовых классов платформы**. Код приложения не должен случайно подменить, например, стандартный `java.lang.String` своей копией.

**Parent-first — стандартная модель, но не абсолютное правило для всех систем.** Пользовательские загрузчики и некоторые контейнеры/плагинные системы могут применять другую стратегию, например child-first.

#### Loading, Linking и Initialization

Жизненный цикл класса не заканчивается чтением `.class`-файла.

Упрощённо:

```text
Loading
   │
   ▼
Linking
 ├── Verification
 ├── Preparation
 └── Resolution
   │
   ▼
Initialization
```

**Loading** — JVM находит бинарное представление класса и создаёт его представление в памяти.

**Linking** — подготовка загруженного класса к использованию:

- **Verification** — проверка корректности class-файла и байткода.
- **Preparation** — создаются необходимые структуры для static-полей и устанавливаются их начальные значения по правилам JVM.
- **Resolution** — символические ссылки на другие классы, методы и поля преобразуются в конкретные ссылки JVM. Resolution может выполняться лениво.

**Initialization** — выполняется логика инициализации класса: в частности, присваивания static-полям и static-блоки, собранные компилятором в метод инициализации класса `<clinit>`.

Пример:

```java
class Config {
    static int port = initPort();

    static {
        System.out.println("Config initialized");
    }

    private static int initPort() {
        return 8080;
    }
}
```

Загрузка класса и его **инициализация — не одно и то же**. JVM может загрузить и связать класс раньше, чем возникнет необходимость его инициализировать.

#### Идентичность класса: имя + ClassLoader

Для JVM тип определяется не только полным именем класса.

Упрощённо:

```text
Class identity = binary name + defining ClassLoader
```

Допустим, два независимых ClassLoader загрузили один и тот же:

```text
com.example.Plugin
```

Для JVM это могут быть **два разных типа**, даже если байткод взят из одного и того же JAR.

Именно это позволяет плагинным системам изолировать разные версии библиотек. Но отсюда возникает и важная ловушка: объект класса, загруженного одним ClassLoader, нельзя автоматически считать экземпляром «такого же» класса, загруженного другим ClassLoader. Это может привести к `ClassCastException`.

#### Custom ClassLoader

Можно создать собственный загрузчик:

```java
class PluginClassLoader extends ClassLoader {

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = loadClassBytes(name); // условный метод
        return defineClass(name, bytes, 0, bytes.length);
    }

    private byte[] loadClassBytes(String name) {
        // Читаем bytecode из нужного источника
        throw new UnsupportedOperationException();
    }
}
```

Обычно переопределяют **`findClass()`**, а стандартный `loadClass()` оставляют без изменений, чтобы сохранить parent-first delegation.

Собственные загрузчики нужны, например, для:

- плагинных архитектур;
- изоляции разных версий библиотек;
- hot reload / hot deploy;
- загрузки байткода из нестандартного источника.

Для обычного backend-приложения писать свой ClassLoader почти никогда не требуется, но понимание механизма полезно при разборе контейнеров, application servers, драйверов, SPI и проблем с зависимостями.

#### Типичные ошибки

**`ClassNotFoundException`** — приложение явно пытается загрузить класс, но загрузчик не может его найти.

**`NoClassDefFoundError`** — JVM во время выполнения не может получить определение класса, которое требуется программе; причины шире, чем просто «нет JAR в runtime», например предыдущая неудачная инициализация класса.

**`LinkageError`** — семейство ошибок, возникающих при проблемах связывания/определения классов.

**`ClassCastException` при разных ClassLoader'ах** — два класса могут иметь одинаковое имя, но быть разными типами для JVM.

#### Что важно запомнить

- ClassLoader загружает классы **по мере необходимости**, а не обязательно все при старте.
- Основная цепочка современной Java: **Bootstrap → Platform → Application**.
- До Java 9 вместо Platform в старой модели использовался **Extension ClassLoader**.
- Стандартная модель делегирования — **parent-first**: сначала пытается родитель, затем текущий загрузчик.
- Загрузка класса проходит через **Loading → Linking → Initialization**; Linking включает Verification, Preparation и Resolution.
- Для JVM идентичность типа определяется **именем класса + defining ClassLoader**.
- Пользовательские ClassLoader'ы позволяют изолировать плагины и версии библиотек.

#### На собеседовании

**Какие основные ClassLoader'ы есть в Java?**

> В современной Java это Bootstrap, Platform и Application ClassLoader. Bootstrap загружает базовую часть платформы, Platform — остальные платформенные классы, а Application — обычно код приложения и зависимости. До Java 9 вместо Platform использовался Extension ClassLoader.

**Как работает parent delegation?**

> Когда загрузчик получает запрос на класс, он сначала проверяет уже загруженные классы и делегирует поиск родителю. Если родитель не нашёл класс, текущий загрузчик пытается загрузить его сам. Это помогает избежать дублирования и случайной подмены базовых классов.

**Могут ли два класса с одинаковым полным именем быть разными типами?**

> Да. Для JVM идентичность типа определяется не только именем, но и defining ClassLoader. Поэтому одинаковый класс, загруженный двумя независимыми ClassLoader'ами, может считаться двумя разными типами.

**Чем Loading отличается от Initialization?**

> Loading создаёт представление класса в JVM на основе его бинарного представления. После этого идёт Linking. Initialization — отдельный более поздний этап, на котором выполняется инициализация static-полей и static-блоков класса.

### 1.3. Память JVM: Heap, Stack, Metaspace и Code Cache

Во время работы Java-программы JVM использует несколько областей памяти с разным назначением. Для собеседования важно не просто перечислить их, а понимать **что где хранится, кому область принадлежит и какие ошибки возникают при её исчерпании**.

Упрощённая картина:

```text
JVM process
│
├── Heap                         ← общий для потоков
│     └── объекты и массивы
│
├── JVM Stack (у каждого потока свой)
│     └── Stack Frames
│           ├── локальные переменные
│           ├── ссылки
│           └── operand stack
│
├── Metaspace                    ← метаданные загруженных классов (HotSpot)
│
└── Code Cache                   ← машинный код, созданный JIT (HotSpot)
```

> Важно различать **области, определённые JVM Specification**, и конкретную организацию памяти в **HotSpot**. Например, JVM Specification определяет Heap, JVM Stacks и Method Area, а Metaspace и Code Cache — детали реализации HotSpot.

#### Heap

**Heap (куча)** — общая для всех потоков область JVM, из которой обычно выделяется память под объекты и массивы.

```java
User user = new User("Alex");
int[] numbers = new int[10];
```

Упрощённо:

```text
Stack                         Heap
┌──────────────┐             ┌────────────────────┐
│ user ────────┼────────────►│ User object        │
│              │             │ name → "Alex"      │
│ numbers ─────┼────────────►│ int[10]            │
└──────────────┘             └────────────────────┘
```

Переменная `user` в данном примере — **ссылка**, а сам объект `User` находится в heap. Если объект содержит примитивное поле, это поле является частью самого объекта.

Heap обслуживается Garbage Collector. Подробно поколения, reachability, GC Roots и конкретные сборщики разберём в следующем подразделе.

При нехватке heap можно получить:

```text
java.lang.OutOfMemoryError: Java heap space
```

Размер heap в HotSpot обычно настраивают параметрами:

```bash
-Xms512m
-Xmx2g
```

где `-Xms` задаёт начальный размер heap, а `-Xmx` — максимальный.

#### JVM Stack

У **каждого Java-потока свой JVM Stack**. Он создаётся вместе с потоком и используется во время выполнения методов.

При каждом вызове метода создаётся **Stack Frame (кадр стека)**. После завершения метода соответствующий frame удаляется.

Пример:

```java
static int square(int value) {
    int result = value * value;
    return result;
}

public static void main(String[] args) {
    int number = 5;
    int answer = square(number);
}
```

Упрощённо во время выполнения `square()`:

```text
Thread Stack

┌────────────────────────────┐
│ square() frame             │  ← текущий вызов
│ value = 5                  │
│ result = 25                │
├────────────────────────────┤
│ main() frame               │
│ number = 5                 │
│ answer = ...               │
└────────────────────────────┘
```

Когда `square()` завершится, его frame исчезнет, а выполнение продолжится в `main()`.

#### Что находится внутри Stack Frame?

Согласно модели JVM, frame содержит в том числе:

- **local variables** — локальные переменные и параметры;
- **operand stack** — стек операндов, который bytecode использует для вычислений;
- данные, необходимые для возврата из метода и поддержки вызовов.

Например, выражение:

```java
int result = a + b;
```

на уровне bytecode концептуально использует operand stack: значения загружаются на стек операндов, выполняется операция сложения, результат сохраняется.

Для обычной подготовки к интервью достаточно помнить:

```text
JVM Stack
    └── Frame одного вызова метода
          ├── Local Variables
          ├── Operand Stack
          └── служебные данные вызова
```

#### StackOverflowError

Если вызовов становится слишком много и стек потока исчерпывается, возникает `StackOverflowError`.

Классический пример — бесконечная рекурсия:

```java
static void recursive() {
    recursive();
}
```

Каждый новый вызов создаёт новый frame:

```text
recursive()
recursive()
recursive()
recursive()
...
↓
StackOverflowError
```

Размер стека потока в HotSpot можно настраивать параметром `-Xss`.

Например:

```bash
-Xss1m
```

Большой `-Xss` позволяет отдельному потоку иметь более глубокий стек, но одновременно увеличивает потенциальное потребление памяти при большом количестве потоков.

#### Важный нюанс: «объекты всегда в Heap, переменные всегда в Stack»

Такую формулу часто используют для обучения, но она **слишком грубая**.

Для собеседования безопаснее говорить:

> Объекты и массивы обычно размещаются в heap. JVM Stack хранит frames вызовов, внутри которых находятся локальные переменные и промежуточные значения. Локальная переменная ссылочного типа содержит ссылку на объект, а не сам объект.

Почему «всегда» опасно? JVM имеет право применять оптимизации. Например, JIT может выполнить escape analysis и устранить отдельную аллокацию вообще. Поэтому не стоит воспринимать учебную схему как описание физического расположения каждого значения после оптимизаций.

#### Metaspace

**Metaspace** — область нативной памяти, которую HotSpot использует для хранения метаданных загруженных классов.

Упрощённо там находятся данные, описывающие классы:

- информация о структуре класса;
- методы и поля;
- runtime constant pool и связанные метаданные;
- данные, необходимые JVM для работы с загруженными типами.

Главная мысль:

```text
Heap       → экземпляры объектов
Metaspace  → метаданные загруженных классов
```

До Java 8 HotSpot использовал **Permanent Generation (PermGen)**. Начиная с Java 8 PermGen был удалён, а метаданные классов хранятся с использованием Metaspace.

Metaspace использует native memory и по умолчанию может расти в зависимости от доступной памяти. Его верхнюю границу можно ограничить:

```bash
-XX:MaxMetaspaceSize=256m
```

При исчерпании возможна ошибка:

```text
java.lang.OutOfMemoryError: Metaspace
```

Одна из причин проблем с Metaspace — постоянное создание новых ClassLoader'ов и загрузка новых классов, когда старые ClassLoader'ы остаются достижимыми и не могут быть освобождены.

#### Code Cache

**Code Cache** — область памяти HotSpot, в которой хранится скомпилированный машинный код, созданный JIT.

Связь с предыдущей темой:

```text
Bytecode
   │
   │ JIT compilation
   ▼
Native machine code
   │
   ▼
Code Cache
```

Когда JVM снова выполняет уже скомпилированный участок, она может использовать машинный код из Code Cache вместо повторной интерпретации этого участка.

Code Cache — **не место хранения Java-объектов** и не замена heap.

#### Где что хранится?

Для быстрого повторения:

| Что | Где концептуально находится |
| --- | --- |
| Объекты и массивы | Heap |
| Поля объекта | В составе объекта в Heap |
| Stack Frame вызванного метода | JVM Stack конкретного потока |
| Локальный примитив | Local Variables текущего Frame |
| Локальная ссылка на объект | Local Variables Frame; объект — в Heap |
| Метаданные загруженных классов | Metaspace в HotSpot |
| JIT-скомпилированный машинный код | Code Cache в HotSpot |

Со **static-полями** лучше не использовать упрощённый ответ «static лежит в Metaspace». Спецификация JVM не требует такого физического размещения. В HotSpot метаданные класса и значения его Java static-полей — не одно и то же; для интервью важнее понимать, что static-поле принадлежит **классу**, а не экземпляру. Детали конкретного физического размещения являются implementation detail.

#### Heap и Stack — главное различие

| Heap | JVM Stack |
| --- | --- |
| Общий для потоков | У каждого потока свой |
| Обычно содержит объекты и массивы | Содержит frames вызовов |
| Управляется GC | Frames удаляются при возврате из методов |
| Может привести к `OutOfMemoryError: Java heap space` | Глубокие вызовы могут привести к `StackOverflowError` |
| Размер обычно контролируется `-Xms/-Xmx` | Размер стека потока — `-Xss` |

#### Что важно запомнить

- **Heap** — общая область, где обычно размещаются объекты и массивы.
- **JVM Stack** принадлежит конкретному потоку и состоит из frames вызванных методов.
- **Stack Frame** содержит local variables, operand stack и служебные данные выполнения метода.
- **Metaspace** в HotSpot хранит метаданные загруженных классов и использует native memory; с Java 8 он заменил PermGen.
- **Code Cache** хранит машинный код, созданный JIT в HotSpot.
- Не стоит механически отвечать «всё локальное — Stack, всё static — Metaspace»: реальная модель и оптимизации JVM сложнее этой мнемоники.

#### На собеседовании

**Чем Heap отличается от Stack?**

> Heap — общая для потоков область, где обычно размещаются объекты и массивы и которой управляет GC. У каждого потока свой JVM Stack, состоящий из frames вызванных методов. Frames содержат локальные переменные, operand stack и служебные данные выполнения.

**Что такое Stack Frame?**

> Это структура, создаваемая в JVM Stack при вызове метода. Она содержит локальные переменные метода, operand stack и данные, необходимые для выполнения и возврата из метода. После завершения вызова frame удаляется.

**Что хранится в Metaspace?**

> В HotSpot Metaspace используется для метаданных загруженных классов. Он находится в native memory и с Java 8 заменил PermGen. При чрезмерной загрузке классов или утечках ClassLoader'ов можно получить OutOfMemoryError: Metaspace.

**Где находится объект, если ссылка на него — локальная переменная?**

> В обычной модели локальная ссылка находится в frame текущего потока, а объект размещён в heap. Но JIT может оптимизировать аллокации, поэтому это не нужно трактовать как абсолютное физическое правило для любого оптимизированного кода.
