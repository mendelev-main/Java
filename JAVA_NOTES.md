## 1. Java Core

### 1.1. Java Platform: JDK, JRE, JVM, Bytecode и JIT

**Java** — язык программирования со статической типизацией и платформа для выполнения программ. Одна из главных идей платформы — **Write Once, Run Anywhere (WORA)**: один и тот же скомпилированный код обычно можно запустить на разных операционных системах, если там есть совместимая среда Java.

#### JDK, JRE и JVM — в чём разница?

| Понятие | Что это | Для чего нужно |
| --- | --- | --- |
| **JVM** (Java Virtual Machine) | Виртуальная машина, выполняющая Java-байткод | Запуск кода, управление памятью, выполнение и оптимизация |
| **JRE** (Java Runtime Environment) | Среда выполнения: JVM и необходимые библиотеки | Запуск Java-приложений |
| **JDK** (Java Development Kit) | Набор для разработки: среда выполнения и инструменты | Написание, компиляция, отладка и запуск приложений |

В JDK есть, например, `javac` (компилятор), `java` (запуск), `jar` (работа с архивами), `javadoc` (документация), `javap` (просмотр содержимого class-файлов).

**Нюанс версий:** схема «JDK содержит JRE, а JRE содержит JVM» удобна для понимания, но исторически описывает в том числе отдельные поставки JRE. В современных JDK всё необходимое для выполнения уже включено в JDK; отдельную JRE устанавливать необязательно. Для небольших runtime-образов можно использовать `jlink`.

#### Как Java-программа превращается в выполняемый код?

Рассмотрим минимальный пример:

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Hello, Java!");
    }
}
```

Сохраняем его как `Main.java`, компилируем и запускаем:

```bash
javac Main.java
java Main
```

Результат:

```text
Hello, Java!
```

Что произошло:

1. **`javac`** преобразовал исходный код из `Main.java` в **байткод** — файл `Main.class`.
2. Команда **`java Main`** запустила среду выполнения и JVM.
3. **ClassLoader** загрузил необходимые классы; JVM проверяет и связывает их в процессе подготовки к выполнению.
4. **Execution Engine** начал выполнять байткод. В HotSpot для этого используются интерпретатор и JIT-компиляторы.
5. Программа вывела строку в консоль.

Упрощённая схема:

```text
Main.java
    │  javac — компиляция
    ▼
Main.class (bytecode)
    │
    ▼
JVM → загрузка и подготовка классов
    │
    ▼
Execution Engine
    ├── Interpreter — выполняет байткод
    └── JIT — компилирует выбранные участки в машинный код
                         │
                         ▼
                        CPU
```

**Байткод** — промежуточные инструкции для JVM, а не машинные инструкции конкретного процессора. Именно поэтому один и тот же `.class` может работать на разных системах. **Сама JVM платформозависима:** под конкретную ОС и архитектуру нужна соответствующая реализация.

Это не абсолютная переносимость: приложению могут требоваться нативные библиотеки, особенности ОС или подходящая версия Java.

#### Interpreter и JIT

**Интерпретатор** выполняет инструкции байткода во время работы программы. Это позволяет начать выполнение без предварительной компиляции всего приложения в машинный код.

**JIT (Just-In-Time compiler)** во время выполнения преобразует выбранные участки байткода в машинный код и оптимизирует их. Например, HotSpot анализирует, какие методы и циклы выполняются часто, и может применить к ним оптимизации.

Зачем это нужно? Интерпретация удобна для старта, а многократное выполнение уже скомпилированного машинного кода часто быстрее.

**Важный нюанс:** JIT — не то же самое, что интерпретатор. JIT именно **компилирует** код. Не весь байткод обязан пройти JIT-компиляцию; детали зависят от реализации и настроек JVM.

При измерении производительности это создаёт эффект **прогрева (warm-up)**: первые запуски участка кода могут отличаться по скорости от последующих, когда JVM накопила профиль выполнения и применила оптимизации.

#### Что важно запомнить

- **JDK** — инструменты разработки плюс среда выполнения; **JRE** — среда выполнения; **JVM** — виртуальная машина, выполняющая байткод.
- `javac` обычно компилирует `.java` в `.class`, а не сразу в машинный код конкретной ОС.
- **WORA** обеспечивается байткодом и наличием совместимой JVM на целевой платформе.
- **Интерпретатор** выполняет байткод; **JIT** компилирует выбранные участки в машинный код во время работы.
- Поведение, гарантированное спецификацией JVM, нужно отличать от особенностей **HotSpot**.

#### На собеседовании

**Чем отличаются JDK, JRE и JVM?**

> JVM выполняет байткод. JRE — среда, которая содержит JVM и библиотеки для запуска. JDK — набор для разработки: он включает среду выполнения, компилятор `javac` и другие инструменты. В современных поставках JDK отдельная установка JRE обычно не требуется.

**Почему Java называют платформонезависимой?**

> Компилятор создаёт байткод, который понимает JVM. Поэтому один и тот же `.class` обычно запускается на разных ОС без перекомпиляции, если есть совместимая JVM и нет платформозависимых зависимостей.

**Зачем нужен JIT?**

> JIT во время работы компилирует подходящие участки байткода в машинный код и оптимизирует их. Это позволяет ускорить часто выполняемые части программы, хотя сначала JVM может потребоваться время на прогрев.

### 1.2. Архитектура JVM: ClassLoader и загрузка классов

На верхнем уровне работу JVM удобно представить как несколько связанных частей:

```text
.class-файлы
     │
     ▼
ClassLoader Subsystem
     │
     ▼
Runtime Data Areas
     │
     ▼
Execution Engine
  ├── Interpreter
  ├── JIT
  └── Garbage Collector
     │
     ▼
Native / OS
```

В этом подразделе разберём **ClassLoader Subsystem** — как JVM находит и загружает классы. Память JVM и Garbage Collector рассмотрим отдельно.

#### Зачем нужен ClassLoader?

**ClassLoader** — механизм JVM, который находит байткод класса и создаёт его представление внутри JVM (`Class<?>`).

Классы не обязаны загружаться все сразу при старте приложения. JVM может загружать их **по мере необходимости**.

Например, когда приложение впервые обращается к `com.example.UserService`, JVM должна понять:

1. не загружен ли этот класс ранее;
2. кто должен его загрузить;
3. где найти его байткод;
4. корректен ли найденный class-файл;
5. как связать класс с другими типами.

#### Основные ClassLoader'ы

В современной Java обычно выделяют три основных уровня:

```text
Bootstrap ClassLoader
        ▲
        │
Platform ClassLoader
        ▲
        │
Application ClassLoader
```

**Bootstrap ClassLoader** — самый верхний уровень. Загружает базовые классы и критически важные модули Java, включая `java.base`.

Например:

```java
System.out.println(String.class.getClassLoader());
```

Обычно увидим:

```text
null
```

Это **не означает, что у `String` нет загрузчика**. В Java API Bootstrap ClassLoader исторически представлен как `null`.

**Platform ClassLoader** загружает классы платформы, которые не относятся к базовой части, загружаемой Bootstrap.

**Application (System) ClassLoader** обычно загружает код нашего приложения и его зависимости из classpath.

```java
public class Main {
    public static void main(String[] args) {
        System.out.println(Main.class.getClassLoader());
    }
}
```

Для обычного приложения здесь, как правило, будет Application ClassLoader.

> **Нюанс версий:** до Java 9 существовал **Extension ClassLoader**, связанный с механизмом extensions (`jre/lib/ext`). Начиная с Java 9 его роль в современной модели занимает **Platform ClassLoader**. Поэтому ответ «Bootstrap → Extension → Application» относится к старым версиям Java.

#### Parent Delegation Model

По умолчанию загрузчики используют модель **parent-first delegation**.

Если Application ClassLoader получил запрос на загрузку класса, он не обязательно сразу ищет его среди классов приложения. Сначала запрос делегируется вверх по цепочке.

Упрощённо:

```text
Application
    │
    │ delegate
    ▼
Platform
    │
    │ delegate
    ▼
Bootstrap
    │
    ├── найден → вернуть класс
    │
    └── не найден
           ▲
           │ Platform пробует найти сам
           ▲
           │ Application пробует найти сам
```

Для типичного `ClassLoader.loadClass(name)` логика выглядит примерно так:

1. Проверить, не был ли класс уже загружен.
2. Передать запрос родительскому загрузчику.
3. Если родитель класс не нашёл — попытаться найти его самостоятельно.
4. Если класс нигде не найден — загрузка завершается ошибкой.

Зачем сначала спрашивать родителя? Одна из причин — **предсказуемость и защита базовых классов платформы**. Код приложения не должен случайно подменить, например, стандартный `java.lang.String` своей копией.

**Parent-first — стандартная модель, но не абсолютное правило для всех систем.** Пользовательские загрузчики и некоторые контейнеры/плагинные системы могут применять другую стратегию, например child-first.

#### Loading, Linking и Initialization

Жизненный цикл класса не заканчивается чтением `.class`-файла.

Упрощённо:

```text
Loading
   │
   ▼
Linking
 ├── Verification
 ├── Preparation
 └── Resolution
   │
   ▼
Initialization
```

**Loading** — JVM находит бинарное представление класса и создаёт его представление в памяти.

**Linking** — подготовка загруженного класса к использованию:

- **Verification** — проверка корректности class-файла и байткода.
- **Preparation** — создаются необходимые структуры для static-полей и устанавливаются их начальные значения по правилам JVM.
- **Resolution** — символические ссылки на другие классы, методы и поля преобразуются в конкретные ссылки JVM. Resolution может выполняться лениво.

**Initialization** — выполняется логика инициализации класса: в частности, присваивания static-полям и static-блоки, собранные компилятором в метод инициализации класса `<clinit>`.

Пример:

```java
class Config {
    static int port = initPort();

    static {
        System.out.println("Config initialized");
    }

    private static int initPort() {
        return 8080;
    }
}
```

Загрузка класса и его **инициализация — не одно и то же**. JVM может загрузить и связать класс раньше, чем возникнет необходимость его инициализировать.

#### Идентичность класса: имя + ClassLoader

Для JVM тип определяется не только полным именем класса.

Упрощённо:

```text
Class identity = binary name + defining ClassLoader
```

Допустим, два независимых ClassLoader загрузили один и тот же:

```text
com.example.Plugin
```

Для JVM это могут быть **два разных типа**, даже если байткод взят из одного и того же JAR.

Именно это позволяет плагинным системам изолировать разные версии библиотек. Но отсюда возникает и важная ловушка: объект класса, загруженного одним ClassLoader, нельзя автоматически считать экземпляром «такого же» класса, загруженного другим ClassLoader. Это может привести к `ClassCastException`.

#### Custom ClassLoader

Можно создать собственный загрузчик:

```java
class PluginClassLoader extends ClassLoader {

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = loadClassBytes(name); // условный метод
        return defineClass(name, bytes, 0, bytes.length);
    }

    private byte[] loadClassBytes(String name) {
        // Читаем bytecode из нужного источника
        throw new UnsupportedOperationException();
    }
}
```

Обычно переопределяют **`findClass()`**, а стандартный `loadClass()` оставляют без изменений, чтобы сохранить parent-first delegation.

Собственные загрузчики нужны, например, для:

- плагинных архитектур;
- изоляции разных версий библиотек;
- hot reload / hot deploy;
- загрузки байткода из нестандартного источника.

Для обычного backend-приложения писать свой ClassLoader почти никогда не требуется, но понимание механизма полезно при разборе контейнеров, application servers, драйверов, SPI и проблем с зависимостями.

#### Типичные ошибки

**`ClassNotFoundException`** — приложение явно пытается загрузить класс, но загрузчик не может его найти.

**`NoClassDefFoundError`** — JVM во время выполнения не может получить определение класса, которое требуется программе; причины шире, чем просто «нет JAR в runtime», например предыдущая неудачная инициализация класса.

**`LinkageError`** — семейство ошибок, возникающих при проблемах связывания/определения классов.

**`ClassCastException` при разных ClassLoader'ах** — два класса могут иметь одинаковое имя, но быть разными типами для JVM.

#### Что важно запомнить

- ClassLoader загружает классы **по мере необходимости**, а не обязательно все при старте.
- Основная цепочка современной Java: **Bootstrap → Platform → Application**.
- До Java 9 вместо Platform в старой модели использовался **Extension ClassLoader**.
- Стандартная модель делегирования — **parent-first**: сначала пытается родитель, затем текущий загрузчик.
- Загрузка класса проходит через **Loading → Linking → Initialization**; Linking включает Verification, Preparation и Resolution.
- Для JVM идентичность типа определяется **именем класса + defining ClassLoader**.
- Пользовательские ClassLoader'ы позволяют изолировать плагины и версии библиотек.

#### На собеседовании

**Какие основные ClassLoader'ы есть в Java?**

> В современной Java это Bootstrap, Platform и Application ClassLoader. Bootstrap загружает базовую часть платформы, Platform — остальные платформенные классы, а Application — обычно код приложения и зависимости. До Java 9 вместо Platform использовался Extension ClassLoader.

**Как работает parent delegation?**

> Когда загрузчик получает запрос на класс, он сначала проверяет уже загруженные классы и делегирует поиск родителю. Если родитель не нашёл класс, текущий загрузчик пытается загрузить его сам. Это помогает избежать дублирования и случайной подмены базовых классов.

**Могут ли два класса с одинаковым полным именем быть разными типами?**

> Да. Для JVM идентичность типа определяется не только именем, но и defining ClassLoader. Поэтому одинаковый класс, загруженный двумя независимыми ClassLoader'ами, может считаться двумя разными типами.

**Чем Loading отличается от Initialization?**

> Loading создаёт представление класса в JVM на основе его бинарного представления. После этого идёт Linking. Initialization — отдельный более поздний этап, на котором выполняется инициализация static-полей и static-блоков класса.

### 1.3. Память JVM: Heap, Stack, Metaspace и Code Cache

Во время работы Java-программы JVM использует несколько областей памяти с разным назначением. Для собеседования важно не просто перечислить их, а понимать **что где хранится, кому область принадлежит и какие ошибки возникают при её исчерпании**.

Упрощённая картина:

```text
JVM process
│
├── Heap                         ← общий для потоков
│     └── объекты и массивы
│
├── JVM Stack (у каждого потока свой)
│     └── Stack Frames
│           ├── локальные переменные
│           ├── ссылки
│           └── operand stack
│
├── Metaspace                    ← метаданные загруженных классов (HotSpot)
│
└── Code Cache                   ← машинный код, созданный JIT (HotSpot)
```

> Важно различать **области, определённые JVM Specification**, и конкретную организацию памяти в **HotSpot**. Например, JVM Specification определяет Heap, JVM Stacks и Method Area, а Metaspace и Code Cache — детали реализации HotSpot.

#### Heap

**Heap (куча)** — общая для всех потоков область JVM, из которой обычно выделяется память под объекты и массивы.

```java
User user = new User("Alex");
int[] numbers = new int[10];
```

Упрощённо:

```text
Stack                         Heap
┌──────────────┐             ┌────────────────────┐
│ user ────────┼────────────►│ User object        │
│              │             │ name → "Alex"      │
│ numbers ─────┼────────────►│ int[10]            │
└──────────────┘             └────────────────────┘
```

Переменная `user` в данном примере — **ссылка**, а сам объект `User` находится в heap. Если объект содержит примитивное поле, это поле является частью самого объекта.

Heap обслуживается Garbage Collector. Подробно поколения, reachability, GC Roots и конкретные сборщики разберём в следующем подразделе.

При нехватке heap можно получить:

```text
java.lang.OutOfMemoryError: Java heap space
```

Размер heap в HotSpot обычно настраивают параметрами:

```bash
-Xms512m
-Xmx2g
```

где `-Xms` задаёт начальный размер heap, а `-Xmx` — максимальный.

#### JVM Stack

У **каждого Java-потока свой JVM Stack**. Он создаётся вместе с потоком и используется во время выполнения методов.

При каждом вызове метода создаётся **Stack Frame (кадр стека)**. После завершения метода соответствующий frame удаляется.

Пример:

```java
static int square(int value) {
    int result = value * value;
    return result;
}

public static void main(String[] args) {
    int number = 5;
    int answer = square(number);
}
```

Упрощённо во время выполнения `square()`:

```text
Thread Stack

┌────────────────────────────┐
│ square() frame             │  ← текущий вызов
│ value = 5                  │
│ result = 25                │
├────────────────────────────┤
│ main() frame               │
│ number = 5                 │
│ answer = ...               │
└────────────────────────────┘
```

Когда `square()` завершится, его frame исчезнет, а выполнение продолжится в `main()`.

#### Что находится внутри Stack Frame?

Согласно модели JVM, frame содержит в том числе:

- **local variables** — локальные переменные и параметры;
- **operand stack** — стек операндов, который bytecode использует для вычислений;
- данные, необходимые для возврата из метода и поддержки вызовов.

Например, выражение:

```java
int result = a + b;
```

на уровне bytecode концептуально использует operand stack: значения загружаются на стек операндов, выполняется операция сложения, результат сохраняется.

Для обычной подготовки к интервью достаточно помнить:

```text
JVM Stack
    └── Frame одного вызова метода
          ├── Local Variables
          ├── Operand Stack
          └── служебные данные вызова
```

#### StackOverflowError

Если вызовов становится слишком много и стек потока исчерпывается, возникает `StackOverflowError`.

Классический пример — бесконечная рекурсия:

```java
static void recursive() {
    recursive();
}
```

Каждый новый вызов создаёт новый frame:

```text
recursive()
recursive()
recursive()
recursive()
...
↓
StackOverflowError
```

Размер стека потока в HotSpot можно настраивать параметром `-Xss`.

Например:

```bash
-Xss1m
```

Большой `-Xss` позволяет отдельному потоку иметь более глубокий стек, но одновременно увеличивает потенциальное потребление памяти при большом количестве потоков.

#### Важный нюанс: «объекты всегда в Heap, переменные всегда в Stack»

Такую формулу часто используют для обучения, но она **слишком грубая**.

Для собеседования безопаснее говорить:

> Объекты и массивы обычно размещаются в heap. JVM Stack хранит frames вызовов, внутри которых находятся локальные переменные и промежуточные значения. Локальная переменная ссылочного типа содержит ссылку на объект, а не сам объект.

Почему «всегда» опасно? JVM имеет право применять оптимизации. Например, JIT может выполнить escape analysis и устранить отдельную аллокацию вообще. Поэтому не стоит воспринимать учебную схему как описание физического расположения каждого значения после оптимизаций.

#### Metaspace

**Metaspace** — область нативной памяти, которую HotSpot использует для хранения метаданных загруженных классов.

Упрощённо там находятся данные, описывающие классы:

- информация о структуре класса;
- методы и поля;
- runtime constant pool и связанные метаданные;
- данные, необходимые JVM для работы с загруженными типами.

Главная мысль:

```text
Heap       → экземпляры объектов
Metaspace  → метаданные загруженных классов
```

До Java 8 HotSpot использовал **Permanent Generation (PermGen)**. Начиная с Java 8 PermGen был удалён, а метаданные классов хранятся с использованием Metaspace.

Metaspace использует native memory и по умолчанию может расти в зависимости от доступной памяти. Его верхнюю границу можно ограничить:

```bash
-XX:MaxMetaspaceSize=256m
```

При исчерпании возможна ошибка:

```text
java.lang.OutOfMemoryError: Metaspace
```

Одна из причин проблем с Metaspace — постоянное создание новых ClassLoader'ов и загрузка новых классов, когда старые ClassLoader'ы остаются достижимыми и не могут быть освобождены.

#### Code Cache

**Code Cache** — область памяти HotSpot, в которой хранится скомпилированный машинный код, созданный JIT.

Связь с предыдущей темой:

```text
Bytecode
   │
   │ JIT compilation
   ▼
Native machine code
   │
   ▼
Code Cache
```

Когда JVM снова выполняет уже скомпилированный участок, она может использовать машинный код из Code Cache вместо повторной интерпретации этого участка.

Code Cache — **не место хранения Java-объектов** и не замена heap.

#### Где что хранится?

Для быстрого повторения:

| Что | Где концептуально находится |
| --- | --- |
| Объекты и массивы | Heap |
| Поля объекта | В составе объекта в Heap |
| Stack Frame вызванного метода | JVM Stack конкретного потока |
| Локальный примитив | Local Variables текущего Frame |
| Локальная ссылка на объект | Local Variables Frame; объект — в Heap |
| Метаданные загруженных классов | Metaspace в HotSpot |
| JIT-скомпилированный машинный код | Code Cache в HotSpot |

Со **static-полями** лучше не использовать упрощённый ответ «static лежит в Metaspace». Спецификация JVM не требует такого физического размещения. В HotSpot метаданные класса и значения его Java static-полей — не одно и то же; для интервью важнее понимать, что static-поле принадлежит **классу**, а не экземпляру. Детали конкретного физического размещения являются implementation detail.

#### Heap и Stack — главное различие

| Heap | JVM Stack |
| --- | --- |
| Общий для потоков | У каждого потока свой |
| Обычно содержит объекты и массивы | Содержит frames вызовов |
| Управляется GC | Frames удаляются при возврате из методов |
| Может привести к `OutOfMemoryError: Java heap space` | Глубокие вызовы могут привести к `StackOverflowError` |
| Размер обычно контролируется `-Xms/-Xmx` | Размер стека потока — `-Xss` |

#### Что важно запомнить

- **Heap** — общая область, где обычно размещаются объекты и массивы.
- **JVM Stack** принадлежит конкретному потоку и состоит из frames вызванных методов.
- **Stack Frame** содержит local variables, operand stack и служебные данные выполнения метода.
- **Metaspace** в HotSpot хранит метаданные загруженных классов и использует native memory; с Java 8 он заменил PermGen.
- **Code Cache** хранит машинный код, созданный JIT в HotSpot.
- Не стоит механически отвечать «всё локальное — Stack, всё static — Metaspace»: реальная модель и оптимизации JVM сложнее этой мнемоники.

#### На собеседовании

**Чем Heap отличается от Stack?**

> Heap — общая для потоков область, где обычно размещаются объекты и массивы и которой управляет GC. У каждого потока свой JVM Stack, состоящий из frames вызванных методов. Frames содержат локальные переменные, operand stack и служебные данные выполнения.

**Что такое Stack Frame?**

> Это структура, создаваемая в JVM Stack при вызове метода. Она содержит локальные переменные метода, operand stack и данные, необходимые для выполнения и возврата из метода. После завершения вызова frame удаляется.

**Что хранится в Metaspace?**

> В HotSpot Metaspace используется для метаданных загруженных классов. Он находится в native memory и с Java 8 заменил PermGen. При чрезмерной загрузке классов или утечках ClassLoader'ов можно получить OutOfMemoryError: Metaspace.

**Где находится объект, если ссылка на него — локальная переменная?**

> В обычной модели локальная ссылка находится в frame текущего потока, а объект размещён в heap. Но JIT может оптимизировать аллокации, поэтому это не нужно трактовать как абсолютное физическое правило для любого оптимизированного кода.

- Основная база: пользовательский конспект «Копия Срез 2–8 Java», тема «Области памяти в Java, Runtime data areas»: Heap, Stack, Metaspace и Code Cache.
- [JVM Specification — Run-Time Data Areas](https://docs.oracle.com/en/java/javase/26/docs/specs/jvms/se26/html/jvms-2.html#jvms-2.5) — Heap, JVM Stacks, Method Area и Frames на уровне спецификации.
- [Java HotSpot VM Guide](https://docs.oracle.com/en/java/javase/26/vm/index.html) — детали реализации HotSpot.

### 1.4. Garbage Collection: достижимость, поколения и сборщики

**Garbage Collector (GC)** — механизм автоматического управления памятью, который находит объекты, больше не нужные программе, и освобождает занимаемую ими память.

Ключевая идея: GC не пытается угадать, «используется ли объект по смыслу». Он определяет, **достижим ли объект из набора корневых ссылок (GC Roots)**.

#### Reachability и GC Roots

Представим граф объектов:

```text
GC Root
   │
   ▼
 Object A ─────► Object B

 Object C ─────► Object D
```

`A` и `B` достижимы от GC Root, поэтому считаются живыми. Если до `C` и `D` больше нет пути от корней, весь этот изолированный граф может быть собран GC — даже если объекты внутри него ссылаются друг на друга.

К типичным **GC Roots** относятся, например:

- ссылки из активных stack frames потоков;
- static-ссылки загруженных классов;
- ссылки из JNI;
- внутренние ссылки самой JVM.

Пример:

```java
User user = new User();
user = null;
```

После `user = null` объект **не обязательно удаляется немедленно**. Если других путей от GC Roots к нему нет, он становится кандидатом на сборку. Когда именно GC освободит память — не гарантируется.

> Поэтому фраза «GC удаляет объекты, на которые нет ссылок» неточна. Важна не абсолютная численность ссылок, а **достижимость от GC Roots**.

#### Garbage Collector не предотвращает все memory leaks

Автоматический GC не означает, что в Java невозможны утечки памяти.

Например:

```java
static final List<byte[]> CACHE = new ArrayList<>();

public static void add() {
    CACHE.add(new byte[1_000_000]);
}
```

Если список постоянно растёт, объекты остаются достижимыми через static-ссылку:

```text
GC Root
   │
   ▼
static CACHE
   │
   ├──► byte[]
   ├──► byte[]
   └──► byte[]
```

GC **не имеет права их удалить**, хотя приложению они могут быть уже логически не нужны.

Это и есть важный вид memory leak в managed-языках: память занята объектами, которые программе больше не нужны, но технически всё ещё достижимы.

#### Почему используются поколения?

Наблюдение, на котором основаны многие generational GC:

> Большинство объектов живут недолго.

Например, временные DTO, строки, промежуточные коллекции и объекты запроса часто перестают быть нужны вскоре после создания.

Поэтому традиционная generational-модель разделяет heap на области:

```text
Heap
├── Young Generation
│     ├── Eden
│     ├── Survivor 0
│     └── Survivor 1
│
└── Old / Tenured Generation
```

Новые объекты **обычно** аллоцируются в Young Generation. Пережившие несколько циклов сборки объекты могут быть **promoted** в Old Generation.

Упрощённо:

```text
new object
    │
    ▼
  Eden
    │
    │ пережил GC
    ▼
Survivor
    │
    │ переживает следующие GC
    ▼
   Old
```

**Важно:** эта схема полезна для понимания Serial/Parallel и общей идеи generational GC, но не является универсальным физическим устройством всех современных сборщиков. Например, G1 организует heap в регионы, а современные режимы ZGC имеют собственную архитектуру.

#### Minor, Major и Full GC

Эти термины широко используются, но их смысл зависит от конкретного collector.

Обычно:

- **Minor GC** — сборка Young Generation;
- **Major GC** — часто подразумевают работу со старым поколением;
- **Full GC** — сборка, затрагивающая весь или почти весь heap и часто другие области/служебные структуры JVM.

Нельзя считать `Major GC` и `Full GC` строгими универсальными синонимами. Для диагностики производительности важнее смотреть **какой collector используется и какое событие реально записано в GC log**.

#### Stop-The-World

**Stop-The-World (STW)** — пауза, во время которой JVM приостанавливает application threads (mutator threads), чтобы выполнить определённую фазу работы GC или другую VM-операцию.

```text
Application: ────────┐      ┌──────────────
                     │ STOP │
GC:                  └──────┘
                       STW
```

STW не означает, что любой GC целиком выполняется при остановленном приложении. Современные collectors стараются выполнять значительную часть работы **concurrently** с application threads, оставляя STW только для отдельных фаз.

Поэтому два важных показателя GC:

- **throughput** — сколько времени приложение реально выполняет полезную работу;
- **latency / pause time** — насколько долгими могут быть паузы.

Часто между ними приходится искать компромисс.

#### Основные алгоритмические идеи

GC-алгоритмы строятся из нескольких базовых подходов.

**Mark-Sweep**

1. Найти и пометить достижимые объекты.
2. Освободить память недостижимых.

Минус — после освобождения могут оставаться разрозненные свободные участки, то есть **фрагментация**.

**Mark-Compact**

После определения живых объектов они перемещаются ближе друг к другу:

```text
До:
[A][free][B][free][free][C]

После:
[A][B][C][      free       ]
```

Это уменьшает фрагментацию, но перемещение объектов требует дополнительной работы.

**Copying / Evacuation**

Живые объекты копируются из одной области памяти в другую. Подход особенно выгоден там, где большинство объектов быстро умирает: копировать приходится только небольшое число выживших объектов.

Современные collectors комбинируют эти идеи, а не обязательно используют ровно один алгоритм.

#### Основные Garbage Collectors

Для собеседования полезно понимать **цель** каждого collector, а не запоминать все внутренние фазы.

| Collector | Основная цель | Общая идея |
| --- | --- | --- |
| **Serial GC** | Простота, небольшие heap | Основная GC-работа выполняется одним GC-потоком; STW |
| **Parallel GC** | Высокий throughput | Использует несколько GC-потоков; делает ставку на пропускную способность |
| **G1 GC** | Баланс throughput и предсказуемых пауз | Heap разделён на регионы; выбирает регионы для сборки и эвакуации |
| **ZGC** | Очень низкие паузы | Большая часть тяжёлой работы выполняется concurrent с приложением |
| **Shenandoah** | Низкие паузы | Выполняет в том числе перемещение объектов преимущественно concurrent |

##### Serial GC

Подходит для небольших приложений и окружений с ограниченными ресурсами.

Запуск:

```bash
-XX:+UseSerialGC
```

Его преимущество — простота и небольшие накладные расходы. Для большого server-side приложения длительные STW-паузы обычно делают его менее привлекательным.

##### Parallel GC

Использует несколько GC threads и ориентирован прежде всего на **throughput**.

```bash
-XX:+UseParallelGC
```

Хороший мысленный ориентир: если важнее выполнить максимум работы за единицу времени, а более заметные паузы допустимы, Parallel GC может быть подходящим кандидатом.

##### G1 GC

**G1 (Garbage-First)** делит heap на множество одинаковых по размеру **regions**, а не опирается на одно непрерывное физическое разделение heap на привычные Eden/Survivor/Old области.

Логически регионы всё равно могут выполнять роли Eden, Survivor и Old:

```text
Heap regions:

[E][E][O][S][O][E][free][O][free]...
```

G1 старается выбирать для очередной сборки регионы, очистка которых даст хороший эффект, и выполняет эвакуацию живых объектов.

Для G1 можно задавать **pause-time goal**, например:

```bash
-XX:MaxGCPauseMillis=200
```

Это **цель**, а не жёсткая гарантия, что каждая пауза будет короче 200 мс.

G1 стал default collector в HotSpot начиная с **JDK 9**.

##### ZGC

**ZGC** разработан для очень низких пауз и больших heap. Значительная часть marking, relocation и другой GC-работы выполняется concurrent с приложением.

Главная идея для интервью:

> ZGC переносит большую часть тяжёлой работы из STW-фаз в concurrent-фазы, поэтому длительность пауз значительно меньше зависит от размера heap, чем у традиционных stop-the-world collectors.

Не стоит обещать конкретное значение вроде «паузы всегда < 10 ms»: реальная latency зависит от версии JDK, железа и workload.

##### Shenandoah

**Shenandoah** также ориентирован на low-pause workloads и выполняет значительную часть работы, включая compaction/evacuation, concurrent с приложением.

На уровне интервью обычно достаточно понимать общую цель:

```text
Parallel GC  → throughput
G1           → balance / pause-time goals
ZGC          → ultra-low latency
Shenandoah   → low latency
```

#### А что с CMS?

В старых материалах часто встречается **CMS (Concurrent Mark Sweep)**. Он действительно был важным low-pause collector и выполнял часть работы concurrent.

Но для современной Java важно знать исторический контекст:

- CMS был **deprecated в JDK 9**;
- CMS был **removed в JDK 14**.

Поэтому на современном собеседовании его полезно знать как исторический collector, но выбирать CMS для новой актуальной JVM уже нельзя.

#### Можно ли вызвать GC вручную?

Можно попросить JVM выполнить GC:

```java
System.gc();
```

или:

```java
Runtime.getRuntime().gc();
```

Но это **не гарантия немедленной сборки**. Это запрос JVM, а не команда «прямо сейчас удали мусор».

В прикладном backend-коде вручную вызывать GC обычно не следует. Если приложение требует постоянных ручных вызовов GC, правильнее искать причину: лишние аллокации, слишком маленький heap, удержание объектов или неверные настройки collector.

#### Типичные ошибки в понимании GC

**«Если присвоить ссылке null, объект сразу удалится».**  
Нет. Объект лишь может стать недостижимым. Время запуска GC не определяется этой строкой.

**«GC гарантирует отсутствие memory leaks».**  
Нет. Если ненужный объект остаётся достижимым, GC считает его живым.

**«Full GC происходит только когда Old полностью заполнен».**  
Слишком грубое правило. Причины и поведение зависят от collector и конкретного состояния JVM.

**«Любой GC полностью останавливает приложение на всё время сборки».**  
Нет. Современные collectors выполняют часть фаз concurrently, хотя STW-фазы всё равно существуют.

**«Young = Eden + S0 + S1 для любого collector».**  
Это хорошая учебная модель generational collectors, но не универсальная физическая разметка всех современных GC.

#### Что важно запомнить

- GC определяет живые объекты через **reachability от GC Roots**.
- Недостижимый объект становится кандидатом на сборку, но не обязан исчезнуть немедленно.
- GC не спасает от утечек, если ненужные объекты всё ещё **достижимы**.
- Generational GC опирается на идею, что большинство объектов живут недолго.
- **STW** — пауза application threads; concurrent GC уменьшает объём работы внутри таких пауз, но не обязательно устраняет их полностью.
- **Parallel** ориентирован на throughput, **G1** — на баланс и pause goals, **ZGC/Shenandoah** — на низкую latency.
- CMS — исторически важный collector, но удалён из JDK начиная с 14.

#### На собеседовании

**Как GC понимает, что объект можно удалить?**

> JVM начинает обход графа объектов от GC Roots. Всё достижимое считается живым. Объекты, до которых нет пути от корней, могут быть собраны GC. Поэтому циклические ссылки сами по себе не мешают сборке, если весь цикл недостижим.

**Что такое GC Roots?**

> Это начальные точки, от которых GC определяет достижимость объектов. К ним относятся, например, ссылки из активных stack frames, static-ссылки загруженных классов, JNI-ссылки и некоторые внутренние ссылки JVM.

**Чем G1 отличается от Parallel GC?**

> Parallel GC в первую очередь оптимизирует throughput и использует параллельные GC-потоки, но допускает заметные STW-паузы. G1 делит heap на регионы и старается балансировать throughput с целевым временем пауз, выбирая регионы для очередной сборки.

**Может ли быть memory leak в Java при наличии GC?**

> Да. GC удаляет недостижимые объекты. Если объект приложению уже не нужен, но на него остаётся достижимая сильная ссылка, например из бесконечно растущего static cache, GC не сможет его удалить.

### 1.5. Типы данных Java: primitives, references и преобразования

В Java тип определяет, **какие значения может хранить переменная и какие операции над ними разрешены**. На верхнем уровне типы удобно разделить на две группы:

```text
Java types
├── Primitive types
│   ├── boolean
│   ├── byte, short, int, long
│   ├── char
│   └── float, double
│
└── Reference types
    ├── classes
    ├── interfaces
    ├── arrays
    └── ...
```

> В исходном конспекте отдельного полноценного блока по базовым типам данных найдено мало, поэтому этот подраздел в основном дополняет базу материалом из Java Language Specification.

#### Primitive types

В Java есть **8 primitive types**:

| Тип | Размер / представление | Пример |
| --- | --- | --- |
| `byte` | 8-bit signed integer | `byte b = 10;` |
| `short` | 16-bit signed integer | `short s = 1000;` |
| `int` | 32-bit signed integer | `int n = 42;` |
| `long` | 64-bit signed integer | `long id = 42L;` |
| `float` | 32-bit IEEE 754 floating-point | `float f = 1.5F;` |
| `double` | 64-bit IEEE 754 floating-point | `double d = 1.5;` |
| `char` | 16-bit unsigned UTF-16 code unit | `char c = 'A';` |
| `boolean` | `true` или `false` | `boolean active = true;` |

Диапазоны целочисленных типов:

```text
byte   -128 ... 127
short  -32768 ... 32767
int    -2^31 ... 2^31 - 1
long   -2^63 ... 2^63 - 1
char   0 ... 65535
```

Для `boolean` Java Language Specification не задаёт «размер в байтах», который следует использовать как языковую гарантию. Поэтому ответ «boolean занимает 1 byte» для собеседования слишком категоричен: физическое представление зависит от реализации JVM и контекста хранения.

#### Primitive и Reference — главное отличие

Primitive-переменная хранит **само значение**:

```java
int age = 30;
```

Reference-переменная содержит **ссылочное значение**, позволяющее обратиться к объекту:

```java
User user = new User();
```

Упрощённо:

```text
int age = 30

age
┌────┐
│ 30 │
└────┘

User user = new User()

user                     object
┌───────────┐           ┌────────────┐
│ reference ├──────────►│ User       │
└───────────┘           └────────────┘
```

Reference-переменная может иметь значение `null`:

```java
User user = null;
```

Primitive — нет:

```java
int value = null; // compile error
```

Wrapper-классы (`Integer`, `Long`, `Boolean` и т. д.) являются **reference types**, а не primitives. Autoboxing подробно рассмотрим следующим подразделом.

#### Default values и локальные переменные

Поля объекта получают default values автоматически:

```java
class Example {
    int number;       // 0
    boolean active;   // false
    String text;      // null
}
```

Для полей основные значения по умолчанию:

- integer types → `0`;
- floating-point → `0.0`;
- `char` → `'\u0000'`;
- `boolean` → `false`;
- references → `null`.

Но **локальная переменная не получает значение, которое можно просто прочитать без инициализации**:

```java
void test() {
    int value;
    System.out.println(value); // compile error
}
```

Компилятор применяет правила **definite assignment** и не позволит использовать локальную переменную до того, как она гарантированно получила значение.

#### Integer literals: почему иногда нужен L?

Целочисленный литерал без суффикса обычно имеет тип `int`, если значение помещается в `int`.

```java
int a = 100;
long b = 100;
```

Во второй строке `int`-значение безопасно расширяется до `long`.

Но большое значение нужно записать как `long` literal:

```java
long population = 8_000_000_000L;
```

Без `L` литерал не представим как обычный decimal `int`.

Обычно используют заглавную `L`, потому что строчная `l` визуально похожа на цифру `1`.

#### Floating-point literals: почему float требует F?

Floating-point literal без суффикса имеет тип `double`:

```java
double d = 1.5;
```

Поэтому это не скомпилируется:

```java
float f = 1.5; // compile error
```

Нужно явно указать `float`:

```java
float f = 1.5F;
```

Причина в том, что преобразование `double → float` является narrowing conversion и может потерять точность.

#### Widening conversion

**Widening primitive conversion** — преобразование в тип, способный представить более широкий набор значений соответствующей категории. Во многих случаях выполняется автоматически:

```java
int value = 100;
long big = value;
double d = big;
```

Упрощённая цепочка числовых расширений:

```text
byte ─► short ─► int ─► long ─► float ─► double
          char ─► int ────────► ...
```

Но «widening» не означает «никогда не теряется точность».

Например:

```java
long value = 9_007_199_254_740_993L;
double d = value;

System.out.println((long) d == value); // false
```

`double` имеет огромный диапазон, но не способен точно представить каждое 64-bit integer value.

#### Narrowing conversion

При переходе к более узкому типу обычно требуется явный cast:

```java
int value = 130;
byte b = (byte) value;

System.out.println(b); // -126
```

Почему `-126`? При narrowing сохраняются только подходящие младшие биты; результат может полностью изменить числовое значение.

Поэтому cast означает не «сделай безопасно», а скорее:

> Я явно разрешаю это преобразование и принимаю возможную потерю информации.

#### Integer overflow

Java не выбрасывает исключение при обычном переполнении `int` или `long`:

```java
int max = Integer.MAX_VALUE;
System.out.println(max + 1);
```

Результат:

```text
-2147483648
```

Целочисленная арифметика для этих типов работает с фиксированной разрядностью, поэтому происходит wrap-around.

Если переполнение должно считаться ошибкой, можно использовать методы:

```java
Math.addExact(a, b);
Math.multiplyExact(a, b);
```

Они выбрасывают `ArithmeticException` при overflow.

#### Numeric promotion: почему byte + byte даёт int?

Это популярная ловушка:

```java
byte a = 10;
byte b = 20;

// byte c = a + b; // compile error
int c = a + b;
```

При арифметических операциях `byte`, `short` и `char` обычно проходят **binary numeric promotion** до `int`.

Поэтому результат `a + b` здесь имеет тип `int`.

Ещё пример:

```java
byte x = 10;
x += 1;       // OK
// x = x + 1; // compile error
```

Compound assignment содержит неявное преобразование обратно к типу левой части. То есть `x += 1` по правилам языка не полностью эквивалентно простой записи `x = x + 1`.

#### char — это не «маленькая String»

`char` представляет **один UTF-16 code unit**, а не обязательно один полноценный Unicode-символ.

```java
char c = 'A';
System.out.println((int) c); // 65
```

Некоторые Unicode code points требуют **двух char** (surrogate pair). Поэтому:

```java
String emoji = "😀";
System.out.println(emoji.length()); // 2
```

`String.length()` возвращает количество UTF-16 code units, а не количество визуально воспринимаемых символов.

Эту тему подробнее разберём в отдельной главе **String & Immutability**.

#### float и double: почему 0.1 + 0.2 != 0.3?

`float` и `double` используют binary floating-point representation. Многие привычные десятичные дроби нельзя представить в двоичной системе точно.

```java
double result = 0.1 + 0.2;

System.out.println(result);        // 0.30000000000000004
System.out.println(result == 0.3); // false
```

Поэтому сравнение вычисленных floating-point values через `==` часто некорректно для прикладной задачи.

Для научных расчётов обычно учитывают допустимую погрешность:

```java
double epsilon = 1e-9;

if (Math.abs(a - b) < epsilon) {
    // достаточно близкие значения для выбранной задачи
}
```

Для денег, где важна **точная десятичная арифметика**, обычно используют `BigDecimal`:

```java
BigDecimal price = new BigDecimal("0.1");
BigDecimal tax = new BigDecimal("0.2");

System.out.println(price.add(tax)); // 0.3
```

Предпочтительнее строковый конструктор или `BigDecimal.valueOf(...)`, а не `new BigDecimal(0.1)`, потому что последний получает уже неточное binary floating-point значение.

#### NaN и Infinity

Floating-point арифметика имеет специальные значения:

```java
double positiveInfinity = 1.0 / 0.0;
double nan = 0.0 / 0.0;

System.out.println(positiveInfinity); // Infinity
System.out.println(nan);              // NaN
```

В отличие от integer division:

```java
int x = 1 / 0; // ArithmeticException
```

Особенно важно поведение `NaN`:

```java
double value = Double.NaN;

System.out.println(value == value);       // false
System.out.println(Double.isNaN(value));  // true
```

`NaN` не равен даже самому себе при обычном операторе `==`.

#### Что важно запомнить

- В Java **8 primitive types**; всё остальное относится к reference types.
- Reference может быть `null`, primitive — нет.
- Поля получают default values, а локальные переменные должны пройти definite assignment перед чтением.
- `byte`, `short` и `char` в арифметике часто продвигаются до `int`.
- Widening обычно не требует cast, narrowing обычно требует, но widening всё равно иногда может потерять **точность**.
- Integer overflow обычно не выбрасывает исключение; для контролируемой арифметики есть `Math.*Exact`.
- `float/double` не подходят для точной денежной арифметики; обычно используют `BigDecimal`.
- `char` — UTF-16 code unit, а не гарантированно один Unicode character.

#### На собеседовании

**Какие primitive types есть в Java?**

> Восемь: byte, short, int, long, float, double, char и boolean. Первые четыре — целочисленные signed-типы, char — unsigned UTF-16 code unit, float и double — floating-point, boolean хранит true или false.

**Почему byte + byte возвращает int?**

> Из-за правил numeric promotion. Перед большинством арифметических операций byte, short и char продвигаются до int, поэтому результат сложения двух byte имеет тип int.

**Чем widening отличается от narrowing?**

> Widening преобразует значение к более широкому типу и обычно выполняется автоматически. Narrowing может отбросить часть информации и обычно требует явного cast. При этом widening тоже не гарантирует сохранение точности, например long → double может округлить большое целое.

**Почему для денег не стоит использовать double?**

> Потому что double хранит двоичную floating-point аппроксимацию, и многие десятичные дроби вроде 0.1 представлены неточно. Для точной десятичной арифметики обычно используют BigDecimal с корректным способом создания значения.

- В пользовательском конспекте отдельный полноценный блок по primitive/reference types в найденных материалах отсутствует; текущий подраздел добавлен как необходимая база Java Core.

- [Java Language Specification — Conversions and Contexts](https://docs.oracle.com/javase/specs/jls/se26/html/jls-5.html) — widening, narrowing и numeric promotion.
- [Java Language Specification — Expressions](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html) — арифметика, compound assignment и операторы.

### 1.6. Wrapper classes и autoboxing/unboxing

Для каждого primitive type в Java существует соответствующий **wrapper class (класс-обёртка)**:

| Primitive | Wrapper |
| --- | --- |
| `byte` | `Byte` |
| `short` | `Short` |
| `int` | `Integer` |
| `long` | `Long` |
| `float` | `Float` |
| `double` | `Double` |
| `char` | `Character` |
| `boolean` | `Boolean` |

Обёртки нужны, когда значение должно использоваться как объект. Например, Java generics не работают непосредственно с primitive types:

```java
// List<int> numbers;      // нельзя
List<Integer> numbers;     // можно
```

Wrapper classes также предоставляют полезные методы:

```java
int value = Integer.parseInt("42");
int max = Integer.max(10, 20);
boolean digit = Character.isDigit('7');
```

> В найденных разделах исходного конспекта отдельного материала про wrapper classes и autoboxing практически нет. Этот подраздел добавлен как необходимая часть Java Core на основе правил Java Language Specification и API wrapper-классов.

#### Autoboxing

**Autoboxing** — автоматическое преобразование primitive value в соответствующий wrapper type.

```java
Integer number = 10;
```

Концептуально это соответствует вызову:

```java
Integer number = Integer.valueOf(10);
```

Другой частый пример:

```java
List<Integer> numbers = new ArrayList<>();

numbers.add(10); // int → Integer
```

Метод `add()` ожидает `Integer`, поэтому компилятор применяет boxing conversion.

#### Unboxing

**Unboxing** — обратное преобразование wrapper object в primitive value:

```java
Integer boxed = 10;
int primitive = boxed;
```

Концептуально:

```java
int primitive = boxed.intValue();
```

Autoboxing/unboxing — удобный синтаксический механизм языка. Но важно помнить, что `int` и `Integer` **не становятся одним и тем же типом**.

#### Главная ловушка unboxing: null

Primitive не может быть `null`, а wrapper — может:

```java
Integer count = null;
```

Поэтому:

```java
Integer count = null;
int value = count;
```

во время выполнения приведёт к:

```text
NullPointerException
```

Причина — скрытый unboxing:

```java
int value = count.intValue();
```

Такая ошибка особенно неприятна, когда преобразование спрятано внутри выражения:

```java
Integer count = null;

if (count > 0) {
    // ...
}
```

Для сравнения с `0` Java должна получить primitive `int`, поэтому происходит unboxing `null`.

Практический вывод: если значение по смыслу **не может отсутствовать**, primitive часто безопаснее wrapper. Wrapper нужен, когда `null` действительно несёт отдельный смысл либо API требует объект.

#### `==` и `equals()` у wrapper-объектов

Для primitives оператор `==` сравнивает значения:

```java
int a = 1000;
int b = 1000;

System.out.println(a == b); // true
```

Для двух references `==` проверяет, ссылаются ли они на **один и тот же объект**:

```java
Integer a = 1000;
Integer b = 1000;

System.out.println(a == b);      // обычно false
System.out.println(a.equals(b)); // true
```

Поэтому wrapper values по содержимому обычно сравнивают через `equals()`:

```java
Objects.equals(a, b);
```

`Objects.equals()` особенно удобен, если один из operands может быть `null`.

#### Integer Cache

Почему следующий код может удивить?

```java
Integer a = 100;
Integer b = 100;

System.out.println(a == b); // true
```

При boxing Java использует `Integer.valueOf(...)`. Для небольших целых значений используются заранее созданные объекты.

Java Language Specification гарантирует для определённых constant expressions как минимум диапазон:

```text
-128 ... 127
```

Поэтому:

```java
Integer a = 127;
Integer b = 127;

System.out.println(a == b); // true
```

Но:

```java
Integer a = 128;
Integer b = 128;

System.out.println(a == b); // обычно false
```

**Нельзя строить бизнес-логику на таком поведении `==`.** Если нужны равные числовые значения:

```java
a.equals(b)
```

или null-safe вариант:

```java
Objects.equals(a, b)
```

Практическая формула:

```text
primitive == primitive → сравнение значений
reference == reference → сравнение идентичности ссылок
wrapper.equals(...)    → сравнение значения с учётом типа
```

#### Почему `new Integer(...)` использовать не нужно

Исторически можно было написать:

```java
Integer value = new Integer(10);
```

Но constructors wrapper-классов вроде `Integer(int)` давно deprecated for removal. Для boxing используется `Integer.valueOf()`, а чаще всего достаточно autoboxing:

```java
Integer value = 10;
```

Это также позволяет использовать cache там, где он предусмотрен.

#### Смешанное сравнение wrapper и primitive

Рассмотрим:

```java
Integer a = 1000;
int b = 1000;

System.out.println(a == b); // true
```

Здесь сравниваются не две references. `a` проходит **unboxing**, после чего фактически сравниваются два `int`.

Но если `a == null`:

```java
Integer a = null;
int b = 1000;

System.out.println(a == b); // NullPointerException
```

Это ещё одна причина всегда смотреть на **типы operands**, а не запоминать правило «`==` с Integer работает так-то».

#### Arithmetic и скрытый boxing

Wrapper участвует в арифметике через unboxing:

```java
Integer count = 10;
count++;
```

Упрощённо происходит:

```text
Integer
   │ unboxing
   ▼
  int
   │ + 1
   ▼
  int
   │ boxing
   ▼
Integer
```

То есть wrapper не становится mutable. `Integer` — immutable class: результат операции представляет другое значение/ссылку.

Это важно и для производительности: большое количество boxing/unboxing может создавать лишнюю работу и, когда значение не берётся из cache, потенциальные allocations.

Например, в производительном числовом коде:

```java
long sum = 0;
for (int i = 0; i < 1_000_000; i++) {
    sum += i;
}
```

primitive types обычно предпочтительнее wrappers, если объектная семантика не нужна.

#### Wrapper в generics и collections

Generics принимают reference types:

```java
List<Integer> ids = List.of(1, 2, 3);
Map<Long, Boolean> flags = new HashMap<>();
```

Поэтому при работе с коллекциями primitives автоматически boxing-ятся.

Из этого следует типичная ловушка с перегрузками `List.remove()`:

```java
List<Integer> numbers = new ArrayList<>(List.of(10, 20, 30));

numbers.remove(1);
```

Здесь вызывается:

```java
remove(int index)
```

и удаляется элемент с индексом `1`, то есть `20`.

Если нужно удалить значение:

```java
numbers.remove(Integer.valueOf(10));
```

тогда вызывается:

```java
remove(Object o)
```

Это уже пересечение wrapper types с Collections; подробно поведение списков разберём в отдельной главе.

#### Wrapper и методы

Wrapper classes полезны не только из-за generics. Они содержат константы и операции преобразования:

```java
int value = Integer.parseInt("123");
Integer boxed = Integer.valueOf("123");

String binary = Integer.toBinaryString(10);

System.out.println(Integer.MAX_VALUE);
System.out.println(Integer.MIN_VALUE);
```

Важно различать:

```java
Integer.parseInt("42")  // возвращает primitive int
Integer.valueOf("42")   // возвращает Integer
```

#### Что важно запомнить

- Wrapper classes — объектные аналоги восьми primitive types.
- **Autoboxing:** primitive → wrapper; **unboxing:** wrapper → primitive.
- Unboxing `null` приводит к **NullPointerException**.
- `==` между двумя wrapper references проверяет identity, а `equals()` — значение.
- При смешанном сравнении wrapper с primitive может произойти unboxing.
- Для `Integer` при boxing гарантирован cache как минимум для `-128..127`; нельзя использовать это как причину сравнивать wrappers через `==`.
- Generics работают с reference types, поэтому `List<int>` невозможен, а `List<Integer>` — возможен.
- `Integer` и другие числовые wrappers immutable.
- Лишний boxing/unboxing может быть нежелателен в performance-sensitive коде.

#### На собеседовании

**Что такое autoboxing и unboxing?**

> Autoboxing — автоматическое преобразование primitive в wrapper, например int в Integer. Unboxing — обратное преобразование Integer в int. Компилятор вставляет необходимые преобразования, например через Integer.valueOf() и intValue(). Важно помнить, что при unboxing null возникает NullPointerException.

**Почему Integer нельзя надёжно сравнивать через ==?**

> Потому что Integer — reference type, и == между двумя references сравнивает идентичность объектов. Для небольших значений результат может случайно выглядеть как сравнение значений из-за Integer Cache, например для диапазона -128..127. Для сравнения значения нужно использовать equals() или Objects.equals().

**Почему `Integer a = 127; Integer b = 127; a == b` возвращает true?**

> При autoboxing используется Integer.valueOf(), а небольшие Integer-классы кэшируются. Для constant values в диапазоне как минимум -128..127 спецификация гарантирует одинаковые boxed instances. Но полагаться на == для сравнения wrapper values нельзя.

**Что произойдёт при `Integer value = null; int x = value;`?**

> Произойдёт unboxing. JVM попытается получить primitive value из null-reference, поэтому будет NullPointerException.

#### Источники и уточнения

- В найденных разделах пользовательского конспекта отдельный материал по wrapper classes/autoboxing отсутствует; подраздел добавлен как необходимая база Java Core.
- [Java Language Specification — Boxing and Unboxing Conversions](https://docs.oracle.com/javase/specs/jls/se26/html/jls-5.html#jls-5.1.7) — правила boxing, cache guarantees и unboxing.
- [Integer API](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/lang/Integer.html) — `valueOf`, `parseInt`, константы и API `Integer`.

### 1.7. Передача параметров и операторы Java

Один из самых частых вопросов по Java Core:

> Java передаёт параметры **по значению (pass-by-value)** или **по ссылке (pass-by-reference)**?

Правильный ответ: **Java всегда использует pass-by-value**.

Путаница возникает потому, что для reference types значением переменной является **ссылка на объект**. При вызове метода копируется эта ссылка.

> В найденных разделах исходного конспекта отдельного материала по pass-by-value и базовым операторам нет. Этот подраздел добавлен как необходимая база Java Core по правилам Java Language Specification.

#### Передача primitive

Простой пример:

```java
static void change(int value) {
    value = 100;
}

public static void main(String[] args) {
    int number = 10;

    change(number);

    System.out.println(number); // 10
}
```

Метод получает **копию значения** `10`:

```text
main()                  change()

number = 10   ─────►    value = 10
   │                       │
   │                       ▼
   │                   value = 100
   │
   ▼
number = 10
```

Изменение параметра `value` никак не меняет переменную `number` вызывающего метода.

#### Что происходит с объектом?

Рассмотрим reference type:

```java
class User {
    String name;

    User(String name) {
        this.name = name;
    }
}

static void rename(User user) {
    user.name = "Bob";
}

public static void main(String[] args) {
    User user = new User("Alice");

    rename(user);

    System.out.println(user.name); // Bob
}
```

На первый взгляд кажется, что объект передали «по ссылке». Но на самом деле метод получил **копию ссылочного значения**.

Упрощённо:

```text
main()                         rename()

user ──────┐              copyOfReference
           │                     │
           └────────┬────────────┘
                    ▼
              ┌───────────┐
              │ User      │
              │ name=Alice│
              └───────────┘
                    │
                    ▼
              name = Bob
```

Обе ссылки указывают на **один объект**, поэтому через локальную копию ссылки метод может изменить состояние этого объекта.

Но саму переменную вызывающего метода он заменить не может.

#### Переприсваивание параметра не меняет исходную ссылку

```java
static void replace(User user) {
    user = new User("Bob");
}

public static void main(String[] args) {
    User user = new User("Alice");

    replace(user);

    System.out.println(user.name); // Alice
}
```

После входа в `replace()` существуют две независимые переменные, содержащие одинаковое ссылочное значение.

После переприсваивания:

```text
main()                         replace()

user ───────────────► [User: Alice]

                         user ─► [User: Bob]
```

Изменился только локальный параметр `user` внутри `replace()`.

Отсюда удобная формула:

> Java передаёт **копию значения переменной**. Для primitive это копия primitive value, для reference type — копия reference value.

#### Почему Java — не pass-by-reference?

При настоящем pass-by-reference вызываемый метод мог бы заменить саму переменную вызывающего кода.

Например, такой `swap()` в Java не работает:

```java
static void swap(User first, User second) {
    User temp = first;
    first = second;
    second = temp;
}
```

```java
User a = new User("Alice");
User b = new User("Bob");

swap(a, b);

System.out.println(a.name); // Alice
System.out.println(b.name); // Bob
```

Метод переставил только **свои копии ссылок**.

Это хороший способ доказать на собеседовании, что Java не использует pass-by-reference.

#### `==`: что именно сравнивается?

Оператор `==` зависит от типов operands.

Для primitives сравниваются значения:

```java
int a = 10;
int b = 10;

System.out.println(a == b); // true
```

Для references сравнивается identity ссылок — указывают ли они на один объект:

```java
User a = new User("Alice");
User b = new User("Alice");
User c = a;

System.out.println(a == b); // false
System.out.println(a == c); // true
```

Содержимое объектов обычно сравнивают через `equals()`, если класс реализует нужную value semantics.

```text
== для primitives  → значение
== для references  → один ли объект
equals()            → логическое равенство по контракту класса
```

Подробно контракт `equals()/hashCode()` разберём в отдельной главе.

#### Short-circuit operators: `&&` и `||`

Операторы **conditional AND** `&&` и **conditional OR** `||` вычисляют правую часть только тогда, когда она действительно нужна.

```java
if (user != null && user.isActive()) {
    // ...
}
```

Если `user == null`, первая часть уже равна `false`. Всё выражение `&&` не может стать `true`, поэтому:

```java
user.isActive()
```

не вызывается.

Именно поэтому такая null-check конструкция безопасна.

Для `||` логика обратная:

```java
if (cached != null || loadFromDatabase()) {
    // ...
}
```

Если `cached != null` уже даёт `true`, правую часть вычислять не требуется.

#### `&` и `|` — это не то же самое

Для boolean operands можно использовать и `&`, `|`, но они **вычисляют обе стороны**:

```java
boolean result = false & expensiveCheck();
```

`expensiveCheck()` будет вызван.

А здесь:

```java
boolean result = false && expensiveCheck();
```

не будет.

Кроме того, `&`, `|` и `^` используются как **bitwise operators** для integer types:

```java
int flags = 0b0101;
int mask  = 0b0001;

System.out.println(flags & mask); // 1
```

Для обычных логических условий чаще нужны `&&` и `||`.

#### Побочные эффекты и short-circuit

Short-circuit влияет не только на производительность, но и на поведение программы:

```java
int x = 0;

boolean result = true || ++x > 0;

System.out.println(x); // 0
```

Правая часть не вычислилась, поэтому `x` не изменился.

Код, который критически зависит от побочного эффекта внутри сложного boolean expression, обычно труднее читать. Лучше не прятать важные изменения состояния в условиях без необходимости.

#### Порядок вычисления operands

В Java operands выражений вычисляются **слева направо**.

```java
static int print(int value) {
    System.out.println(value);
    return value;
}

int result = print(1) + print(2);
```

Сначала будет вызван `print(1)`, затем `print(2)`.

Это отличается от **приоритета операторов**. Приоритет определяет структуру выражения:

```java
int result = 2 + 3 * 4; // 14
```

Сначала по структуре выполняется умножение:

```text
2 + (3 * 4)
```

Если выражение сложно читать, лучше использовать скобки, даже если приоритет операторов известен.

#### `++i` и `i++`

Оба оператора увеличивают переменную на единицу, но значение самого выражения различается.

**Prefix increment:**

```java
int i = 5;
int x = ++i;

System.out.println(i); // 6
System.out.println(x); // 6
```

Сначала increment, затем используется новое значение.

**Postfix increment:**

```java
int i = 5;
int x = i++;

System.out.println(i); // 6
System.out.println(x); // 5
```

В выражении используется старое значение, а переменная увеличивается.

Не стоит писать головоломки вроде:

```java
int x = i++ + ++i;
```

Язык определяет порядок вычисления, но такой код плохо читается и легко приводит к ошибкам.

#### Тернарный оператор

Conditional operator:

```java
condition ? valueIfTrue : valueIfFalse
```

Пример:

```java
String status = age >= 18 ? "adult" : "minor";
```

Выполняется только одна из двух ветвей — выбранная по условию.

Тернарный оператор удобен для короткого выбора **значения**, но глубокая вложенность быстро ухудшает читаемость:

```java
String result = a ? "A" : b ? "B" : c ? "C" : "D";
```

В таких случаях обычный `if/else` часто понятнее.

#### Оператор `instanceof`

`instanceof` проверяет, совместим ли объект с указанным reference type:

```java
if (value instanceof String) {
    String text = (String) value;
}
```

Современная Java поддерживает pattern matching:

```java
if (value instanceof String text) {
    System.out.println(text.length());
}
```

Здесь проверка типа и получение переменной `text` объединены.

Для `null`:

```java
Object value = null;

System.out.println(value instanceof String); // false
```

`instanceof` не выбрасывает `NullPointerException` для `null`.

#### Типичные ошибки

**«Объекты в Java передаются по ссылке».**  
Нет. Передаётся копия значения ссылки.

**«Если метод изменил объект, значит это pass-by-reference».**  
Нет. Две независимые reference-переменные могут указывать на один mutable object.

**«`==` сравнивает объекты по содержимому».**  
Для references `==` проверяет identity. Логическое равенство обычно реализуется через `equals()`.

**«`&` и `&&` отличаются только написанием».**  
Нет. Для boolean `&&` short-circuit, а `&` вычисляет обе стороны; кроме того, `&` работает как bitwise operator для integer types.

#### Что важно запомнить

- Java **всегда pass-by-value**.
- Для primitive копируется primitive value; для объекта копируется **reference value**.
- Через копию ссылки можно изменить mutable object, но нельзя переприсвоить переменную вызывающего метода.
- `==` сравнивает primitive values или identity references.
- `&&` и `||` используют short-circuit evaluation.
- `&` и `|` для boolean вычисляют обе стороны; для integer types выполняют bitwise operations.
- Java вычисляет operands слева направо.
- `++i` возвращает новое значение, `i++` — старое значение выражения.
- Pattern matching для `instanceof` позволяет одновременно проверить тип и получить типизированную переменную.

#### На собеседовании

**Java — pass-by-value или pass-by-reference?**

> Java всегда pass-by-value. При передаче primitive копируется само значение. При передаче объекта копируется значение ссылки на этот объект. Поэтому метод может через эту копию изменить состояние общего объекта, но переприсваивание параметра внутри метода не изменит ссылочную переменную вызывающего кода.

**Почему изменение поля объекта внутри метода видно снаружи?**

> Потому что исходная переменная и параметр метода содержат две копии одной и той же ссылки и указывают на один объект. Изменяется сам объект, а не ссылочная переменная вызывающего метода.

**Чем `&&` отличается от `&` для boolean?**

> `&&` использует short-circuit: если результат уже известен по левой части, правая не вычисляется. `&` вычисляет обе части всегда. Поэтому проверка `obj != null && obj.isValid()` безопасна, а с одиночным `&` вызов справа всё равно произошёл бы.

**Чем `==` отличается от `equals()`?**

> Для primitive `==` сравнивает значения, а для references — указывают ли ссылки на один объект. `equals()` — метод, через который класс может определить логическое равенство объектов по содержимому. Его контракт подробно рассматривается отдельно.

#### Источники и уточнения

- В найденных разделах пользовательского конспекта отдельного материала по pass-by-value и базовым операторам не обнаружено; подраздел добавлен как необходимая база Java Core.
- [Java Language Specification — Variables](https://docs.oracle.com/javase/specs/jls/se26/html/jls-4.html#jls-4.12) — значения переменных и параметры.
- [Java Language Specification — Method Invocation Expressions](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.12) — вычисление аргументов и передача значений при вызове.
- [Java Language Specification — Evaluation Order](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.7) — порядок вычисления.
- [Java Language Specification — Conditional-And / Conditional-Or](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.23) — short-circuit operators.

### 1.8. ООП в Java: инкапсуляция, наследование, полиморфизм и абстракция

**Объектно-ориентированное программирование (ООП)** — подход, при котором программа строится вокруг объектов, объединяющих **состояние** и **поведение**.

В Java класс описывает структуру и поведение, а объект — конкретный экземпляр класса:

```java
class BankAccount {
    private long balance;

    void deposit(long amount) {
        balance += amount;
    }

    long getBalance() {
        return balance;
    }
}

BankAccount account = new BankAccount();
```

Четыре классических понятия, которые обычно ожидают услышать на собеседовании:

```text
OOP
├── Encapsulation
├── Inheritance
├── Polymorphism
└── Abstraction
```

> В исходном конспекте ООП встречается через темы наследования JPA, SOLID и полиморфизма, но отдельного цельного раздела с четырьмя базовыми принципами в найденном материале нет. Поэтому базовое объяснение ниже дополнено как необходимая часть Java Core. Связь наследования с Liskov Substitution Principle поддерживается исходным материалом и будет подробно разобрана в главе SOLID.

#### Инкапсуляция

**Инкапсуляция (encapsulation)** — объединение состояния и поведения объекта и контроль доступа к внутренним деталям.

Плохой вариант:

```java
class BankAccount {
    public long balance;
}
```

Любой код может сделать:

```java
account.balance = -1_000_000;
```

Класс не контролирует собственное состояние.

Лучше скрыть детали и предоставить операции, сохраняющие инварианты:

```java
class BankAccount {
    private long balance;

    public void deposit(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("amount must be positive");
        }

        balance += amount;
    }

    public long getBalance() {
        return balance;
    }
}
```

Здесь внешний код знает **что можно сделать**, но не обязан знать **как внутри хранится и изменяется balance**.

Инкапсуляция — это не просто «все поля сделать `private` и создать getter/setter». Если написать:

```java
public void setBalance(long balance) {
    this.balance = balance;
}
```

то формально поле скрыто, но объект всё ещё может позволять установить некорректное состояние.

Главная идея:

> Объект сам контролирует допустимые изменения своего состояния.

#### Наследование

**Наследование (inheritance)** позволяет создать новый класс на основе существующего.

```java
class Animal {
    void makeSound() {
        System.out.println("...");
    }
}

class Dog extends Animal {
    @Override
    void makeSound() {
        System.out.println("Woof");
    }
}
```

`Dog` наследует доступное поведение `Animal` и может его переопределять.

Отношение наследования обычно читают как **is-a**:

```text
Dog is an Animal
```

Java поддерживает:

- наследование **одного класса** через `extends`;
- реализацию **нескольких интерфейсов** через `implements`.

```java
class Dog extends Animal implements Runnable, Comparable<Dog> {
    // ...
}
```

Множественного наследования классов в Java нет:

```java
// class C extends A, B { } // нельзя
```

Это избегает ряда неоднозначностей состояния и реализации, возникающих при наследовании сразу от нескольких классов.

#### Наследование — не просто способ переиспользовать код

Если классы имеют похожий код, это ещё не означает, что между ними должно быть наследование.

Наследник должен корректно использоваться там, где ожидается родитель:

```java
void process(Animal animal) {
    animal.makeSound();
}

process(new Dog());
```

Это связано с **Liskov Substitution Principle (LSP)**: подтип не должен неожиданно ломать ожидания, установленные контрактом базового типа.

Исходный конспект формулирует эту идею практически: если наследник в корне меняет ожидаемое поведение родителя, такую иерархию лучше не строить.

#### Полиморфизм

**Полиморфизм (polymorphism)** позволяет работать с объектами разных конкретных типов через общий базовый тип.

```java
interface PaymentProcessor {
    void pay(long amount);
}

class CardProcessor implements PaymentProcessor {
    @Override
    public void pay(long amount) {
        System.out.println("Pay by card: " + amount);
    }
}

class CryptoProcessor implements PaymentProcessor {
    @Override
    public void pay(long amount) {
        System.out.println("Pay by crypto: " + amount);
    }
}
```

Клиентский код зависит от абстракции:

```java
static void checkout(PaymentProcessor processor) {
    processor.pay(100);
}

checkout(new CardProcessor());
checkout(new CryptoProcessor());
```

`checkout()` не нужно знать конкретный класс.

Это один из главных практических эффектов ООП:

```text
           PaymentProcessor
             ▲          ▲
             │          │
      CardProcessor  CryptoProcessor
             ▲          ▲
             └──── checkout() ────┘
```

#### Dynamic dispatch

Рассмотрим:

```java
Animal animal = new Dog();
animal.makeSound();
```

Тип переменной — `Animal`, реальный объект — `Dog`.

Для переопределённого instance-метода JVM выбирает реализацию в соответствии с **runtime class объекта**:

```text
reference type: Animal
runtime object: Dog

animal.makeSound()
        │
        ▼
Dog.makeSound()
```

Это называют **dynamic method dispatch**.

Именно он лежит в основе runtime polymorphism для переопределённых instance methods.

#### Overriding и Overloading — не одно и то же

**Overriding (переопределение)** — наследник предоставляет новую реализацию instance-метода базового типа:

```java
class Animal {
    void makeSound() {}
}

class Dog extends Animal {
    @Override
    void makeSound() {}
}
```

Какой overriding-метод выполнить, определяется runtime type объекта.

**Overloading (перегрузка)** — методы имеют одно имя, но разные списки параметров:

```java
void print(int value) {}
void print(String value) {}
```

Выбор подходящей overload-сигнатуры выполняется **на этапе компиляции** исходя из compile-time типов и правил overload resolution.

Ловушка:

```java
static void print(Animal animal) {
    System.out.println("Animal");
}

static void print(Dog dog) {
    System.out.println("Dog");
}

Animal animal = new Dog();
print(animal);
```

Результат:

```text
Animal
```

Потому что overload выбирается по compile-time типу `animal`, то есть `Animal`.

#### static-методы не участвуют в dynamic dispatch как instance methods

```java
class Parent {
    static void hello() {
        System.out.println("Parent");
    }
}

class Child extends Parent {
    static void hello() {
        System.out.println("Child");
    }
}
```

Для static methods речь идёт не об overriding, а о **method hiding**.

Поэтому:

```java
Parent value = new Child();
value.hello();
```

выберет метод на основе compile-time типа `Parent`, а не runtime-типа объекта.

Практически static-методы лучше вызывать через имя класса:

```java
Parent.hello();
Child.hello();
```

#### Абстракция

**Абстракция (abstraction)** — выделение существенного контракта и сокрытие ненужных пользователю деталей реализации.

Например:

```java
interface NotificationSender {
    void send(String message);
}
```

Код, использующий `NotificationSender`, знает только контракт:

```java
class OrderService {
    private final NotificationSender sender;

    OrderService(NotificationSender sender) {
        this.sender = sender;
    }

    void createOrder() {
        // business logic
        sender.send("Order created");
    }
}
```

Конкретная реализация может быть любой:

```java
class EmailSender implements NotificationSender {
    @Override
    public void send(String message) {
        // SMTP implementation
    }
}
```

```java
class TelegramSender implements NotificationSender {
    @Override
    public void send(String message) {
        // Telegram API implementation
    }
}
```

`OrderService` не зависит от деталей SMTP или Telegram API.

Инкапсуляция и абстракция связаны, но это не одно и то же:

- **инкапсуляция** отвечает за границы объекта и контроль его внутреннего состояния;
- **абстракция** отвечает за то, какой существенный контракт мы показываем пользователю, скрывая лишние детали.

#### Composition over inheritance

**Композиция (composition)** означает, что объект получает нужное поведение через другие объекты, а не обязательно через наследование.

Через наследование:

```text
Car extends Engine
```

Это плохая модель: автомобиль **не является двигателем**.

Через композицию:

```java
class Car {
    private final Engine engine;

    Car(Engine engine) {
        this.engine = engine;
    }

    void start() {
        engine.start();
    }
}
```

Отношение:

```text
Car has an Engine
```

Композиция часто предпочтительнее, потому что:

- уменьшает жёсткую связанность с базовым классом;
- позволяет заменять реализацию зависимости;
- удобнее тестируется;
- не заставляет моделировать ложное отношение `is-a`;
- позволяет собирать поведение из нескольких компонентов.

Но правило **composition over inheritance** не означает «наследование всегда плохо». Наследование хорошо подходит, когда существует настоящее отношение подтипа и соблюдается контракт базового класса.

#### Пример: полиморфизм вместо большого if/switch

Без полиморфизма:

```java
void pay(String type, long amount) {
    if ("CARD".equals(type)) {
        // card logic
    } else if ("CRYPTO".equals(type)) {
        // crypto logic
    }
}
```

При добавлении каждого нового способа оплаты этот метод приходится менять.

С полиморфизмом:

```java
interface PaymentProcessor {
    void pay(long amount);
}
```

Каждая реализация содержит своё поведение, а вызывающий код работает с общим контрактом:

```java
void pay(PaymentProcessor processor, long amount) {
    processor.pay(amount);
}
```

Это не означает, что любой `switch` нужно заменять иерархией классов. Полиморфизм полезен, когда у нас действительно есть несколько взаимозаменяемых поведений и ожидается их развитие.

#### Типичные ошибки

**«Инкапсуляция — это private поля + getters/setters».**  
Это только инструмент. Цель — контролировать состояние и скрывать внутренние детали.

**«Наследование нужно для переиспользования кода».**  
Переиспользование — возможный эффект, но главным должно быть корректное отношение подтипа `is-a`.

**«Overloading — runtime polymorphism».**  
Overload resolution происходит на compile time. Dynamic dispatch относится к overriding instance methods.

**«static-метод переопределяется».**  
Нет. Static methods скрываются (method hiding), а не участвуют в обычном dynamic dispatch.

**«Composition over inheritance означает никогда не использовать extends».**  
Нет. Нужно выбирать композицию, когда требуется `has-a`/делегирование, и наследование — когда действительно моделируется корректный подтип.

#### Что важно запомнить

- **Encapsulation** — объект контролирует своё состояние и скрывает детали реализации.
- **Inheritance** — отношение подтипа `is-a`; в Java класс наследуется только от одного класса.
- **Polymorphism** — разные реализации можно использовать через общий тип.
- **Abstraction** — клиент работает с существенным контрактом, не зная лишних деталей реализации.
- Overriding instance methods поддерживает **dynamic dispatch** по runtime type объекта.
- Overloading разрешается **на compile time**.
- Static methods скрываются, а не переопределяются полиморфно.
- Композиция часто гибче наследования, но наследование уместно для настоящего отношения подтипа.

#### На собеседовании

**Назовите основные принципы ООП.**

> Обычно выделяют инкапсуляцию, наследование, полиморфизм и абстракцию. Инкапсуляция позволяет объекту контролировать своё состояние, наследование моделирует отношение подтипа, полиморфизм позволяет работать с разными реализациями через общий тип, а абстракция выделяет необходимый контракт и скрывает детали реализации.

**Что такое полиморфизм в Java?**

> Это возможность использовать объекты разных конкретных типов через общий базовый класс или интерфейс. При вызове переопределённого instance-метода конкретная реализация выбирается по runtime type объекта — это dynamic dispatch.

**Чем overriding отличается от overloading?**

> Overriding — наследник переопределяет instance-метод родителя, и конкретная реализация выбирается во время выполнения по runtime type. Overloading — несколько методов имеют одно имя, но разные параметры; нужная сигнатура выбирается компилятором на compile time.

**Почему часто рекомендуют composition over inheritance?**

> Композиция слабее связывает классы и позволяет менять или подменять поведение через зависимости. Наследование стоит использовать, когда объект действительно является подтипом базового класса и сохраняет его контракт, а не просто ради повторного использования нескольких методов.

#### Источники и уточнения

- Исходный конспект содержит наследование в контексте JPA/Hibernate и отдельно связывает корректную иерархию наследования с Liskov Substitution Principle.
- Исходный материал по SOLID формулирует LSP как требование не менять поведение наследника неожиданным для контракта родителя образом; подробный SOLID будет разобран в своей главе.
- [Java Language Specification — Classes](https://docs.oracle.com/javase/specs/jls/se26/html/jls-8.html) — классы, наследование, overriding и hiding.
- [Java Language Specification — Interfaces](https://docs.oracle.com/javase/specs/jls/se26/html/jls-9.html) — интерфейсы и их наследование.
- [Java Language Specification — Method Invocation](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.12) — overload resolution и выбор метода.

### 1.9. Interface и abstract class: что выбрать

И **interface**, и **abstract class** позволяют описать абстракцию, но решают немного разные задачи.

Короткий ориентир:

```text
interface
→ контракт / capability
→ разные классы могут реализовать один интерфейс
→ класс может реализовать несколько интерфейсов

abstract class
→ общая база близких классов
→ может хранить instance state
→ может иметь constructor
→ класс может наследоваться только от одного класса
```

> В найденных фрагментах исходного конспекта интерфейсы используются в контексте SOLID и Spring, но отдельного сравнения interface vs abstract class нет. Поэтому языковые правила этого подраздела добавлены по Java Language Specification. Из исходника сохраняется практическая идея Interface Segregation: небольшие специализированные интерфейсы обычно предпочтительнее одного огромного.

#### Interface

**Interface** задаёт контракт, который класс обязуется реализовать.

```java
interface PaymentProcessor {
    void pay(long amount);
}
```

Реализация:

```java
class CardPaymentProcessor implements PaymentProcessor {

    @Override
    public void pay(long amount) {
        System.out.println("Card payment: " + amount);
    }
}
```

Клиент может зависеть от интерфейса:

```java
class OrderService {
    private final PaymentProcessor processor;

    OrderService(PaymentProcessor processor) {
        this.processor = processor;
    }

    void checkout(long amount) {
        processor.pay(amount);
    }
}
```

В результате `OrderService` не привязан к конкретной реализации оплаты.

Именно такой подход постоянно встречается в Spring: зависимость объявляется через интерфейс, а конкретную реализацию предоставляет контейнер.

#### Abstract class

**Abstract class** — класс, экземпляр которого нельзя создать напрямую и который может содержать как абстрактное, так и готовое поведение.

```java
abstract class PaymentProcessor {

    protected final String providerName;

    protected PaymentProcessor(String providerName) {
        this.providerName = providerName;
    }

    public abstract void pay(long amount);

    public void printProvider() {
        System.out.println(providerName);
    }
}
```

Наследник обязан реализовать абстрактный метод, если сам не является abstract:

```java
class CardPaymentProcessor extends PaymentProcessor {

    CardPaymentProcessor() {
        super("Card provider");
    }

    @Override
    public void pay(long amount) {
        System.out.println("Card payment: " + amount);
    }
}
```

Abstract class может иметь:

- instance fields;
- constructors;
- abstract methods;
- обычные concrete methods;
- `static` methods;
- методы и поля с различными допустимыми access modifiers.

То есть abstract class подходит не только для контракта, но и для **общего состояния и общей реализации** иерархии.

#### `extends` и `implements`

Класс наследуется от класса через `extends`:

```java
class Dog extends Animal {
}
```

Класс реализует интерфейс через `implements`:

```java
class Dog implements Runnable {
    @Override
    public void run() {
    }
}
```

Можно совместить:

```java
class Dog extends Animal implements Runnable, Comparable<Dog> {

    @Override
    public void run() {
    }

    @Override
    public int compareTo(Dog other) {
        return 0;
    }
}
```

Java разрешает классу:

```text
extends     → максимум один непосредственный superclass
implements  → несколько interfaces
```

Сам интерфейс может наследовать несколько интерфейсов:

```java
interface Readable {
    void read();
}

interface Writable {
    void write();
}

interface Storage extends Readable, Writable {
}
```

#### Поля интерфейса

Переменные, объявленные в interface, не являются instance fields.

Например:

```java
interface Limits {
    int MAX_RETRIES = 3;
}
```

Поле интерфейса неявно:

```java
public static final int MAX_RETRIES = 3;
```

Поэтому интерфейс не хранит изменяемое состояние конкретного экземпляра так, как обычный или abstract class.

Если абстракции действительно нужно общее instance state:

```java
protected int retryCount;
```

это аргумент в пользу abstract class или композиции.

#### Методы интерфейса: не только abstract

Историческая формула «interface содержит только abstract methods» для современной Java неверна.

Interface может содержать несколько видов методов.

**Abstract method:**

```java
interface Sender {
    void send(String message);
}
```

Такой метод неявно `public abstract`.

**Default method** — появился в Java 8:

```java
interface Sender {

    void send(String message);

    default void sendDefaultMessage() {
        send("Hello");
    }
}
```

Он содержит реализацию и наследуется реализующими классами.

Одна из важных причин появления default methods — возможность **эволюционировать интерфейсы**, добавляя поведение без обязательного немедленного изменения каждой существующей реализации.

**Static method:**

```java
interface Sender {

    static boolean isValid(String message) {
        return message != null && !message.isBlank();
    }
}
```

Вызывается через имя интерфейса:

```java
Sender.isValid("Hello");
```

Static interface method не является instance-методом реализации.

**Private method** — поддерживается в interfaces начиная с Java 9:

```java
interface Sender {

    default void sendHello() {
        sendNormalized(" hello ");
    }

    default void sendBye() {
        sendNormalized(" bye ");
    }

    private void sendNormalized(String message) {
        send(message.trim());
    }

    void send(String message);
}
```

Private methods позволяют вынести повторяющуюся внутреннюю логику нескольких default/private методов и не выставлять её как часть публичного контракта.

#### Зачем default methods?

Представим библиотечный интерфейс:

```java
interface Logger {
    void log(String message);
}
```

У него сотни реализаций. Если просто добавить новый abstract method:

```java
void logError(String message);
```

старые реализации перестанут удовлетворять контракту.

Default method позволяет предоставить реализацию:

```java
interface Logger {

    void log(String message);

    default void logError(String message) {
        log("ERROR: " + message);
    }
}
```

Существующие реализации получают новое поведение автоматически, если им не требуется его переопределять.

#### Конфликт default methods

Несколько интерфейсов могут содержать одинаковый default method:

```java
interface A {
    default void hello() {
        System.out.println("A");
    }
}

interface B {
    default void hello() {
        System.out.println("B");
    }
}
```

Если класс реализует оба:

```java
class C implements A, B {
}
```

компилятор не может сам выбрать реализацию. Класс обязан разрешить конфликт:

```java
class C implements A, B {

    @Override
    public void hello() {
        A.super.hello();
    }
}
```

Можно вызвать одну из родительских реализаций либо написать полностью свою.

Это иногда называют **diamond problem**, но Java не допускает неоднозначность молча — конфликт должен быть разрешён явно.

#### Class wins over interface default

Если метод уже существует в superclass, а interface предлагает default method с той же подходящей сигнатурой, приоритет имеет метод класса.

Упрощённое правило:

```text
class implementation > interface default
```

Это важно для совместимости старых классов после появления default methods.

#### Abstract class тоже может реализовать interface

```java
interface Sender {
    void send(String message);
}

abstract class BaseSender implements Sender {

    protected void validate(String message) {
        if (message == null) {
            throw new IllegalArgumentException();
        }
    }
}
```

`BaseSender` может не реализовывать `send()`, потому что сам является abstract.

Конкретный наследник завершает контракт:

```java
class EmailSender extends BaseSender {

    @Override
    public void send(String message) {
        validate(message);
        System.out.println("Email: " + message);
    }
}
```

Это позволяет сочетать интерфейс как внешний контракт и abstract class как необязательную базовую реализацию.

#### Может ли abstract class не иметь abstract methods?

Да:

```java
abstract class BaseService {

    public void log() {
        System.out.println("log");
    }
}
```

Ключевое слово `abstract` запрещает создавать экземпляр напрямую:

```java
// new BaseService(); // compile error
```

Наличие хотя бы одного abstract method не является обязательным.

Обратное правило строгое: если класс содержит abstract method, сам класс должен быть `abstract`.

#### Abstract method и `final`

`abstract` означает:

> наследник должен предоставить реализацию.

`final` для метода означает:

> наследник не может переопределить метод.

Поэтому сочетание:

```java
// abstract final void execute();
```

логически противоречиво и запрещено.

А вот abstract class может иметь final concrete method:

```java
abstract class Processor {

    public final void execute() {
        validate();
        process();
    }

    protected abstract void process();

    private void validate() {
        // ...
    }
}
```

Это позволяет зафиксировать общий алгоритм, оставив наследнику отдельную точку расширения.

#### Interface vs abstract class

Для быстрого повторения:

| Interface | Abstract class |
| --- | --- |
| Хорош для контракта/capability | Хорош для общей базы иерархии |
| Класс может реализовать несколько | Наследоваться можно только от одного класса |
| Нет instance state | Может иметь instance state |
| Нет constructor | Может иметь constructor |
| Может иметь abstract/default/static/private methods | Может иметь abstract и concrete methods |
| Поля — `public static final` | Возможны обычные instance/static fields |
| Удобен для слабой связанности | Удобен для общего состояния и реализации |

#### Как выбирать на практике?

**Выбирай interface**, когда:

- нужен контракт для потенциально несвязанных классов;
- ожидается несколько взаимозаменяемых реализаций;
- важна возможность реализовать несколько контрактов;
- абстракция не требует общего mutable instance state;
- зависимость должна легко подменяться, например в DI или тестах.

Пример:

```java
interface PaymentGateway {
    PaymentResult pay(Order order);
}
```

Реализации Stripe, банковского API или тестовый fake не обязаны иметь общего superclass.

**Рассматривай abstract class**, когда:

- классы действительно принадлежат одной иерархии;
- им нужно общее состояние;
- нужен общий constructor;
- существенная часть реализации одинакова;
- нужно предоставить `protected` API наследникам.

На практике часто полезна комбинация:

```text
interface
   │
   ├── Implementation A
   │
   └── abstract BaseImplementation
              │
              ├── Implementation B
              └── Implementation C
```

Клиенты зависят от интерфейса, а некоторые реализации при необходимости переиспользуют общую базу.

#### Интерфейсы и Interface Segregation

В исходном конспекте принцип **Interface Segregation Principle (ISP)** сформулирован как идея:

> лучше несколько небольших интерфейсов, чем один огромный.

Например, вместо:

```java
interface Worker {
    void code();
    void drive();
    void cook();
}
```

лучше выделить отдельные способности:

```java
interface Developer {
    void code();
}

interface Driver {
    void drive();
}
```

Тогда класс реализует только тот контракт, который ему действительно нужен.

Подробно ISP и остальные принципы SOLID будут разобраны отдельно.

#### Типичные ошибки

**«В interface нельзя писать реализацию методов».**  
Устарело. В современной Java есть default, static и private interface methods.

**«Interface вообще не может содержать поля».**  
Может, но они неявно `public static final` — это константы интерфейса, а не instance state.

**«Abstract class обязан иметь abstract method».**  
Нет. Abstract class может вообще не иметь abstract methods.

**«Interface всегда лучше abstract class».**  
Нет. Они решают разные задачи. Если нужна общая база с состоянием и constructor, abstract class может быть естественнее.

**«Java поддерживает множественное наследование классов через interfaces».**  
Interface даёт множественное наследование **контрактов** и в современной Java некоторого поведения через default methods, но класс по-прежнему имеет только один непосредственный superclass и не наследует instance state из interfaces.

#### Что важно запомнить

- Класс может `extends` только один класс, но `implements` несколько interfaces.
- Interface — прежде всего **контракт**, abstract class — **общая база иерархии** с возможностью хранить state.
- Interface fields неявно `public static final`.
- Interface может иметь abstract, default, static и private methods.
- Default methods появились в Java 8; private interface methods — в Java 9.
- Конфликт одинаковых default methods нескольких interfaces класс должен разрешить явно.
- Abstract class может иметь constructor и может не содержать ни одного abstract method.
- `abstract` и `final` нельзя одновременно применять к одному методу.
- На практике часто удобно дать клиентам interface, а общую реализацию вынести в abstract base class только там, где она действительно нужна.

#### На собеседовании

**Чем interface отличается от abstract class?**

> Interface обычно описывает контракт и позволяет одному классу реализовать несколько независимых контрактов. Abstract class подходит для общей иерархии: может хранить instance state, иметь constructor, protected members и общую реализацию. Класс может наследоваться только от одного класса, но реализовать несколько interfaces.

**Какие методы могут быть в interface?**

> Abstract methods, default и static methods начиная с Java 8, а также private methods начиная с Java 9. Default method наследуется реализациями, static вызывается через интерфейс, private используется для внутреннего переиспользования логики внутри самого interface.

**Что произойдёт, если два интерфейса имеют одинаковый default method?**

> Если класс наследует конфликтующие default implementations и ни одна не имеет приоритета, класс должен явно переопределить метод и разрешить конфликт. При необходимости можно вызвать конкретную реализацию через `InterfaceName.super.method()`.

**Может ли abstract class не содержать abstract methods?**

> Да. `abstract` запрещает прямое создание экземпляра класса, но не требует наличия abstract methods. При этом класс с abstract method сам обязательно должен быть abstract.
