## 1. Java Core

### 1.1. Java Platform: JDK, JRE, JVM, Bytecode и JIT

**Java** — язык программирования со статической типизацией и платформа для выполнения программ. Одна из главных идей платформы — **Write Once, Run Anywhere (WORA)**: один и тот же скомпилированный код обычно можно запустить на разных операционных системах, если там есть совместимая среда Java.

#### JDK, JRE и JVM — в чём разница?

| Понятие | Что это | Для чего нужно |
| --- | --- | --- |
| **JVM** (Java Virtual Machine) | Виртуальная машина, выполняющая Java-байткод | Запуск кода, управление памятью, выполнение и оптимизация |
| **JRE** (Java Runtime Environment) | Среда выполнения: JVM и необходимые библиотеки | Запуск Java-приложений |
| **JDK** (Java Development Kit) | Набор для разработки: среда выполнения и инструменты | Написание, компиляция, отладка и запуск приложений |

В JDK есть, например, `javac` (компилятор), `java` (запуск), `jar` (работа с архивами), `javadoc` (документация), `javap` (просмотр содержимого class-файлов).

**Нюанс версий:** схема «JDK содержит JRE, а JRE содержит JVM» удобна для понимания, но исторически описывает в том числе отдельные поставки JRE. В современных JDK всё необходимое для выполнения уже включено в JDK; отдельную JRE устанавливать необязательно. Для небольших runtime-образов можно использовать `jlink`.

#### Как Java-программа превращается в выполняемый код?

Рассмотрим минимальный пример:

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Hello, Java!");
    }
}
```

Сохраняем его как `Main.java`, компилируем и запускаем:

```bash
javac Main.java
java Main
```

Результат:

```text
Hello, Java!
```

Что произошло:

1. **`javac`** преобразовал исходный код из `Main.java` в **байткод** — файл `Main.class`.
2. Команда **`java Main`** запустила среду выполнения и JVM.
3. **ClassLoader** загрузил необходимые классы; JVM проверяет и связывает их в процессе подготовки к выполнению.
4. **Execution Engine** начал выполнять байткод. В HotSpot для этого используются интерпретатор и JIT-компиляторы.
5. Программа вывела строку в консоль.

Упрощённая схема:

```text
Main.java
    │  javac — компиляция
    ▼
Main.class (bytecode)
    │
    ▼
JVM → загрузка и подготовка классов
    │
    ▼
Execution Engine
    ├── Interpreter — выполняет байткод
    └── JIT — компилирует выбранные участки в машинный код
                         │
                         ▼
                        CPU
```

**Байткод** — промежуточные инструкции для JVM, а не машинные инструкции конкретного процессора. Именно поэтому один и тот же `.class` может работать на разных системах. **Сама JVM платформозависима:** под конкретную ОС и архитектуру нужна соответствующая реализация.

Это не абсолютная переносимость: приложению могут требоваться нативные библиотеки, особенности ОС или подходящая версия Java.

#### Interpreter и JIT

**Интерпретатор** выполняет инструкции байткода во время работы программы. Это позволяет начать выполнение без предварительной компиляции всего приложения в машинный код.

**JIT (Just-In-Time compiler)** во время выполнения преобразует выбранные участки байткода в машинный код и оптимизирует их. Например, HotSpot анализирует, какие методы и циклы выполняются часто, и может применить к ним оптимизации.

Зачем это нужно? Интерпретация удобна для старта, а многократное выполнение уже скомпилированного машинного кода часто быстрее.

**Важный нюанс:** JIT — не то же самое, что интерпретатор. JIT именно **компилирует** код. Не весь байткод обязан пройти JIT-компиляцию; детали зависят от реализации и настроек JVM.

При измерении производительности это создаёт эффект **прогрева (warm-up)**: первые запуски участка кода могут отличаться по скорости от последующих, когда JVM накопила профиль выполнения и применила оптимизации.

#### Что важно запомнить

- **JDK** — инструменты разработки плюс среда выполнения; **JRE** — среда выполнения; **JVM** — виртуальная машина, выполняющая байткод.
- `javac` обычно компилирует `.java` в `.class`, а не сразу в машинный код конкретной ОС.
- **WORA** обеспечивается байткодом и наличием совместимой JVM на целевой платформе.
- **Интерпретатор** выполняет байткод; **JIT** компилирует выбранные участки в машинный код во время работы.
- Поведение, гарантированное спецификацией JVM, нужно отличать от особенностей **HotSpot**.

#### На собеседовании

**Чем отличаются JDK, JRE и JVM?**

> JVM выполняет байткод. JRE — среда, которая содержит JVM и библиотеки для запуска. JDK — набор для разработки: он включает среду выполнения, компилятор `javac` и другие инструменты. В современных поставках JDK отдельная установка JRE обычно не требуется.

**Почему Java называют платформонезависимой?**

> Компилятор создаёт байткод, который понимает JVM. Поэтому один и тот же `.class` обычно запускается на разных ОС без перекомпиляции, если есть совместимая JVM и нет платформозависимых зависимостей.

**Зачем нужен JIT?**

> JIT во время работы компилирует подходящие участки байткода в машинный код и оптимизирует их. Это позволяет ускорить часто выполняемые части программы, хотя сначала JVM может потребоваться время на прогрев.

### 1.2. Архитектура JVM: ClassLoader и загрузка классов

На верхнем уровне работу JVM удобно представить как несколько связанных частей:

```text
.class-файлы
     │
     ▼
ClassLoader Subsystem
     │
     ▼
Runtime Data Areas
     │
     ▼
Execution Engine
  ├── Interpreter
  ├── JIT
  └── Garbage Collector
     │
     ▼
Native / OS
```

В этом подразделе разберём **ClassLoader Subsystem** — как JVM находит и загружает классы. Память JVM и Garbage Collector рассмотрим отдельно.

#### Зачем нужен ClassLoader?

**ClassLoader** — механизм JVM, который находит байткод класса и создаёт его представление внутри JVM (`Class<?>`).

Классы не обязаны загружаться все сразу при старте приложения. JVM может загружать их **по мере необходимости**.

Например, когда приложение впервые обращается к `com.example.UserService`, JVM должна понять:

1. не загружен ли этот класс ранее;
2. кто должен его загрузить;
3. где найти его байткод;
4. корректен ли найденный class-файл;
5. как связать класс с другими типами.

#### Основные ClassLoader'ы

В современной Java обычно выделяют три основных уровня:

```text
Bootstrap ClassLoader
        ▲
        │
Platform ClassLoader
        ▲
        │
Application ClassLoader
```

**Bootstrap ClassLoader** — самый верхний уровень. Загружает базовые классы и критически важные модули Java, включая `java.base`.

Например:

```java
System.out.println(String.class.getClassLoader());
```

Обычно увидим:

```text
null
```

Это **не означает, что у `String` нет загрузчика**. В Java API Bootstrap ClassLoader исторически представлен как `null`.

**Platform ClassLoader** загружает классы платформы, которые не относятся к базовой части, загружаемой Bootstrap.

**Application (System) ClassLoader** обычно загружает код нашего приложения и его зависимости из classpath.

```java
public class Main {
    public static void main(String[] args) {
        System.out.println(Main.class.getClassLoader());
    }
}
```

Для обычного приложения здесь, как правило, будет Application ClassLoader.

> **Нюанс версий:** до Java 9 существовал **Extension ClassLoader**, связанный с механизмом extensions (`jre/lib/ext`). Начиная с Java 9 его роль в современной модели занимает **Platform ClassLoader**. Поэтому ответ «Bootstrap → Extension → Application» относится к старым версиям Java.

#### Parent Delegation Model

По умолчанию загрузчики используют модель **parent-first delegation**.

Если Application ClassLoader получил запрос на загрузку класса, он не обязательно сразу ищет его среди классов приложения. Сначала запрос делегируется вверх по цепочке.

Упрощённо:

```text
Application
    │
    │ delegate
    ▼
Platform
    │
    │ delegate
    ▼
Bootstrap
    │
    ├── найден → вернуть класс
    │
    └── не найден
           ▲
           │ Platform пробует найти сам
           ▲
           │ Application пробует найти сам
```

Для типичного `ClassLoader.loadClass(name)` логика выглядит примерно так:

1. Проверить, не был ли класс уже загружен.
2. Передать запрос родительскому загрузчику.
3. Если родитель класс не нашёл — попытаться найти его самостоятельно.
4. Если класс нигде не найден — загрузка завершается ошибкой.

Зачем сначала спрашивать родителя? Одна из причин — **предсказуемость и защита базовых классов платформы**. Код приложения не должен случайно подменить, например, стандартный `java.lang.String` своей копией.

**Parent-first — стандартная модель, но не абсолютное правило для всех систем.** Пользовательские загрузчики и некоторые контейнеры/плагинные системы могут применять другую стратегию, например child-first.

#### Loading, Linking и Initialization

Жизненный цикл класса не заканчивается чтением `.class`-файла.

Упрощённо:

```text
Loading
   │
   ▼
Linking
 ├── Verification
 ├── Preparation
 └── Resolution
   │
   ▼
Initialization
```

**Loading** — JVM находит бинарное представление класса и создаёт его представление в памяти.

**Linking** — подготовка загруженного класса к использованию:

- **Verification** — проверка корректности class-файла и байткода.
- **Preparation** — создаются необходимые структуры для static-полей и устанавливаются их начальные значения по правилам JVM.
- **Resolution** — символические ссылки на другие классы, методы и поля преобразуются в конкретные ссылки JVM. Resolution может выполняться лениво.

**Initialization** — выполняется логика инициализации класса: в частности, присваивания static-полям и static-блоки, собранные компилятором в метод инициализации класса `<clinit>`.

Пример:

```java
class Config {
    static int port = initPort();

    static {
        System.out.println("Config initialized");
    }

    private static int initPort() {
        return 8080;
    }
}
```

Загрузка класса и его **инициализация — не одно и то же**. JVM может загрузить и связать класс раньше, чем возникнет необходимость его инициализировать.

#### Идентичность класса: имя + ClassLoader

Для JVM тип определяется не только полным именем класса.

Упрощённо:

```text
Class identity = binary name + defining ClassLoader
```

Допустим, два независимых ClassLoader загрузили один и тот же:

```text
com.example.Plugin
```

Для JVM это могут быть **два разных типа**, даже если байткод взят из одного и того же JAR.

Именно это позволяет плагинным системам изолировать разные версии библиотек. Но отсюда возникает и важная ловушка: объект класса, загруженного одним ClassLoader, нельзя автоматически считать экземпляром «такого же» класса, загруженного другим ClassLoader. Это может привести к `ClassCastException`.

#### Custom ClassLoader

Можно создать собственный загрузчик:

```java
class PluginClassLoader extends ClassLoader {

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = loadClassBytes(name); // условный метод
        return defineClass(name, bytes, 0, bytes.length);
    }

    private byte[] loadClassBytes(String name) {
        // Читаем bytecode из нужного источника
        throw new UnsupportedOperationException();
    }
}
```

Обычно переопределяют **`findClass()`**, а стандартный `loadClass()` оставляют без изменений, чтобы сохранить parent-first delegation.

Собственные загрузчики нужны, например, для:

- плагинных архитектур;
- изоляции разных версий библиотек;
- hot reload / hot deploy;
- загрузки байткода из нестандартного источника.

Для обычного backend-приложения писать свой ClassLoader почти никогда не требуется, но понимание механизма полезно при разборе контейнеров, application servers, драйверов, SPI и проблем с зависимостями.

#### Типичные ошибки

**`ClassNotFoundException`** — приложение явно пытается загрузить класс, но загрузчик не может его найти.

**`NoClassDefFoundError`** — JVM во время выполнения не может получить определение класса, которое требуется программе; причины шире, чем просто «нет JAR в runtime», например предыдущая неудачная инициализация класса.

**`LinkageError`** — семейство ошибок, возникающих при проблемах связывания/определения классов.

**`ClassCastException` при разных ClassLoader'ах** — два класса могут иметь одинаковое имя, но быть разными типами для JVM.

#### Что важно запомнить

- ClassLoader загружает классы **по мере необходимости**, а не обязательно все при старте.
- Основная цепочка современной Java: **Bootstrap → Platform → Application**.
- До Java 9 вместо Platform в старой модели использовался **Extension ClassLoader**.
- Стандартная модель делегирования — **parent-first**: сначала пытается родитель, затем текущий загрузчик.
- Загрузка класса проходит через **Loading → Linking → Initialization**; Linking включает Verification, Preparation и Resolution.
- Для JVM идентичность типа определяется **именем класса + defining ClassLoader**.
- Пользовательские ClassLoader'ы позволяют изолировать плагины и версии библиотек.

#### На собеседовании

**Какие основные ClassLoader'ы есть в Java?**

> В современной Java это Bootstrap, Platform и Application ClassLoader. Bootstrap загружает базовую часть платформы, Platform — остальные платформенные классы, а Application — обычно код приложения и зависимости. До Java 9 вместо Platform использовался Extension ClassLoader.

**Как работает parent delegation?**

> Когда загрузчик получает запрос на класс, он сначала проверяет уже загруженные классы и делегирует поиск родителю. Если родитель не нашёл класс, текущий загрузчик пытается загрузить его сам. Это помогает избежать дублирования и случайной подмены базовых классов.

**Могут ли два класса с одинаковым полным именем быть разными типами?**

> Да. Для JVM идентичность типа определяется не только именем, но и defining ClassLoader. Поэтому одинаковый класс, загруженный двумя независимыми ClassLoader'ами, может считаться двумя разными типами.

**Чем Loading отличается от Initialization?**

> Loading создаёт представление класса в JVM на основе его бинарного представления. После этого идёт Linking. Initialization — отдельный более поздний этап, на котором выполняется инициализация static-полей и static-блоков класса.

### 1.3. Память JVM: Heap, Stack, Metaspace и Code Cache

Во время работы Java-программы JVM использует несколько областей памяти с разным назначением. Для собеседования важно не просто перечислить их, а понимать **что где хранится, кому область принадлежит и какие ошибки возникают при её исчерпании**.

Упрощённая картина:

```text
JVM process
│
├── Heap                         ← общий для потоков
│     └── объекты и массивы
│
├── JVM Stack (у каждого потока свой)
│     └── Stack Frames
│           ├── локальные переменные
│           ├── ссылки
│           └── operand stack
│
├── Metaspace                    ← метаданные загруженных классов (HotSpot)
│
└── Code Cache                   ← машинный код, созданный JIT (HotSpot)
```

> Важно различать **области, определённые JVM Specification**, и конкретную организацию памяти в **HotSpot**. Например, JVM Specification определяет Heap, JVM Stacks и Method Area, а Metaspace и Code Cache — детали реализации HotSpot.

#### Heap

**Heap (куча)** — общая для всех потоков область JVM, из которой обычно выделяется память под объекты и массивы.

```java
User user = new User("Alex");
int[] numbers = new int[10];
```

Упрощённо:

```text
Stack                         Heap
┌──────────────┐             ┌────────────────────┐
│ user ────────┼────────────►│ User object        │
│              │             │ name → "Alex"      │
│ numbers ─────┼────────────►│ int[10]            │
└──────────────┘             └────────────────────┘
```

Переменная `user` в данном примере — **ссылка**, а сам объект `User` находится в heap. Если объект содержит примитивное поле, это поле является частью самого объекта.

Heap обслуживается Garbage Collector. Подробно поколения, reachability, GC Roots и конкретные сборщики разберём в следующем подразделе.

При нехватке heap можно получить:

```text
java.lang.OutOfMemoryError: Java heap space
```

Размер heap в HotSpot обычно настраивают параметрами:

```bash
-Xms512m
-Xmx2g
```

где `-Xms` задаёт начальный размер heap, а `-Xmx` — максимальный.

#### JVM Stack

У **каждого Java-потока свой JVM Stack**. Он создаётся вместе с потоком и используется во время выполнения методов.

При каждом вызове метода создаётся **Stack Frame (кадр стека)**. После завершения метода соответствующий frame удаляется.

Пример:

```java
static int square(int value) {
    int result = value * value;
    return result;
}

public static void main(String[] args) {
    int number = 5;
    int answer = square(number);
}
```

Упрощённо во время выполнения `square()`:

```text
Thread Stack

┌────────────────────────────┐
│ square() frame             │  ← текущий вызов
│ value = 5                  │
│ result = 25                │
├────────────────────────────┤
│ main() frame               │
│ number = 5                 │
│ answer = ...               │
└────────────────────────────┘
```

Когда `square()` завершится, его frame исчезнет, а выполнение продолжится в `main()`.

#### Что находится внутри Stack Frame?

Согласно модели JVM, frame содержит в том числе:

- **local variables** — локальные переменные и параметры;
- **operand stack** — стек операндов, который bytecode использует для вычислений;
- данные, необходимые для возврата из метода и поддержки вызовов.

Например, выражение:

```java
int result = a + b;
```

на уровне bytecode концептуально использует operand stack: значения загружаются на стек операндов, выполняется операция сложения, результат сохраняется.

Для обычной подготовки к интервью достаточно помнить:

```text
JVM Stack
    └── Frame одного вызова метода
          ├── Local Variables
          ├── Operand Stack
          └── служебные данные вызова
```

#### StackOverflowError

Если вызовов становится слишком много и стек потока исчерпывается, возникает `StackOverflowError`.

Классический пример — бесконечная рекурсия:

```java
static void recursive() {
    recursive();
}
```

Каждый новый вызов создаёт новый frame:

```text
recursive()
recursive()
recursive()
recursive()
...
↓
StackOverflowError
```

Размер стека потока в HotSpot можно настраивать параметром `-Xss`.

Например:

```bash
-Xss1m
```

Большой `-Xss` позволяет отдельному потоку иметь более глубокий стек, но одновременно увеличивает потенциальное потребление памяти при большом количестве потоков.

#### Важный нюанс: «объекты всегда в Heap, переменные всегда в Stack»

Такую формулу часто используют для обучения, но она **слишком грубая**.

Для собеседования безопаснее говорить:

> Объекты и массивы обычно размещаются в heap. JVM Stack хранит frames вызовов, внутри которых находятся локальные переменные и промежуточные значения. Локальная переменная ссылочного типа содержит ссылку на объект, а не сам объект.

Почему «всегда» опасно? JVM имеет право применять оптимизации. Например, JIT может выполнить escape analysis и устранить отдельную аллокацию вообще. Поэтому не стоит воспринимать учебную схему как описание физического расположения каждого значения после оптимизаций.

#### Metaspace

**Metaspace** — область нативной памяти, которую HotSpot использует для хранения метаданных загруженных классов.

Упрощённо там находятся данные, описывающие классы:

- информация о структуре класса;
- методы и поля;
- runtime constant pool и связанные метаданные;
- данные, необходимые JVM для работы с загруженными типами.

Главная мысль:

```text
Heap       → экземпляры объектов
Metaspace  → метаданные загруженных классов
```

До Java 8 HotSpot использовал **Permanent Generation (PermGen)**. Начиная с Java 8 PermGen был удалён, а метаданные классов хранятся с использованием Metaspace.

Metaspace использует native memory и по умолчанию может расти в зависимости от доступной памяти. Его верхнюю границу можно ограничить:

```bash
-XX:MaxMetaspaceSize=256m
```

При исчерпании возможна ошибка:

```text
java.lang.OutOfMemoryError: Metaspace
```

Одна из причин проблем с Metaspace — постоянное создание новых ClassLoader'ов и загрузка новых классов, когда старые ClassLoader'ы остаются достижимыми и не могут быть освобождены.

#### Code Cache

**Code Cache** — область памяти HotSpot, в которой хранится скомпилированный машинный код, созданный JIT.

Связь с предыдущей темой:

```text
Bytecode
   │
   │ JIT compilation
   ▼
Native machine code
   │
   ▼
Code Cache
```

Когда JVM снова выполняет уже скомпилированный участок, она может использовать машинный код из Code Cache вместо повторной интерпретации этого участка.

Code Cache — **не место хранения Java-объектов** и не замена heap.

#### Где что хранится?

Для быстрого повторения:

| Что | Где концептуально находится |
| --- | --- |
| Объекты и массивы | Heap |
| Поля объекта | В составе объекта в Heap |
| Stack Frame вызванного метода | JVM Stack конкретного потока |
| Локальный примитив | Local Variables текущего Frame |
| Локальная ссылка на объект | Local Variables Frame; объект — в Heap |
| Метаданные загруженных классов | Metaspace в HotSpot |
| JIT-скомпилированный машинный код | Code Cache в HotSpot |

Со **static-полями** лучше не использовать упрощённый ответ «static лежит в Metaspace». Спецификация JVM не требует такого физического размещения. В HotSpot метаданные класса и значения его Java static-полей — не одно и то же; для интервью важнее понимать, что static-поле принадлежит **классу**, а не экземпляру. Детали конкретного физического размещения являются implementation detail.

#### Heap и Stack — главное различие

| Heap | JVM Stack |
| --- | --- |
| Общий для потоков | У каждого потока свой |
| Обычно содержит объекты и массивы | Содержит frames вызовов |
| Управляется GC | Frames удаляются при возврате из методов |
| Может привести к `OutOfMemoryError: Java heap space` | Глубокие вызовы могут привести к `StackOverflowError` |
| Размер обычно контролируется `-Xms/-Xmx` | Размер стека потока — `-Xss` |

#### Что важно запомнить

- **Heap** — общая область, где обычно размещаются объекты и массивы.
- **JVM Stack** принадлежит конкретному потоку и состоит из frames вызванных методов.
- **Stack Frame** содержит local variables, operand stack и служебные данные выполнения метода.
- **Metaspace** в HotSpot хранит метаданные загруженных классов и использует native memory; с Java 8 он заменил PermGen.
- **Code Cache** хранит машинный код, созданный JIT в HotSpot.
- Не стоит механически отвечать «всё локальное — Stack, всё static — Metaspace»: реальная модель и оптимизации JVM сложнее этой мнемоники.

#### На собеседовании

**Чем Heap отличается от Stack?**

> Heap — общая для потоков область, где обычно размещаются объекты и массивы и которой управляет GC. У каждого потока свой JVM Stack, состоящий из frames вызванных методов. Frames содержат локальные переменные, operand stack и служебные данные выполнения.

**Что такое Stack Frame?**

> Это структура, создаваемая в JVM Stack при вызове метода. Она содержит локальные переменные метода, operand stack и данные, необходимые для выполнения и возврата из метода. После завершения вызова frame удаляется.

**Что хранится в Metaspace?**

> В HotSpot Metaspace используется для метаданных загруженных классов. Он находится в native memory и с Java 8 заменил PermGen. При чрезмерной загрузке классов или утечках ClassLoader'ов можно получить OutOfMemoryError: Metaspace.

**Где находится объект, если ссылка на него — локальная переменная?**

> В обычной модели локальная ссылка находится в frame текущего потока, а объект размещён в heap. Но JIT может оптимизировать аллокации, поэтому это не нужно трактовать как абсолютное физическое правило для любого оптимизированного кода.

- Основная база: пользовательский конспект «Копия Срез 2–8 Java», тема «Области памяти в Java, Runtime data areas»: Heap, Stack, Metaspace и Code Cache.
- [JVM Specification — Run-Time Data Areas](https://docs.oracle.com/en/java/javase/26/docs/specs/jvms/se26/html/jvms-2.html#jvms-2.5) — Heap, JVM Stacks, Method Area и Frames на уровне спецификации.
- [Java HotSpot VM Guide](https://docs.oracle.com/en/java/javase/26/vm/index.html) — детали реализации HotSpot.

### 1.4. Garbage Collection: достижимость, поколения и сборщики

**Garbage Collector (GC)** — механизм автоматического управления памятью, который находит объекты, больше не нужные программе, и освобождает занимаемую ими память.

Ключевая идея: GC не пытается угадать, «используется ли объект по смыслу». Он определяет, **достижим ли объект из набора корневых ссылок (GC Roots)**.

#### Reachability и GC Roots

Представим граф объектов:

```text
GC Root
   │
   ▼
 Object A ─────► Object B

 Object C ─────► Object D
```

`A` и `B` достижимы от GC Root, поэтому считаются живыми. Если до `C` и `D` больше нет пути от корней, весь этот изолированный граф может быть собран GC — даже если объекты внутри него ссылаются друг на друга.

К типичным **GC Roots** относятся, например:

- ссылки из активных stack frames потоков;
- static-ссылки загруженных классов;
- ссылки из JNI;
- внутренние ссылки самой JVM.

Пример:

```java
User user = new User();
user = null;
```

После `user = null` объект **не обязательно удаляется немедленно**. Если других путей от GC Roots к нему нет, он становится кандидатом на сборку. Когда именно GC освободит память — не гарантируется.

> Поэтому фраза «GC удаляет объекты, на которые нет ссылок» неточна. Важна не абсолютная численность ссылок, а **достижимость от GC Roots**.

#### Garbage Collector не предотвращает все memory leaks

Автоматический GC не означает, что в Java невозможны утечки памяти.

Например:

```java
static final List<byte[]> CACHE = new ArrayList<>();

public static void add() {
    CACHE.add(new byte[1_000_000]);
}
```

Если список постоянно растёт, объекты остаются достижимыми через static-ссылку:

```text
GC Root
   │
   ▼
static CACHE
   │
   ├──► byte[]
   ├──► byte[]
   └──► byte[]
```

GC **не имеет права их удалить**, хотя приложению они могут быть уже логически не нужны.

Это и есть важный вид memory leak в managed-языках: память занята объектами, которые программе больше не нужны, но технически всё ещё достижимы.

#### Почему используются поколения?

Наблюдение, на котором основаны многие generational GC:

> Большинство объектов живут недолго.

Например, временные DTO, строки, промежуточные коллекции и объекты запроса часто перестают быть нужны вскоре после создания.

Поэтому традиционная generational-модель разделяет heap на области:

```text
Heap
├── Young Generation
│     ├── Eden
│     ├── Survivor 0
│     └── Survivor 1
│
└── Old / Tenured Generation
```

Новые объекты **обычно** аллоцируются в Young Generation. Пережившие несколько циклов сборки объекты могут быть **promoted** в Old Generation.

Упрощённо:

```text
new object
    │
    ▼
  Eden
    │
    │ пережил GC
    ▼
Survivor
    │
    │ переживает следующие GC
    ▼
   Old
```

**Важно:** эта схема полезна для понимания Serial/Parallel и общей идеи generational GC, но не является универсальным физическим устройством всех современных сборщиков. Например, G1 организует heap в регионы, а современные режимы ZGC имеют собственную архитектуру.

#### Minor, Major и Full GC

Эти термины широко используются, но их смысл зависит от конкретного collector.

Обычно:

- **Minor GC** — сборка Young Generation;
- **Major GC** — часто подразумевают работу со старым поколением;
- **Full GC** — сборка, затрагивающая весь или почти весь heap и часто другие области/служебные структуры JVM.

Нельзя считать `Major GC` и `Full GC` строгими универсальными синонимами. Для диагностики производительности важнее смотреть **какой collector используется и какое событие реально записано в GC log**.

#### Stop-The-World

**Stop-The-World (STW)** — пауза, во время которой JVM приостанавливает application threads (mutator threads), чтобы выполнить определённую фазу работы GC или другую VM-операцию.

```text
Application: ────────┐      ┌──────────────
                     │ STOP │
GC:                  └──────┘
                       STW
```

STW не означает, что любой GC целиком выполняется при остановленном приложении. Современные collectors стараются выполнять значительную часть работы **concurrently** с application threads, оставляя STW только для отдельных фаз.

Поэтому два важных показателя GC:

- **throughput** — сколько времени приложение реально выполняет полезную работу;
- **latency / pause time** — насколько долгими могут быть паузы.

Часто между ними приходится искать компромисс.

#### Основные алгоритмические идеи

GC-алгоритмы строятся из нескольких базовых подходов.

**Mark-Sweep**

1. Найти и пометить достижимые объекты.
2. Освободить память недостижимых.

Минус — после освобождения могут оставаться разрозненные свободные участки, то есть **фрагментация**.

**Mark-Compact**

После определения живых объектов они перемещаются ближе друг к другу:

```text
До:
[A][free][B][free][free][C]

После:
[A][B][C][      free       ]
```

Это уменьшает фрагментацию, но перемещение объектов требует дополнительной работы.

**Copying / Evacuation**

Живые объекты копируются из одной области памяти в другую. Подход особенно выгоден там, где большинство объектов быстро умирает: копировать приходится только небольшое число выживших объектов.

Современные collectors комбинируют эти идеи, а не обязательно используют ровно один алгоритм.

#### Основные Garbage Collectors

Для собеседования полезно понимать **цель** каждого collector, а не запоминать все внутренние фазы.

| Collector | Основная цель | Общая идея |
| --- | --- | --- |
| **Serial GC** | Простота, небольшие heap | Основная GC-работа выполняется одним GC-потоком; STW |
| **Parallel GC** | Высокий throughput | Использует несколько GC-потоков; делает ставку на пропускную способность |
| **G1 GC** | Баланс throughput и предсказуемых пауз | Heap разделён на регионы; выбирает регионы для сборки и эвакуации |
| **ZGC** | Очень низкие паузы | Большая часть тяжёлой работы выполняется concurrent с приложением |
| **Shenandoah** | Низкие паузы | Выполняет в том числе перемещение объектов преимущественно concurrent |

##### Serial GC

Подходит для небольших приложений и окружений с ограниченными ресурсами.

Запуск:

```bash
-XX:+UseSerialGC
```

Его преимущество — простота и небольшие накладные расходы. Для большого server-side приложения длительные STW-паузы обычно делают его менее привлекательным.

##### Parallel GC

Использует несколько GC threads и ориентирован прежде всего на **throughput**.

```bash
-XX:+UseParallelGC
```

Хороший мысленный ориентир: если важнее выполнить максимум работы за единицу времени, а более заметные паузы допустимы, Parallel GC может быть подходящим кандидатом.

##### G1 GC

**G1 (Garbage-First)** делит heap на множество одинаковых по размеру **regions**, а не опирается на одно непрерывное физическое разделение heap на привычные Eden/Survivor/Old области.

Логически регионы всё равно могут выполнять роли Eden, Survivor и Old:

```text
Heap regions:

[E][E][O][S][O][E][free][O][free]...
```

G1 старается выбирать для очередной сборки регионы, очистка которых даст хороший эффект, и выполняет эвакуацию живых объектов.

Для G1 можно задавать **pause-time goal**, например:

```bash
-XX:MaxGCPauseMillis=200
```

Это **цель**, а не жёсткая гарантия, что каждая пауза будет короче 200 мс.

G1 стал default collector в HotSpot начиная с **JDK 9**.

##### ZGC

**ZGC** разработан для очень низких пауз и больших heap. Значительная часть marking, relocation и другой GC-работы выполняется concurrent с приложением.

Главная идея для интервью:

> ZGC переносит большую часть тяжёлой работы из STW-фаз в concurrent-фазы, поэтому длительность пауз значительно меньше зависит от размера heap, чем у традиционных stop-the-world collectors.

Не стоит обещать конкретное значение вроде «паузы всегда < 10 ms»: реальная latency зависит от версии JDK, железа и workload.

##### Shenandoah

**Shenandoah** также ориентирован на low-pause workloads и выполняет значительную часть работы, включая compaction/evacuation, concurrent с приложением.

На уровне интервью обычно достаточно понимать общую цель:

```text
Parallel GC  → throughput
G1           → balance / pause-time goals
ZGC          → ultra-low latency
Shenandoah   → low latency
```

#### А что с CMS?

В старых материалах часто встречается **CMS (Concurrent Mark Sweep)**. Он действительно был важным low-pause collector и выполнял часть работы concurrent.

Но для современной Java важно знать исторический контекст:

- CMS был **deprecated в JDK 9**;
- CMS был **removed в JDK 14**.

Поэтому на современном собеседовании его полезно знать как исторический collector, но выбирать CMS для новой актуальной JVM уже нельзя.

#### Можно ли вызвать GC вручную?

Можно попросить JVM выполнить GC:

```java
System.gc();
```

или:

```java
Runtime.getRuntime().gc();
```

Но это **не гарантия немедленной сборки**. Это запрос JVM, а не команда «прямо сейчас удали мусор».

В прикладном backend-коде вручную вызывать GC обычно не следует. Если приложение требует постоянных ручных вызовов GC, правильнее искать причину: лишние аллокации, слишком маленький heap, удержание объектов или неверные настройки collector.

#### Типичные ошибки в понимании GC

**«Если присвоить ссылке null, объект сразу удалится».**  
Нет. Объект лишь может стать недостижимым. Время запуска GC не определяется этой строкой.

**«GC гарантирует отсутствие memory leaks».**  
Нет. Если ненужный объект остаётся достижимым, GC считает его живым.

**«Full GC происходит только когда Old полностью заполнен».**  
Слишком грубое правило. Причины и поведение зависят от collector и конкретного состояния JVM.

**«Любой GC полностью останавливает приложение на всё время сборки».**  
Нет. Современные collectors выполняют часть фаз concurrently, хотя STW-фазы всё равно существуют.

**«Young = Eden + S0 + S1 для любого collector».**  
Это хорошая учебная модель generational collectors, но не универсальная физическая разметка всех современных GC.

#### Что важно запомнить

- GC определяет живые объекты через **reachability от GC Roots**.
- Недостижимый объект становится кандидатом на сборку, но не обязан исчезнуть немедленно.
- GC не спасает от утечек, если ненужные объекты всё ещё **достижимы**.
- Generational GC опирается на идею, что большинство объектов живут недолго.
- **STW** — пауза application threads; concurrent GC уменьшает объём работы внутри таких пауз, но не обязательно устраняет их полностью.
- **Parallel** ориентирован на throughput, **G1** — на баланс и pause goals, **ZGC/Shenandoah** — на низкую latency.
- CMS — исторически важный collector, но удалён из JDK начиная с 14.

#### На собеседовании

**Как GC понимает, что объект можно удалить?**

> JVM начинает обход графа объектов от GC Roots. Всё достижимое считается живым. Объекты, до которых нет пути от корней, могут быть собраны GC. Поэтому циклические ссылки сами по себе не мешают сборке, если весь цикл недостижим.

**Что такое GC Roots?**

> Это начальные точки, от которых GC определяет достижимость объектов. К ним относятся, например, ссылки из активных stack frames, static-ссылки загруженных классов, JNI-ссылки и некоторые внутренние ссылки JVM.

**Чем G1 отличается от Parallel GC?**

> Parallel GC в первую очередь оптимизирует throughput и использует параллельные GC-потоки, но допускает заметные STW-паузы. G1 делит heap на регионы и старается балансировать throughput с целевым временем пауз, выбирая регионы для очередной сборки.

**Может ли быть memory leak в Java при наличии GC?**

> Да. GC удаляет недостижимые объекты. Если объект приложению уже не нужен, но на него остаётся достижимая сильная ссылка, например из бесконечно растущего static cache, GC не сможет его удалить.

### 1.5. Типы данных Java: primitives, references и преобразования

В Java тип определяет, **какие значения может хранить переменная и какие операции над ними разрешены**. На верхнем уровне типы удобно разделить на две группы:

```text
Java types
├── Primitive types
│   ├── boolean
│   ├── byte, short, int, long
│   ├── char
│   └── float, double
│
└── Reference types
    ├── classes
    ├── interfaces
    ├── arrays
    └── ...
```

> В исходном конспекте отдельного полноценного блока по базовым типам данных найдено мало, поэтому этот подраздел в основном дополняет базу материалом из Java Language Specification.

#### Primitive types

В Java есть **8 primitive types**:

| Тип | Размер / представление | Пример |
| --- | --- | --- |
| `byte` | 8-bit signed integer | `byte b = 10;` |
| `short` | 16-bit signed integer | `short s = 1000;` |
| `int` | 32-bit signed integer | `int n = 42;` |
| `long` | 64-bit signed integer | `long id = 42L;` |
| `float` | 32-bit IEEE 754 floating-point | `float f = 1.5F;` |
| `double` | 64-bit IEEE 754 floating-point | `double d = 1.5;` |
| `char` | 16-bit unsigned UTF-16 code unit | `char c = 'A';` |
| `boolean` | `true` или `false` | `boolean active = true;` |

Диапазоны целочисленных типов:

```text
byte   -128 ... 127
short  -32768 ... 32767
int    -2^31 ... 2^31 - 1
long   -2^63 ... 2^63 - 1
char   0 ... 65535
```

Для `boolean` Java Language Specification не задаёт «размер в байтах», который следует использовать как языковую гарантию. Поэтому ответ «boolean занимает 1 byte» для собеседования слишком категоричен: физическое представление зависит от реализации JVM и контекста хранения.

#### Primitive и Reference — главное отличие

Primitive-переменная хранит **само значение**:

```java
int age = 30;
```

Reference-переменная содержит **ссылочное значение**, позволяющее обратиться к объекту:

```java
User user = new User();
```

Упрощённо:

```text
int age = 30

age
┌────┐
│ 30 │
└────┘

User user = new User()

user                     object
┌───────────┐           ┌────────────┐
│ reference ├──────────►│ User       │
└───────────┘           └────────────┘
```

Reference-переменная может иметь значение `null`:

```java
User user = null;
```

Primitive — нет:

```java
int value = null; // compile error
```

Wrapper-классы (`Integer`, `Long`, `Boolean` и т. д.) являются **reference types**, а не primitives. Autoboxing подробно рассмотрим следующим подразделом.

#### Default values и локальные переменные

Поля объекта получают default values автоматически:

```java
class Example {
    int number;       // 0
    boolean active;   // false
    String text;      // null
}
```

Для полей основные значения по умолчанию:

- integer types → `0`;
- floating-point → `0.0`;
- `char` → `'\u0000'`;
- `boolean` → `false`;
- references → `null`.

Но **локальная переменная не получает значение, которое можно просто прочитать без инициализации**:

```java
void test() {
    int value;
    System.out.println(value); // compile error
}
```

Компилятор применяет правила **definite assignment** и не позволит использовать локальную переменную до того, как она гарантированно получила значение.

#### Integer literals: почему иногда нужен L?

Целочисленный литерал без суффикса обычно имеет тип `int`, если значение помещается в `int`.

```java
int a = 100;
long b = 100;
```

Во второй строке `int`-значение безопасно расширяется до `long`.

Но большое значение нужно записать как `long` literal:

```java
long population = 8_000_000_000L;
```

Без `L` литерал не представим как обычный decimal `int`.

Обычно используют заглавную `L`, потому что строчная `l` визуально похожа на цифру `1`.

#### Floating-point literals: почему float требует F?

Floating-point literal без суффикса имеет тип `double`:

```java
double d = 1.5;
```

Поэтому это не скомпилируется:

```java
float f = 1.5; // compile error
```

Нужно явно указать `float`:

```java
float f = 1.5F;
```

Причина в том, что преобразование `double → float` является narrowing conversion и может потерять точность.

#### Widening conversion

**Widening primitive conversion** — преобразование в тип, способный представить более широкий набор значений соответствующей категории. Во многих случаях выполняется автоматически:

```java
int value = 100;
long big = value;
double d = big;
```

Упрощённая цепочка числовых расширений:

```text
byte ─► short ─► int ─► long ─► float ─► double
          char ─► int ────────► ...
```

Но «widening» не означает «никогда не теряется точность».

Например:

```java
long value = 9_007_199_254_740_993L;
double d = value;

System.out.println((long) d == value); // false
```

`double` имеет огромный диапазон, но не способен точно представить каждое 64-bit integer value.

#### Narrowing conversion

При переходе к более узкому типу обычно требуется явный cast:

```java
int value = 130;
byte b = (byte) value;

System.out.println(b); // -126
```

Почему `-126`? При narrowing сохраняются только подходящие младшие биты; результат может полностью изменить числовое значение.

Поэтому cast означает не «сделай безопасно», а скорее:

> Я явно разрешаю это преобразование и принимаю возможную потерю информации.

#### Integer overflow

Java не выбрасывает исключение при обычном переполнении `int` или `long`:

```java
int max = Integer.MAX_VALUE;
System.out.println(max + 1);
```

Результат:

```text
-2147483648
```

Целочисленная арифметика для этих типов работает с фиксированной разрядностью, поэтому происходит wrap-around.

Если переполнение должно считаться ошибкой, можно использовать методы:

```java
Math.addExact(a, b);
Math.multiplyExact(a, b);
```

Они выбрасывают `ArithmeticException` при overflow.

#### Numeric promotion: почему byte + byte даёт int?

Это популярная ловушка:

```java
byte a = 10;
byte b = 20;

// byte c = a + b; // compile error
int c = a + b;
```

При арифметических операциях `byte`, `short` и `char` обычно проходят **binary numeric promotion** до `int`.

Поэтому результат `a + b` здесь имеет тип `int`.

Ещё пример:

```java
byte x = 10;
x += 1;       // OK
// x = x + 1; // compile error
```

Compound assignment содержит неявное преобразование обратно к типу левой части. То есть `x += 1` по правилам языка не полностью эквивалентно простой записи `x = x + 1`.

#### char — это не «маленькая String»

`char` представляет **один UTF-16 code unit**, а не обязательно один полноценный Unicode-символ.

```java
char c = 'A';
System.out.println((int) c); // 65
```

Некоторые Unicode code points требуют **двух char** (surrogate pair). Поэтому:

```java
String emoji = "😀";
System.out.println(emoji.length()); // 2
```

`String.length()` возвращает количество UTF-16 code units, а не количество визуально воспринимаемых символов.

Эту тему подробнее разберём в отдельной главе **String & Immutability**.

#### float и double: почему 0.1 + 0.2 != 0.3?

`float` и `double` используют binary floating-point representation. Многие привычные десятичные дроби нельзя представить в двоичной системе точно.

```java
double result = 0.1 + 0.2;

System.out.println(result);        // 0.30000000000000004
System.out.println(result == 0.3); // false
```

Поэтому сравнение вычисленных floating-point values через `==` часто некорректно для прикладной задачи.

Для научных расчётов обычно учитывают допустимую погрешность:

```java
double epsilon = 1e-9;

if (Math.abs(a - b) < epsilon) {
    // достаточно близкие значения для выбранной задачи
}
```

Для денег, где важна **точная десятичная арифметика**, обычно используют `BigDecimal`:

```java
BigDecimal price = new BigDecimal("0.1");
BigDecimal tax = new BigDecimal("0.2");

System.out.println(price.add(tax)); // 0.3
```

Предпочтительнее строковый конструктор или `BigDecimal.valueOf(...)`, а не `new BigDecimal(0.1)`, потому что последний получает уже неточное binary floating-point значение.

#### NaN и Infinity

Floating-point арифметика имеет специальные значения:

```java
double positiveInfinity = 1.0 / 0.0;
double nan = 0.0 / 0.0;

System.out.println(positiveInfinity); // Infinity
System.out.println(nan);              // NaN
```

В отличие от integer division:

```java
int x = 1 / 0; // ArithmeticException
```

Особенно важно поведение `NaN`:

```java
double value = Double.NaN;

System.out.println(value == value);       // false
System.out.println(Double.isNaN(value));  // true
```

`NaN` не равен даже самому себе при обычном операторе `==`.

#### Что важно запомнить

- В Java **8 primitive types**; всё остальное относится к reference types.
- Reference может быть `null`, primitive — нет.
- Поля получают default values, а локальные переменные должны пройти definite assignment перед чтением.
- `byte`, `short` и `char` в арифметике часто продвигаются до `int`.
- Widening обычно не требует cast, narrowing обычно требует, но widening всё равно иногда может потерять **точность**.
- Integer overflow обычно не выбрасывает исключение; для контролируемой арифметики есть `Math.*Exact`.
- `float/double` не подходят для точной денежной арифметики; обычно используют `BigDecimal`.
- `char` — UTF-16 code unit, а не гарантированно один Unicode character.

#### На собеседовании

**Какие primitive types есть в Java?**

> Восемь: byte, short, int, long, float, double, char и boolean. Первые четыре — целочисленные signed-типы, char — unsigned UTF-16 code unit, float и double — floating-point, boolean хранит true или false.

**Почему byte + byte возвращает int?**

> Из-за правил numeric promotion. Перед большинством арифметических операций byte, short и char продвигаются до int, поэтому результат сложения двух byte имеет тип int.

**Чем widening отличается от narrowing?**

> Widening преобразует значение к более широкому типу и обычно выполняется автоматически. Narrowing может отбросить часть информации и обычно требует явного cast. При этом widening тоже не гарантирует сохранение точности, например long → double может округлить большое целое.

**Почему для денег не стоит использовать double?**

> Потому что double хранит двоичную floating-point аппроксимацию, и многие десятичные дроби вроде 0.1 представлены неточно. Для точной десятичной арифметики обычно используют BigDecimal с корректным способом создания значения.

- В пользовательском конспекте отдельный полноценный блок по primitive/reference types в найденных материалах отсутствует; текущий подраздел добавлен как необходимая база Java Core.

- [Java Language Specification — Conversions and Contexts](https://docs.oracle.com/javase/specs/jls/se26/html/jls-5.html) — widening, narrowing и numeric promotion.
- [Java Language Specification — Expressions](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html) — арифметика, compound assignment и операторы.

### 1.6. Wrapper classes и autoboxing/unboxing

Для каждого primitive type в Java существует соответствующий **wrapper class (класс-обёртка)**:

| Primitive | Wrapper |
| --- | --- |
| `byte` | `Byte` |
| `short` | `Short` |
| `int` | `Integer` |
| `long` | `Long` |
| `float` | `Float` |
| `double` | `Double` |
| `char` | `Character` |
| `boolean` | `Boolean` |

Обёртки нужны, когда значение должно использоваться как объект. Например, Java generics не работают непосредственно с primitive types:

```java
// List<int> numbers;      // нельзя
List<Integer> numbers;     // можно
```

Wrapper classes также предоставляют полезные методы:

```java
int value = Integer.parseInt("42");
int max = Integer.max(10, 20);
boolean digit = Character.isDigit('7');
```

> В найденных разделах исходного конспекта отдельного материала про wrapper classes и autoboxing практически нет. Этот подраздел добавлен как необходимая часть Java Core на основе правил Java Language Specification и API wrapper-классов.

#### Autoboxing

**Autoboxing** — автоматическое преобразование primitive value в соответствующий wrapper type.

```java
Integer number = 10;
```

Концептуально это соответствует вызову:

```java
Integer number = Integer.valueOf(10);
```

Другой частый пример:

```java
List<Integer> numbers = new ArrayList<>();

numbers.add(10); // int → Integer
```

Метод `add()` ожидает `Integer`, поэтому компилятор применяет boxing conversion.

#### Unboxing

**Unboxing** — обратное преобразование wrapper object в primitive value:

```java
Integer boxed = 10;
int primitive = boxed;
```

Концептуально:

```java
int primitive = boxed.intValue();
```

Autoboxing/unboxing — удобный синтаксический механизм языка. Но важно помнить, что `int` и `Integer` **не становятся одним и тем же типом**.

#### Главная ловушка unboxing: null

Primitive не может быть `null`, а wrapper — может:

```java
Integer count = null;
```

Поэтому:

```java
Integer count = null;
int value = count;
```

во время выполнения приведёт к:

```text
NullPointerException
```

Причина — скрытый unboxing:

```java
int value = count.intValue();
```

Такая ошибка особенно неприятна, когда преобразование спрятано внутри выражения:

```java
Integer count = null;

if (count > 0) {
    // ...
}
```

Для сравнения с `0` Java должна получить primitive `int`, поэтому происходит unboxing `null`.

Практический вывод: если значение по смыслу **не может отсутствовать**, primitive часто безопаснее wrapper. Wrapper нужен, когда `null` действительно несёт отдельный смысл либо API требует объект.

#### `==` и `equals()` у wrapper-объектов

Для primitives оператор `==` сравнивает значения:

```java
int a = 1000;
int b = 1000;

System.out.println(a == b); // true
```

Для двух references `==` проверяет, ссылаются ли они на **один и тот же объект**:

```java
Integer a = 1000;
Integer b = 1000;

System.out.println(a == b);      // обычно false
System.out.println(a.equals(b)); // true
```

Поэтому wrapper values по содержимому обычно сравнивают через `equals()`:

```java
Objects.equals(a, b);
```

`Objects.equals()` особенно удобен, если один из operands может быть `null`.

#### Integer Cache

Почему следующий код может удивить?

```java
Integer a = 100;
Integer b = 100;

System.out.println(a == b); // true
```

При boxing Java использует `Integer.valueOf(...)`. Для небольших целых значений используются заранее созданные объекты.

Java Language Specification гарантирует для определённых constant expressions как минимум диапазон:

```text
-128 ... 127
```

Поэтому:

```java
Integer a = 127;
Integer b = 127;

System.out.println(a == b); // true
```

Но:

```java
Integer a = 128;
Integer b = 128;

System.out.println(a == b); // обычно false
```

**Нельзя строить бизнес-логику на таком поведении `==`.** Если нужны равные числовые значения:

```java
a.equals(b)
```

или null-safe вариант:

```java
Objects.equals(a, b)
```

Практическая формула:

```text
primitive == primitive → сравнение значений
reference == reference → сравнение идентичности ссылок
wrapper.equals(...)    → сравнение значения с учётом типа
```

#### Почему `new Integer(...)` использовать не нужно

Исторически можно было написать:

```java
Integer value = new Integer(10);
```

Но constructors wrapper-классов вроде `Integer(int)` давно deprecated for removal. Для boxing используется `Integer.valueOf()`, а чаще всего достаточно autoboxing:

```java
Integer value = 10;
```

Это также позволяет использовать cache там, где он предусмотрен.

#### Смешанное сравнение wrapper и primitive

Рассмотрим:

```java
Integer a = 1000;
int b = 1000;

System.out.println(a == b); // true
```

Здесь сравниваются не две references. `a` проходит **unboxing**, после чего фактически сравниваются два `int`.

Но если `a == null`:

```java
Integer a = null;
int b = 1000;

System.out.println(a == b); // NullPointerException
```

Это ещё одна причина всегда смотреть на **типы operands**, а не запоминать правило «`==` с Integer работает так-то».

#### Arithmetic и скрытый boxing

Wrapper участвует в арифметике через unboxing:

```java
Integer count = 10;
count++;
```

Упрощённо происходит:

```text
Integer
   │ unboxing
   ▼
  int
   │ + 1
   ▼
  int
   │ boxing
   ▼
Integer
```

То есть wrapper не становится mutable. `Integer` — immutable class: результат операции представляет другое значение/ссылку.

Это важно и для производительности: большое количество boxing/unboxing может создавать лишнюю работу и, когда значение не берётся из cache, потенциальные allocations.

Например, в производительном числовом коде:

```java
long sum = 0;
for (int i = 0; i < 1_000_000; i++) {
    sum += i;
}
```

primitive types обычно предпочтительнее wrappers, если объектная семантика не нужна.

#### Wrapper в generics и collections

Generics принимают reference types:

```java
List<Integer> ids = List.of(1, 2, 3);
Map<Long, Boolean> flags = new HashMap<>();
```

Поэтому при работе с коллекциями primitives автоматически boxing-ятся.

Из этого следует типичная ловушка с перегрузками `List.remove()`:

```java
List<Integer> numbers = new ArrayList<>(List.of(10, 20, 30));

numbers.remove(1);
```

Здесь вызывается:

```java
remove(int index)
```

и удаляется элемент с индексом `1`, то есть `20`.

Если нужно удалить значение:

```java
numbers.remove(Integer.valueOf(10));
```

тогда вызывается:

```java
remove(Object o)
```

Это уже пересечение wrapper types с Collections; подробно поведение списков разберём в отдельной главе.

#### Wrapper и методы

Wrapper classes полезны не только из-за generics. Они содержат константы и операции преобразования:

```java
int value = Integer.parseInt("123");
Integer boxed = Integer.valueOf("123");

String binary = Integer.toBinaryString(10);

System.out.println(Integer.MAX_VALUE);
System.out.println(Integer.MIN_VALUE);
```

Важно различать:

```java
Integer.parseInt("42")  // возвращает primitive int
Integer.valueOf("42")   // возвращает Integer
```

#### Что важно запомнить

- Wrapper classes — объектные аналоги восьми primitive types.
- **Autoboxing:** primitive → wrapper; **unboxing:** wrapper → primitive.
- Unboxing `null` приводит к **NullPointerException**.
- `==` между двумя wrapper references проверяет identity, а `equals()` — значение.
- При смешанном сравнении wrapper с primitive может произойти unboxing.
- Для `Integer` при boxing гарантирован cache как минимум для `-128..127`; нельзя использовать это как причину сравнивать wrappers через `==`.
- Generics работают с reference types, поэтому `List<int>` невозможен, а `List<Integer>` — возможен.
- `Integer` и другие числовые wrappers immutable.
- Лишний boxing/unboxing может быть нежелателен в performance-sensitive коде.

#### На собеседовании

**Что такое autoboxing и unboxing?**

> Autoboxing — автоматическое преобразование primitive в wrapper, например int в Integer. Unboxing — обратное преобразование Integer в int. Компилятор вставляет необходимые преобразования, например через Integer.valueOf() и intValue(). Важно помнить, что при unboxing null возникает NullPointerException.

**Почему Integer нельзя надёжно сравнивать через ==?**

> Потому что Integer — reference type, и == между двумя references сравнивает идентичность объектов. Для небольших значений результат может случайно выглядеть как сравнение значений из-за Integer Cache, например для диапазона -128..127. Для сравнения значения нужно использовать equals() или Objects.equals().

**Почему `Integer a = 127; Integer b = 127; a == b` возвращает true?**

> При autoboxing используется Integer.valueOf(), а небольшие Integer-классы кэшируются. Для constant values в диапазоне как минимум -128..127 спецификация гарантирует одинаковые boxed instances. Но полагаться на == для сравнения wrapper values нельзя.

**Что произойдёт при `Integer value = null; int x = value;`?**

> Произойдёт unboxing. JVM попытается получить primitive value из null-reference, поэтому будет NullPointerException.

#### Источники и уточнения

- В найденных разделах пользовательского конспекта отдельный материал по wrapper classes/autoboxing отсутствует; подраздел добавлен как необходимая база Java Core.
- [Java Language Specification — Boxing and Unboxing Conversions](https://docs.oracle.com/javase/specs/jls/se26/html/jls-5.html#jls-5.1.7) — правила boxing, cache guarantees и unboxing.
- [Integer API](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/lang/Integer.html) — `valueOf`, `parseInt`, константы и API `Integer`.

### 1.7. Передача параметров и операторы Java

Один из самых частых вопросов по Java Core:

> Java передаёт параметры **по значению (pass-by-value)** или **по ссылке (pass-by-reference)**?

Правильный ответ: **Java всегда использует pass-by-value**.

Путаница возникает потому, что для reference types значением переменной является **ссылка на объект**. При вызове метода копируется эта ссылка.

> В найденных разделах исходного конспекта отдельного материала по pass-by-value и базовым операторам нет. Этот подраздел добавлен как необходимая база Java Core по правилам Java Language Specification.

#### Передача primitive

Простой пример:

```java
static void change(int value) {
    value = 100;
}

public static void main(String[] args) {
    int number = 10;

    change(number);

    System.out.println(number); // 10
}
```

Метод получает **копию значения** `10`:

```text
main()                  change()

number = 10   ─────►    value = 10
   │                       │
   │                       ▼
   │                   value = 100
   │
   ▼
number = 10
```

Изменение параметра `value` никак не меняет переменную `number` вызывающего метода.

#### Что происходит с объектом?

Рассмотрим reference type:

```java
class User {
    String name;

    User(String name) {
        this.name = name;
    }
}

static void rename(User user) {
    user.name = "Bob";
}

public static void main(String[] args) {
    User user = new User("Alice");

    rename(user);

    System.out.println(user.name); // Bob
}
```

На первый взгляд кажется, что объект передали «по ссылке». Но на самом деле метод получил **копию ссылочного значения**.

Упрощённо:

```text
main()                         rename()

user ──────┐              copyOfReference
           │                     │
           └────────┬────────────┘
                    ▼
              ┌───────────┐
              │ User      │
              │ name=Alice│
              └───────────┘
                    │
                    ▼
              name = Bob
```

Обе ссылки указывают на **один объект**, поэтому через локальную копию ссылки метод может изменить состояние этого объекта.

Но саму переменную вызывающего метода он заменить не может.

#### Переприсваивание параметра не меняет исходную ссылку

```java
static void replace(User user) {
    user = new User("Bob");
}

public static void main(String[] args) {
    User user = new User("Alice");

    replace(user);

    System.out.println(user.name); // Alice
}
```

После входа в `replace()` существуют две независимые переменные, содержащие одинаковое ссылочное значение.

После переприсваивания:

```text
main()                         replace()

user ───────────────► [User: Alice]

                         user ─► [User: Bob]
```

Изменился только локальный параметр `user` внутри `replace()`.

Отсюда удобная формула:

> Java передаёт **копию значения переменной**. Для primitive это копия primitive value, для reference type — копия reference value.

#### Почему Java — не pass-by-reference?

При настоящем pass-by-reference вызываемый метод мог бы заменить саму переменную вызывающего кода.

Например, такой `swap()` в Java не работает:

```java
static void swap(User first, User second) {
    User temp = first;
    first = second;
    second = temp;
}
```

```java
User a = new User("Alice");
User b = new User("Bob");

swap(a, b);

System.out.println(a.name); // Alice
System.out.println(b.name); // Bob
```

Метод переставил только **свои копии ссылок**.

Это хороший способ доказать на собеседовании, что Java не использует pass-by-reference.

#### `==`: что именно сравнивается?

Оператор `==` зависит от типов operands.

Для primitives сравниваются значения:

```java
int a = 10;
int b = 10;

System.out.println(a == b); // true
```

Для references сравнивается identity ссылок — указывают ли они на один объект:

```java
User a = new User("Alice");
User b = new User("Alice");
User c = a;

System.out.println(a == b); // false
System.out.println(a == c); // true
```

Содержимое объектов обычно сравнивают через `equals()`, если класс реализует нужную value semantics.

```text
== для primitives  → значение
== для references  → один ли объект
equals()            → логическое равенство по контракту класса
```

Подробно контракт `equals()/hashCode()` разберём в отдельной главе.

#### Short-circuit operators: `&&` и `||`

Операторы **conditional AND** `&&` и **conditional OR** `||` вычисляют правую часть только тогда, когда она действительно нужна.

```java
if (user != null && user.isActive()) {
    // ...
}
```

Если `user == null`, первая часть уже равна `false`. Всё выражение `&&` не может стать `true`, поэтому:

```java
user.isActive()
```

не вызывается.

Именно поэтому такая null-check конструкция безопасна.

Для `||` логика обратная:

```java
if (cached != null || loadFromDatabase()) {
    // ...
}
```

Если `cached != null` уже даёт `true`, правую часть вычислять не требуется.

#### `&` и `|` — это не то же самое

Для boolean operands можно использовать и `&`, `|`, но они **вычисляют обе стороны**:

```java
boolean result = false & expensiveCheck();
```

`expensiveCheck()` будет вызван.

А здесь:

```java
boolean result = false && expensiveCheck();
```

не будет.

Кроме того, `&`, `|` и `^` используются как **bitwise operators** для integer types:

```java
int flags = 0b0101;
int mask  = 0b0001;

System.out.println(flags & mask); // 1
```

Для обычных логических условий чаще нужны `&&` и `||`.

#### Побочные эффекты и short-circuit

Short-circuit влияет не только на производительность, но и на поведение программы:

```java
int x = 0;

boolean result = true || ++x > 0;

System.out.println(x); // 0
```

Правая часть не вычислилась, поэтому `x` не изменился.

Код, который критически зависит от побочного эффекта внутри сложного boolean expression, обычно труднее читать. Лучше не прятать важные изменения состояния в условиях без необходимости.

#### Порядок вычисления operands

В Java operands выражений вычисляются **слева направо**.

```java
static int print(int value) {
    System.out.println(value);
    return value;
}

int result = print(1) + print(2);
```

Сначала будет вызван `print(1)`, затем `print(2)`.

Это отличается от **приоритета операторов**. Приоритет определяет структуру выражения:

```java
int result = 2 + 3 * 4; // 14
```

Сначала по структуре выполняется умножение:

```text
2 + (3 * 4)
```

Если выражение сложно читать, лучше использовать скобки, даже если приоритет операторов известен.

#### `++i` и `i++`

Оба оператора увеличивают переменную на единицу, но значение самого выражения различается.

**Prefix increment:**

```java
int i = 5;
int x = ++i;

System.out.println(i); // 6
System.out.println(x); // 6
```

Сначала increment, затем используется новое значение.

**Postfix increment:**

```java
int i = 5;
int x = i++;

System.out.println(i); // 6
System.out.println(x); // 5
```

В выражении используется старое значение, а переменная увеличивается.

Не стоит писать головоломки вроде:

```java
int x = i++ + ++i;
```

Язык определяет порядок вычисления, но такой код плохо читается и легко приводит к ошибкам.

#### Тернарный оператор

Conditional operator:

```java
condition ? valueIfTrue : valueIfFalse
```

Пример:

```java
String status = age >= 18 ? "adult" : "minor";
```

Выполняется только одна из двух ветвей — выбранная по условию.

Тернарный оператор удобен для короткого выбора **значения**, но глубокая вложенность быстро ухудшает читаемость:

```java
String result = a ? "A" : b ? "B" : c ? "C" : "D";
```

В таких случаях обычный `if/else` часто понятнее.

#### Оператор `instanceof`

`instanceof` проверяет, совместим ли объект с указанным reference type:

```java
if (value instanceof String) {
    String text = (String) value;
}
```

Современная Java поддерживает pattern matching:

```java
if (value instanceof String text) {
    System.out.println(text.length());
}
```

Здесь проверка типа и получение переменной `text` объединены.

Для `null`:

```java
Object value = null;

System.out.println(value instanceof String); // false
```

`instanceof` не выбрасывает `NullPointerException` для `null`.

#### Типичные ошибки

**«Объекты в Java передаются по ссылке».**  
Нет. Передаётся копия значения ссылки.

**«Если метод изменил объект, значит это pass-by-reference».**  
Нет. Две независимые reference-переменные могут указывать на один mutable object.

**«`==` сравнивает объекты по содержимому».**  
Для references `==` проверяет identity. Логическое равенство обычно реализуется через `equals()`.

**«`&` и `&&` отличаются только написанием».**  
Нет. Для boolean `&&` short-circuit, а `&` вычисляет обе стороны; кроме того, `&` работает как bitwise operator для integer types.

#### Что важно запомнить

- Java **всегда pass-by-value**.
- Для primitive копируется primitive value; для объекта копируется **reference value**.
- Через копию ссылки можно изменить mutable object, но нельзя переприсвоить переменную вызывающего метода.
- `==` сравнивает primitive values или identity references.
- `&&` и `||` используют short-circuit evaluation.
- `&` и `|` для boolean вычисляют обе стороны; для integer types выполняют bitwise operations.
- Java вычисляет operands слева направо.
- `++i` возвращает новое значение, `i++` — старое значение выражения.
- Pattern matching для `instanceof` позволяет одновременно проверить тип и получить типизированную переменную.

#### На собеседовании

**Java — pass-by-value или pass-by-reference?**

> Java всегда pass-by-value. При передаче primitive копируется само значение. При передаче объекта копируется значение ссылки на этот объект. Поэтому метод может через эту копию изменить состояние общего объекта, но переприсваивание параметра внутри метода не изменит ссылочную переменную вызывающего кода.

**Почему изменение поля объекта внутри метода видно снаружи?**

> Потому что исходная переменная и параметр метода содержат две копии одной и той же ссылки и указывают на один объект. Изменяется сам объект, а не ссылочная переменная вызывающего метода.

**Чем `&&` отличается от `&` для boolean?**

> `&&` использует short-circuit: если результат уже известен по левой части, правая не вычисляется. `&` вычисляет обе части всегда. Поэтому проверка `obj != null && obj.isValid()` безопасна, а с одиночным `&` вызов справа всё равно произошёл бы.

**Чем `==` отличается от `equals()`?**

> Для primitive `==` сравнивает значения, а для references — указывают ли ссылки на один объект. `equals()` — метод, через который класс может определить логическое равенство объектов по содержимому. Его контракт подробно рассматривается отдельно.

#### Источники и уточнения

- В найденных разделах пользовательского конспекта отдельного материала по pass-by-value и базовым операторам не обнаружено; подраздел добавлен как необходимая база Java Core.
- [Java Language Specification — Variables](https://docs.oracle.com/javase/specs/jls/se26/html/jls-4.html#jls-4.12) — значения переменных и параметры.
- [Java Language Specification — Method Invocation Expressions](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.12) — вычисление аргументов и передача значений при вызове.
- [Java Language Specification — Evaluation Order](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.7) — порядок вычисления.
- [Java Language Specification — Conditional-And / Conditional-Or](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.23) — short-circuit operators.

### 1.8. ООП в Java: инкапсуляция, наследование, полиморфизм и абстракция

**Объектно-ориентированное программирование (ООП)** — подход, при котором программа строится вокруг объектов, объединяющих **состояние** и **поведение**.

В Java класс описывает структуру и поведение, а объект — конкретный экземпляр класса:

```java
class BankAccount {
    private long balance;

    void deposit(long amount) {
        balance += amount;
    }

    long getBalance() {
        return balance;
    }
}

BankAccount account = new BankAccount();
```

Четыре классических понятия, которые обычно ожидают услышать на собеседовании:

```text
OOP
├── Encapsulation
├── Inheritance
├── Polymorphism
└── Abstraction
```

> В исходном конспекте ООП встречается через темы наследования JPA, SOLID и полиморфизма, но отдельного цельного раздела с четырьмя базовыми принципами в найденном материале нет. Поэтому базовое объяснение ниже дополнено как необходимая часть Java Core. Связь наследования с Liskov Substitution Principle поддерживается исходным материалом и будет подробно разобрана в главе SOLID.

#### Инкапсуляция

**Инкапсуляция (encapsulation)** — объединение состояния и поведения объекта и контроль доступа к внутренним деталям.

Плохой вариант:

```java
class BankAccount {
    public long balance;
}
```

Любой код может сделать:

```java
account.balance = -1_000_000;
```

Класс не контролирует собственное состояние.

Лучше скрыть детали и предоставить операции, сохраняющие инварианты:

```java
class BankAccount {
    private long balance;

    public void deposit(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("amount must be positive");
        }

        balance += amount;
    }

    public long getBalance() {
        return balance;
    }
}
```

Здесь внешний код знает **что можно сделать**, но не обязан знать **как внутри хранится и изменяется balance**.

Инкапсуляция — это не просто «все поля сделать `private` и создать getter/setter». Если написать:

```java
public void setBalance(long balance) {
    this.balance = balance;
}
```

то формально поле скрыто, но объект всё ещё может позволять установить некорректное состояние.

Главная идея:

> Объект сам контролирует допустимые изменения своего состояния.

#### Наследование

**Наследование (inheritance)** позволяет создать новый класс на основе существующего.

```java
class Animal {
    void makeSound() {
        System.out.println("...");
    }
}

class Dog extends Animal {
    @Override
    void makeSound() {
        System.out.println("Woof");
    }
}
```

`Dog` наследует доступное поведение `Animal` и может его переопределять.

Отношение наследования обычно читают как **is-a**:

```text
Dog is an Animal
```

Java поддерживает:

- наследование **одного класса** через `extends`;
- реализацию **нескольких интерфейсов** через `implements`.

```java
class Dog extends Animal implements Runnable, Comparable<Dog> {
    // ...
}
```

Множественного наследования классов в Java нет:

```java
// class C extends A, B { } // нельзя
```

Это избегает ряда неоднозначностей состояния и реализации, возникающих при наследовании сразу от нескольких классов.

#### Наследование — не просто способ переиспользовать код

Если классы имеют похожий код, это ещё не означает, что между ними должно быть наследование.

Наследник должен корректно использоваться там, где ожидается родитель:

```java
void process(Animal animal) {
    animal.makeSound();
}

process(new Dog());
```

Это связано с **Liskov Substitution Principle (LSP)**: подтип не должен неожиданно ломать ожидания, установленные контрактом базового типа.

Исходный конспект формулирует эту идею практически: если наследник в корне меняет ожидаемое поведение родителя, такую иерархию лучше не строить.

#### Полиморфизм

**Полиморфизм (polymorphism)** позволяет работать с объектами разных конкретных типов через общий базовый тип.

```java
interface PaymentProcessor {
    void pay(long amount);
}

class CardProcessor implements PaymentProcessor {
    @Override
    public void pay(long amount) {
        System.out.println("Pay by card: " + amount);
    }
}

class CryptoProcessor implements PaymentProcessor {
    @Override
    public void pay(long amount) {
        System.out.println("Pay by crypto: " + amount);
    }
}
```

Клиентский код зависит от абстракции:

```java
static void checkout(PaymentProcessor processor) {
    processor.pay(100);
}

checkout(new CardProcessor());
checkout(new CryptoProcessor());
```

`checkout()` не нужно знать конкретный класс.

Это один из главных практических эффектов ООП:

```text
           PaymentProcessor
             ▲          ▲
             │          │
      CardProcessor  CryptoProcessor
             ▲          ▲
             └──── checkout() ────┘
```

#### Dynamic dispatch

Рассмотрим:

```java
Animal animal = new Dog();
animal.makeSound();
```

Тип переменной — `Animal`, реальный объект — `Dog`.

Для переопределённого instance-метода JVM выбирает реализацию в соответствии с **runtime class объекта**:

```text
reference type: Animal
runtime object: Dog

animal.makeSound()
        │
        ▼
Dog.makeSound()
```

Это называют **dynamic method dispatch**.

Именно он лежит в основе runtime polymorphism для переопределённых instance methods.

#### Overriding и Overloading — не одно и то же

**Overriding (переопределение)** — наследник предоставляет новую реализацию instance-метода базового типа:

```java
class Animal {
    void makeSound() {}
}

class Dog extends Animal {
    @Override
    void makeSound() {}
}
```

Какой overriding-метод выполнить, определяется runtime type объекта.

**Overloading (перегрузка)** — методы имеют одно имя, но разные списки параметров:

```java
void print(int value) {}
void print(String value) {}
```

Выбор подходящей overload-сигнатуры выполняется **на этапе компиляции** исходя из compile-time типов и правил overload resolution.

Ловушка:

```java
static void print(Animal animal) {
    System.out.println("Animal");
}

static void print(Dog dog) {
    System.out.println("Dog");
}

Animal animal = new Dog();
print(animal);
```

Результат:

```text
Animal
```

Потому что overload выбирается по compile-time типу `animal`, то есть `Animal`.

#### static-методы не участвуют в dynamic dispatch как instance methods

```java
class Parent {
    static void hello() {
        System.out.println("Parent");
    }
}

class Child extends Parent {
    static void hello() {
        System.out.println("Child");
    }
}
```

Для static methods речь идёт не об overriding, а о **method hiding**.

Поэтому:

```java
Parent value = new Child();
value.hello();
```

выберет метод на основе compile-time типа `Parent`, а не runtime-типа объекта.

Практически static-методы лучше вызывать через имя класса:

```java
Parent.hello();
Child.hello();
```

#### Абстракция

**Абстракция (abstraction)** — выделение существенного контракта и сокрытие ненужных пользователю деталей реализации.

Например:

```java
interface NotificationSender {
    void send(String message);
}
```

Код, использующий `NotificationSender`, знает только контракт:

```java
class OrderService {
    private final NotificationSender sender;

    OrderService(NotificationSender sender) {
        this.sender = sender;
    }

    void createOrder() {
        // business logic
        sender.send("Order created");
    }
}
```

Конкретная реализация может быть любой:

```java
class EmailSender implements NotificationSender {
    @Override
    public void send(String message) {
        // SMTP implementation
    }
}
```

```java
class TelegramSender implements NotificationSender {
    @Override
    public void send(String message) {
        // Telegram API implementation
    }
}
```

`OrderService` не зависит от деталей SMTP или Telegram API.

Инкапсуляция и абстракция связаны, но это не одно и то же:

- **инкапсуляция** отвечает за границы объекта и контроль его внутреннего состояния;
- **абстракция** отвечает за то, какой существенный контракт мы показываем пользователю, скрывая лишние детали.

#### Composition over inheritance

**Композиция (composition)** означает, что объект получает нужное поведение через другие объекты, а не обязательно через наследование.

Через наследование:

```text
Car extends Engine
```

Это плохая модель: автомобиль **не является двигателем**.

Через композицию:

```java
class Car {
    private final Engine engine;

    Car(Engine engine) {
        this.engine = engine;
    }

    void start() {
        engine.start();
    }
}
```

Отношение:

```text
Car has an Engine
```

Композиция часто предпочтительнее, потому что:

- уменьшает жёсткую связанность с базовым классом;
- позволяет заменять реализацию зависимости;
- удобнее тестируется;
- не заставляет моделировать ложное отношение `is-a`;
- позволяет собирать поведение из нескольких компонентов.

Но правило **composition over inheritance** не означает «наследование всегда плохо». Наследование хорошо подходит, когда существует настоящее отношение подтипа и соблюдается контракт базового класса.

#### Пример: полиморфизм вместо большого if/switch

Без полиморфизма:

```java
void pay(String type, long amount) {
    if ("CARD".equals(type)) {
        // card logic
    } else if ("CRYPTO".equals(type)) {
        // crypto logic
    }
}
```

При добавлении каждого нового способа оплаты этот метод приходится менять.

С полиморфизмом:

```java
interface PaymentProcessor {
    void pay(long amount);
}
```

Каждая реализация содержит своё поведение, а вызывающий код работает с общим контрактом:

```java
void pay(PaymentProcessor processor, long amount) {
    processor.pay(amount);
}
```

Это не означает, что любой `switch` нужно заменять иерархией классов. Полиморфизм полезен, когда у нас действительно есть несколько взаимозаменяемых поведений и ожидается их развитие.

#### Типичные ошибки

**«Инкапсуляция — это private поля + getters/setters».**  
Это только инструмент. Цель — контролировать состояние и скрывать внутренние детали.

**«Наследование нужно для переиспользования кода».**  
Переиспользование — возможный эффект, но главным должно быть корректное отношение подтипа `is-a`.

**«Overloading — runtime polymorphism».**  
Overload resolution происходит на compile time. Dynamic dispatch относится к overriding instance methods.

**«static-метод переопределяется».**  
Нет. Static methods скрываются (method hiding), а не участвуют в обычном dynamic dispatch.

**«Composition over inheritance означает никогда не использовать extends».**  
Нет. Нужно выбирать композицию, когда требуется `has-a`/делегирование, и наследование — когда действительно моделируется корректный подтип.

#### Что важно запомнить

- **Encapsulation** — объект контролирует своё состояние и скрывает детали реализации.
- **Inheritance** — отношение подтипа `is-a`; в Java класс наследуется только от одного класса.
- **Polymorphism** — разные реализации можно использовать через общий тип.
- **Abstraction** — клиент работает с существенным контрактом, не зная лишних деталей реализации.
- Overriding instance methods поддерживает **dynamic dispatch** по runtime type объекта.
- Overloading разрешается **на compile time**.
- Static methods скрываются, а не переопределяются полиморфно.
- Композиция часто гибче наследования, но наследование уместно для настоящего отношения подтипа.

#### На собеседовании

**Назовите основные принципы ООП.**

> Обычно выделяют инкапсуляцию, наследование, полиморфизм и абстракцию. Инкапсуляция позволяет объекту контролировать своё состояние, наследование моделирует отношение подтипа, полиморфизм позволяет работать с разными реализациями через общий тип, а абстракция выделяет необходимый контракт и скрывает детали реализации.

**Что такое полиморфизм в Java?**

> Это возможность использовать объекты разных конкретных типов через общий базовый класс или интерфейс. При вызове переопределённого instance-метода конкретная реализация выбирается по runtime type объекта — это dynamic dispatch.

**Чем overriding отличается от overloading?**

> Overriding — наследник переопределяет instance-метод родителя, и конкретная реализация выбирается во время выполнения по runtime type. Overloading — несколько методов имеют одно имя, но разные параметры; нужная сигнатура выбирается компилятором на compile time.

**Почему часто рекомендуют composition over inheritance?**

> Композиция слабее связывает классы и позволяет менять или подменять поведение через зависимости. Наследование стоит использовать, когда объект действительно является подтипом базового класса и сохраняет его контракт, а не просто ради повторного использования нескольких методов.

#### Источники и уточнения

- Исходный конспект содержит наследование в контексте JPA/Hibernate и отдельно связывает корректную иерархию наследования с Liskov Substitution Principle.
- Исходный материал по SOLID формулирует LSP как требование не менять поведение наследника неожиданным для контракта родителя образом; подробный SOLID будет разобран в своей главе.
- [Java Language Specification — Classes](https://docs.oracle.com/javase/specs/jls/se26/html/jls-8.html) — классы, наследование, overriding и hiding.
- [Java Language Specification — Interfaces](https://docs.oracle.com/javase/specs/jls/se26/html/jls-9.html) — интерфейсы и их наследование.
- [Java Language Specification — Method Invocation](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.12) — overload resolution и выбор метода.

### 1.9. Interface и abstract class: что выбрать

И **interface**, и **abstract class** позволяют описать абстракцию, но решают немного разные задачи.

Короткий ориентир:

```text
interface
→ контракт / capability
→ разные классы могут реализовать один интерфейс
→ класс может реализовать несколько интерфейсов

abstract class
→ общая база близких классов
→ может хранить instance state
→ может иметь constructor
→ класс может наследоваться только от одного класса
```

> В найденных фрагментах исходного конспекта интерфейсы используются в контексте SOLID и Spring, но отдельного сравнения interface vs abstract class нет. Поэтому языковые правила этого подраздела добавлены по Java Language Specification. Из исходника сохраняется практическая идея Interface Segregation: небольшие специализированные интерфейсы обычно предпочтительнее одного огромного.

#### Interface

**Interface** задаёт контракт, который класс обязуется реализовать.

```java
interface PaymentProcessor {
    void pay(long amount);
}
```

Реализация:

```java
class CardPaymentProcessor implements PaymentProcessor {

    @Override
    public void pay(long amount) {
        System.out.println("Card payment: " + amount);
    }
}
```

Клиент может зависеть от интерфейса:

```java
class OrderService {
    private final PaymentProcessor processor;

    OrderService(PaymentProcessor processor) {
        this.processor = processor;
    }

    void checkout(long amount) {
        processor.pay(amount);
    }
}
```

В результате `OrderService` не привязан к конкретной реализации оплаты.

Именно такой подход постоянно встречается в Spring: зависимость объявляется через интерфейс, а конкретную реализацию предоставляет контейнер.

#### Abstract class

**Abstract class** — класс, экземпляр которого нельзя создать напрямую и который может содержать как абстрактное, так и готовое поведение.

```java
abstract class PaymentProcessor {

    protected final String providerName;

    protected PaymentProcessor(String providerName) {
        this.providerName = providerName;
    }

    public abstract void pay(long amount);

    public void printProvider() {
        System.out.println(providerName);
    }
}
```

Наследник обязан реализовать абстрактный метод, если сам не является abstract:

```java
class CardPaymentProcessor extends PaymentProcessor {

    CardPaymentProcessor() {
        super("Card provider");
    }

    @Override
    public void pay(long amount) {
        System.out.println("Card payment: " + amount);
    }
}
```

Abstract class может иметь:

- instance fields;
- constructors;
- abstract methods;
- обычные concrete methods;
- `static` methods;
- методы и поля с различными допустимыми access modifiers.

То есть abstract class подходит не только для контракта, но и для **общего состояния и общей реализации** иерархии.

#### `extends` и `implements`

Класс наследуется от класса через `extends`:

```java
class Dog extends Animal {
}
```

Класс реализует интерфейс через `implements`:

```java
class Dog implements Runnable {
    @Override
    public void run() {
    }
}
```

Можно совместить:

```java
class Dog extends Animal implements Runnable, Comparable<Dog> {

    @Override
    public void run() {
    }

    @Override
    public int compareTo(Dog other) {
        return 0;
    }
}
```

Java разрешает классу:

```text
extends     → максимум один непосредственный superclass
implements  → несколько interfaces
```

Сам интерфейс может наследовать несколько интерфейсов:

```java
interface Readable {
    void read();
}

interface Writable {
    void write();
}

interface Storage extends Readable, Writable {
}
```

#### Поля интерфейса

Переменные, объявленные в interface, не являются instance fields.

Например:

```java
interface Limits {
    int MAX_RETRIES = 3;
}
```

Поле интерфейса неявно:

```java
public static final int MAX_RETRIES = 3;
```

Поэтому интерфейс не хранит изменяемое состояние конкретного экземпляра так, как обычный или abstract class.

Если абстракции действительно нужно общее instance state:

```java
protected int retryCount;
```

это аргумент в пользу abstract class или композиции.

#### Методы интерфейса: не только abstract

Историческая формула «interface содержит только abstract methods» для современной Java неверна.

Interface может содержать несколько видов методов.

**Abstract method:**

```java
interface Sender {
    void send(String message);
}
```

Такой метод неявно `public abstract`.

**Default method** — появился в Java 8:

```java
interface Sender {

    void send(String message);

    default void sendDefaultMessage() {
        send("Hello");
    }
}
```

Он содержит реализацию и наследуется реализующими классами.

Одна из важных причин появления default methods — возможность **эволюционировать интерфейсы**, добавляя поведение без обязательного немедленного изменения каждой существующей реализации.

**Static method:**

```java
interface Sender {

    static boolean isValid(String message) {
        return message != null && !message.isBlank();
    }
}
```

Вызывается через имя интерфейса:

```java
Sender.isValid("Hello");
```

Static interface method не является instance-методом реализации.

**Private method** — поддерживается в interfaces начиная с Java 9:

```java
interface Sender {

    default void sendHello() {
        sendNormalized(" hello ");
    }

    default void sendBye() {
        sendNormalized(" bye ");
    }

    private void sendNormalized(String message) {
        send(message.trim());
    }

    void send(String message);
}
```

Private methods позволяют вынести повторяющуюся внутреннюю логику нескольких default/private методов и не выставлять её как часть публичного контракта.

#### Зачем default methods?

Представим библиотечный интерфейс:

```java
interface Logger {
    void log(String message);
}
```

У него сотни реализаций. Если просто добавить новый abstract method:

```java
void logError(String message);
```

старые реализации перестанут удовлетворять контракту.

Default method позволяет предоставить реализацию:

```java
interface Logger {

    void log(String message);

    default void logError(String message) {
        log("ERROR: " + message);
    }
}
```

Существующие реализации получают новое поведение автоматически, если им не требуется его переопределять.

#### Конфликт default methods

Несколько интерфейсов могут содержать одинаковый default method:

```java
interface A {
    default void hello() {
        System.out.println("A");
    }
}

interface B {
    default void hello() {
        System.out.println("B");
    }
}
```

Если класс реализует оба:

```java
class C implements A, B {
}
```

компилятор не может сам выбрать реализацию. Класс обязан разрешить конфликт:

```java
class C implements A, B {

    @Override
    public void hello() {
        A.super.hello();
    }
}
```

Можно вызвать одну из родительских реализаций либо написать полностью свою.

Это иногда называют **diamond problem**, но Java не допускает неоднозначность молча — конфликт должен быть разрешён явно.

#### Class wins over interface default

Если метод уже существует в superclass, а interface предлагает default method с той же подходящей сигнатурой, приоритет имеет метод класса.

Упрощённое правило:

```text
class implementation > interface default
```

Это важно для совместимости старых классов после появления default methods.

#### Abstract class тоже может реализовать interface

```java
interface Sender {
    void send(String message);
}

abstract class BaseSender implements Sender {

    protected void validate(String message) {
        if (message == null) {
            throw new IllegalArgumentException();
        }
    }
}
```

`BaseSender` может не реализовывать `send()`, потому что сам является abstract.

Конкретный наследник завершает контракт:

```java
class EmailSender extends BaseSender {

    @Override
    public void send(String message) {
        validate(message);
        System.out.println("Email: " + message);
    }
}
```

Это позволяет сочетать интерфейс как внешний контракт и abstract class как необязательную базовую реализацию.

#### Может ли abstract class не иметь abstract methods?

Да:

```java
abstract class BaseService {

    public void log() {
        System.out.println("log");
    }
}
```

Ключевое слово `abstract` запрещает создавать экземпляр напрямую:

```java
// new BaseService(); // compile error
```

Наличие хотя бы одного abstract method не является обязательным.

Обратное правило строгое: если класс содержит abstract method, сам класс должен быть `abstract`.

#### Abstract method и `final`

`abstract` означает:

> наследник должен предоставить реализацию.

`final` для метода означает:

> наследник не может переопределить метод.

Поэтому сочетание:

```java
// abstract final void execute();
```

логически противоречиво и запрещено.

А вот abstract class может иметь final concrete method:

```java
abstract class Processor {

    public final void execute() {
        validate();
        process();
    }

    protected abstract void process();

    private void validate() {
        // ...
    }
}
```

Это позволяет зафиксировать общий алгоритм, оставив наследнику отдельную точку расширения.

#### Interface vs abstract class

Для быстрого повторения:

| Interface | Abstract class |
| --- | --- |
| Хорош для контракта/capability | Хорош для общей базы иерархии |
| Класс может реализовать несколько | Наследоваться можно только от одного класса |
| Нет instance state | Может иметь instance state |
| Нет constructor | Может иметь constructor |
| Может иметь abstract/default/static/private methods | Может иметь abstract и concrete methods |
| Поля — `public static final` | Возможны обычные instance/static fields |
| Удобен для слабой связанности | Удобен для общего состояния и реализации |

#### Как выбирать на практике?

**Выбирай interface**, когда:

- нужен контракт для потенциально несвязанных классов;
- ожидается несколько взаимозаменяемых реализаций;
- важна возможность реализовать несколько контрактов;
- абстракция не требует общего mutable instance state;
- зависимость должна легко подменяться, например в DI или тестах.

Пример:

```java
interface PaymentGateway {
    PaymentResult pay(Order order);
}
```

Реализации Stripe, банковского API или тестовый fake не обязаны иметь общего superclass.

**Рассматривай abstract class**, когда:

- классы действительно принадлежат одной иерархии;
- им нужно общее состояние;
- нужен общий constructor;
- существенная часть реализации одинакова;
- нужно предоставить `protected` API наследникам.

На практике часто полезна комбинация:

```text
interface
   │
   ├── Implementation A
   │
   └── abstract BaseImplementation
              │
              ├── Implementation B
              └── Implementation C
```

Клиенты зависят от интерфейса, а некоторые реализации при необходимости переиспользуют общую базу.

#### Интерфейсы и Interface Segregation

В исходном конспекте принцип **Interface Segregation Principle (ISP)** сформулирован как идея:

> лучше несколько небольших интерфейсов, чем один огромный.

Например, вместо:

```java
interface Worker {
    void code();
    void drive();
    void cook();
}
```

лучше выделить отдельные способности:

```java
interface Developer {
    void code();
}

interface Driver {
    void drive();
}
```

Тогда класс реализует только тот контракт, который ему действительно нужен.

Подробно ISP и остальные принципы SOLID будут разобраны отдельно.

#### Типичные ошибки

**«В interface нельзя писать реализацию методов».**  
Устарело. В современной Java есть default, static и private interface methods.

**«Interface вообще не может содержать поля».**  
Может, но они неявно `public static final` — это константы интерфейса, а не instance state.

**«Abstract class обязан иметь abstract method».**  
Нет. Abstract class может вообще не иметь abstract methods.

**«Interface всегда лучше abstract class».**  
Нет. Они решают разные задачи. Если нужна общая база с состоянием и constructor, abstract class может быть естественнее.

**«Java поддерживает множественное наследование классов через interfaces».**  
Interface даёт множественное наследование **контрактов** и в современной Java некоторого поведения через default methods, но класс по-прежнему имеет только один непосредственный superclass и не наследует instance state из interfaces.

#### Что важно запомнить

- Класс может `extends` только один класс, но `implements` несколько interfaces.
- Interface — прежде всего **контракт**, abstract class — **общая база иерархии** с возможностью хранить state.
- Interface fields неявно `public static final`.
- Interface может иметь abstract, default, static и private methods.
- Default methods появились в Java 8; private interface methods — в Java 9.
- Конфликт одинаковых default methods нескольких interfaces класс должен разрешить явно.
- Abstract class может иметь constructor и может не содержать ни одного abstract method.
- `abstract` и `final` нельзя одновременно применять к одному методу.
- На практике часто удобно дать клиентам interface, а общую реализацию вынести в abstract base class только там, где она действительно нужна.

#### На собеседовании

**Чем interface отличается от abstract class?**

> Interface обычно описывает контракт и позволяет одному классу реализовать несколько независимых контрактов. Abstract class подходит для общей иерархии: может хранить instance state, иметь constructor, protected members и общую реализацию. Класс может наследоваться только от одного класса, но реализовать несколько interfaces.

**Какие методы могут быть в interface?**

> Abstract methods, default и static methods начиная с Java 8, а также private methods начиная с Java 9. Default method наследуется реализациями, static вызывается через интерфейс, private используется для внутреннего переиспользования логики внутри самого interface.

**Что произойдёт, если два интерфейса имеют одинаковый default method?**

> Если класс наследует конфликтующие default implementations и ни одна не имеет приоритета, класс должен явно переопределить метод и разрешить конфликт. При необходимости можно вызвать конкретную реализацию через `InterfaceName.super.method()`.

**Может ли abstract class не содержать abstract methods?**

> Да. `abstract` запрещает прямое создание экземпляра класса, но не требует наличия abstract methods. При этом класс с abstract method сам обязательно должен быть abstract.

#### Источники и уточнения

- Исходный конспект использует interfaces в разделах Spring и SOLID; в частности, ISP сформулирован как предпочтение нескольких небольших интерфейсов одному большому. fileciteturn36file0
- Отдельного сравнения interface и abstract class в найденном исходном материале нет; языковые правила раздела добавлены по JLS.
- [Java Language Specification — Classes](https://docs.oracle.com/javase/specs/jls/se26/html/jls-8.html) — abstract classes, inheritance и members.
- [Java Language Specification — Interfaces](https://docs.oracle.com/javase/specs/jls/se26/html/jls-9.html) — interface declarations, fields, default/static/private methods и наследование.
- [Java Language Specification — Overriding](https://docs.oracle.com/javase/specs/jls/se26/html/jls-9.html#jls-9.4.1) — правила overriding interface methods.

### 1.10. `static` и `final`: принадлежность классу и запрет изменения

`static` и `final` решают разные задачи:

```text
static → member принадлежит классу, а не конкретному объекту
final  → запрещает определённый вид изменения
```

Они могут использоваться вместе:

```java
public static final int MAX_RETRIES = 3;
```

Так обычно объявляют константы уровня класса.

> В исходном конспекте `final` подробно появляется в контексте Java Memory Model и безопасной публикации, а static-поля — в теме памяти JVM. Отдельного цельного раздела по языковой семантике `static/final` в найденном материале нет, поэтому базовые правила ниже дополнены по Java Language Specification. JMM-гарантии `final` здесь только обозначены; подробно они будут разобраны в главе JMM.

#### Instance members и static members

Обычное поле принадлежит **конкретному экземпляру**:

```java
class User {
    String name;
}
```

```java
User first = new User();
first.name = "Alice";

User second = new User();
second.name = "Bob";
```

У объектов независимые значения:

```text
first  ─► User { name = "Alice" }
second ─► User { name = "Bob" }
```

Static field принадлежит **классу как целому**:

```java
class User {
    static int createdCount;
    String name;

    User(String name) {
        this.name = name;
        createdCount++;
    }
}
```

```java
new User("Alice");
new User("Bob");

System.out.println(User.createdCount); // 2
```

Все экземпляры работают с одним static field данного класса/ClassLoader.

Практически static members лучше обращаться через имя класса:

```java
User.createdCount
```

а не:

```java
user.createdCount
```

Последняя форма для доступного static field может компилироваться, но создаёт ложное впечатление, что значение принадлежит объекту.

#### Static method

Static method также относится к классу:

```java
class MathUtils {

    static int square(int value) {
        return value * value;
    }
}
```

Вызов:

```java
int result = MathUtils.square(5);
```

У static method нет текущего экземпляра `this`.

Поэтому напрямую обратиться к instance field нельзя:

```java
class User {
    String name;

    static void printName() {
        // System.out.println(name); // compile error
    }
}
```

Но static method может работать с объектом, если ссылка на него получена явно:

```java
static void printName(User user) {
    System.out.println(user.name);
}
```

#### Static method не переопределяется полиморфно

Как уже обсуждалось в ООП, static methods **скрываются (method hiding)**, а не участвуют в dynamic dispatch как instance methods.

```java
class Parent {
    static void print() {
        System.out.println("Parent");
    }
}

class Child extends Parent {
    static void print() {
        System.out.println("Child");
    }
}
```

```java
Parent value = new Child();
value.print(); // Parent
```

Выбор static method связан с compile-time type выражения.

Для читаемости:

```java
Parent.print();
Child.print();
```

#### Static initialization

Класс может иметь static field initializers и static blocks:

```java
class Config {

    static String host = loadHost();

    static {
        System.out.println("Config initialized");
    }

    private static String loadHost() {
        return "localhost";
    }
}
```

При **инициализации класса** static initializers и static blocks выполняются в текстовом порядке, в котором они записаны в классе.

Например:

```java
class Example {

    static int a = print("a");

    static {
        print("block");
    }

    static int b = print("b");

    static int print(String value) {
        System.out.println(value);
        return 1;
    }
}
```

При инициализации:

```text
a
block
b
```

Важно отличать **загрузку класса** от его **инициализации**: ClassLoader может загрузить класс раньше, а static initialization запускается при наступлении условий инициализации, определённых JVM/JLS.

#### Когда класс инициализируется?

Типичные случаи active use:

```java
new MyClass();
MyClass.someStaticMethod();
System.out.println(MyClass.nonConstantStaticField);
```

Перед первым таким использованием класс должен быть инициализирован.

Но есть важная ловушка с compile-time constants:

```java
class Constants {
    static final int PORT = 8080;

    static {
        System.out.println("initialized");
    }
}
```

```java
System.out.println(Constants.PORT);
```

Если `PORT` — **constant variable** и значение встроено компилятором в использующий код, такое обращение само по себе не обязано инициировать initialization класса `Constants`.

Это одна из причин, почему «любое обращение к static-полю загружает и инициализирует класс» — слишком грубое правило.

#### Что означает `final` для переменной?

Final variable можно присвоить **только один раз**:

```java
final int port = 8080;

// port = 9090; // compile error
```

Final local variable можно присвоить позже, если компилятор может доказать, что это происходит ровно один раз:

```java
final int value;

if (condition) {
    value = 10;
} else {
    value = 20;
}

System.out.println(value);
```

Это называется **blank final** в соответствующих контекстах: значение не обязательно задавать прямо в месте объявления, но после присваивания изменить его нельзя.

#### Final reference не делает объект immutable

Очень важная ловушка:

```java
final List<String> names = new ArrayList<>();

names.add("Alice"); // OK
names.add("Bob");   // OK
```

Запрещено изменить **саму ссылку**:

```java
// names = new ArrayList<>(); // compile error
```

Но объект остаётся mutable:

```text
final reference ─────────► mutable ArrayList
      │
      └── reference нельзя перенаправить
                         объект менять можно
```

Следовательно:

> `final` reference ≠ immutable object.

Для иммутабельности нужно контролировать состояние самого объекта, а не только ссылку на него.

#### Final field

```java
class User {
    private final long id;
    private final String name;

    User(long id, String name) {
        this.id = id;
        this.name = name;
    }
}
```

Instance final field должен быть гарантированно присвоен до завершения constructor — либо в объявлении, либо в constructor/initializer по правилам definite assignment.

Final fields полезны для объектов, состояние которых после создания не должно переназначаться.

Но снова:

```java
class Team {
    private final List<String> members = new ArrayList<>();
}
```

список всё ещё mutable.

#### `static final` — всегда константа?

Не обязательно.

```java
static final int MAX = 100;
```

Это может быть **compile-time constant**, если initializer является constant expression подходящего primitive/String типа.

Но:

```java
static final Integer LIMIT = Integer.valueOf(100);
static final List<String> NAMES = new ArrayList<>();
static final String ID = UUID.randomUUID().toString();
```

тоже `static final`, однако это не compile-time constants в смысле JLS.

Поэтому полезно различать:

```text
static final
      ≠
compile-time constant во всех случаях
```

#### Final method

Final instance method нельзя override:

```java
class PaymentService {

    public final void validate() {
        // fixed behavior
    }
}
```

Наследник может пользоваться методом, но не заменить его реализацию.

Это используют, когда определённую часть поведения базового класса нельзя нарушать.

#### Final class

Final class нельзя наследовать:

```java
final class Token {
}
```

```java
// class JwtToken extends Token { } // compile error
```

Например, `String` — final class.

Но `final class` сам по себе **не гарантирует immutable state**. Он лишь запрещает наследование. Для настоящей immutability нужно дополнительно правильно проектировать поля и API.

#### `abstract` и `final`

Для класса:

```text
abstract → класс предполагает наследование для завершения реализации
final    → наследование запрещено
```

Поэтому класс не может быть одновременно `abstract final`.

Аналогично abstract method требует реализации в наследнике, а final method запрещает overriding, поэтому сочетание для одного метода невозможно.

#### Effectively final

Начиная с Java 8 локальная переменная не обязана быть явно помечена `final`, чтобы использоваться в lambda expression или anonymous/local class, если она **effectively final**.

```java
String prefix = "USER-";

Function<String, String> mapper =
        value -> prefix + value;
```

`prefix` effectively final, потому что после первоначального присваивания значение переменной не меняется.

Но:

```java
String prefix = "USER-";
prefix = "ADMIN-";

Function<String, String> mapper =
        value -> prefix + value; // compile error
```

Переменная перестала быть effectively final.

Причина связана с тем, что lambda захватывает значение локальной переменной, а не получает общую изменяемую stack-variable между жизненными циклами вызовов.

#### Почему это не запрещает менять объект?

```java
List<String> names = new ArrayList<>();

Runnable task = () -> names.add("Alice");
```

Это допустимо, если переменная `names` не переназначается.

Effectively final относится к **переменной-ссылке**, а не к mutability объекта:

```text
names ─────────► ArrayList
  │                │
  │                └── содержимое может меняться
  └── сама local variable не переназначается
```

Это та же концептуальная граница, что и у final reference.

#### `final` и Java Memory Model

Исходный конспект отдельно отмечает важное свойство `final` в JMM: корректно сконструированный объект имеет специальные гарантии видимости для final fields после завершения constructor. fileciteturn40file1

Это **не означает**, что добавление `final` автоматически делает весь объект thread-safe. Например, final reference на mutable collection не делает операции над коллекцией потокобезопасными.

Детали final-field semantics, safe publication и happens-before разберём в главе **Java Memory Model**.

#### Типичные ошибки

**«static field существует отдельно у каждого объекта».**  
Нет. Static member относится к классу, а не к экземпляру.

**«static method может напрямую обратиться к this».**  
Нет. У static method нет текущего экземпляра.

**«final reference делает объект immutable».**  
Нет. Нельзя переназначить ссылку, но mutable object через неё менять можно.

**«static final всегда compile-time constant».**  
Нет. Это зависит от типа и initializer; `UUID.randomUUID().toString()` не становится compile-time constant только из-за `static final`.

**«final class обязательно immutable».**  
Нет. Final запрещает наследование, но ничего сам по себе не говорит о mutability полей.

**«effectively final означает, что объект нельзя менять».**  
Нет. Нельзя переназначать захватываемую local variable; состояние объекта может оставаться mutable.

#### Что важно запомнить

- `static` означает принадлежность **классу**, а не экземпляру.
- Static method не имеет `this` и не участвует в dynamic dispatch как instance method.
- Static initializers выполняются при initialization класса в текстовом порядке.
- `final` variable можно присвоить один раз.
- Final reference запрещает переназначить ссылку, но **не делает объект immutable**.
- Final method нельзя override, final class нельзя наследовать.
- `static final` не всегда означает compile-time constant.
- Local variable может быть **effectively final** без явного `final` и тогда может захватываться lambda.
- У final fields есть специальные гарантии JMM при корректном конструировании объекта, но `final` не равен thread safety.

#### На собеседовании

**Что означает `static`?**

> Static member принадлежит классу, а не конкретному экземпляру. Static field общий для экземпляров данного класса в рамках соответствующей загрузки класса, а static method вызывается без объекта и не имеет `this`.

**Что означает `final` для переменной, метода и класса?**

> Final variable нельзя переназначить после присваивания. Final method нельзя override. Final class нельзя наследовать. При этом final reference не делает сам объект immutable.

**Чем `static final` отличается от compile-time constant?**

> `static final` лишь означает static member с однократным присваиванием ссылки/значения. Compile-time constant имеет дополнительные требования JLS: например, primitive или String variable с constant expression initializer. Поэтому `static final String ID = UUID.randomUUID().toString()` не является compile-time constant.

**Что такое effectively final?**

> Это локальная переменная или параметр, которые не объявлены final, но после присваивания не изменяются. Такие переменные можно захватывать в lambda. Требование относится к самой переменной: объект, на который она ссылается, при этом может быть mutable.

#### Источники и уточнения

- Исходный конспект связывает `final` с JMM и safe publication: корректно инициализированные final fields имеют специальные гарантии видимости. fileciteturn40file1
- Исходник также обсуждает static fields в разделе памяти JVM; физическое размещение не используется здесь как языковая гарантия, поскольку это отдельный implementation-level вопрос. fileciteturn40file8

- [Java Language Specification — Initialization](https://docs.oracle.com/javase/specs/jls/se26/html/jls-12.html#jls-12.4) — условия и порядок initialization классов.
- [Java Language Specification — Lambda Expressions](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.27) — захват final/effectively final variables.

### 1.11. Generics: type safety, wildcards, PECS и type erasure

**Generics** позволяют параметризовать классы, интерфейсы и методы типами.

Главная практическая цель — получить **type safety на этапе компиляции** и не писать ручные casts там, где тип уже известен.

Без generics:

```java
List values = new ArrayList();
values.add("Java");

String value = (String) values.get(0);
```

С generics:

```java
List<String> values = new ArrayList<>();
values.add("Java");

String value = values.get(0);
```

Компилятор знает, что список предназначен для `String`, и не позволит случайно добавить несовместимый объект.

> Поиск по исходному конспекту не нашёл отдельного учебного блока по Java Generics. В исходнике встречаются generic-сигнатуры вроде `Map<Long, Order>`, generic API библиотек и коллекций, но не объясняются invariance, wildcards, PECS или type erasure. Поэтому этот подраздел добавлен как необходимая Java Core база по Java Language Specification.

#### Generic class

Простейший generic class:

```java
class Box<T> {

    private T value;

    void set(T value) {
        this.value = value;
    }

    T get() {
        return value;
    }
}
```

Использование:

```java
Box<String> box = new Box<>();
box.set("Java");

String value = box.get();
```

`T` — **type parameter**.

После подстановки:

```text
Box<String>
    T → String

Box<Integer>
    T → Integer
```

Распространённые соглашения имён:

- `T` — Type;
- `E` — Element;
- `K` — Key;
- `V` — Value;
- `R` — Result/Return type.

Это соглашения, а не специальные ключевые слова.

#### Несколько type parameters

```java
class Pair<K, V> {

    private final K key;
    private final V value;

    Pair(K key, V value) {
        this.key = key;
        this.value = value;
    }

    K key() {
        return key;
    }

    V value() {
        return value;
    }
}
```

```java
Pair<Long, String> user =
        new Pair<>(42L, "Alice");
```

Компилятор часто умеет вывести type arguments справа, поэтому используется diamond operator `<>`.

#### Generic method

Generic может быть не весь класс, а отдельный метод:

```java
static <T> T first(List<T> values) {
    return values.get(0);
}
```

`<T>` объявляется **перед return type**.

Использование:

```java
String firstName = first(List.of("Alice", "Bob"));
Integer firstNumber = first(List.of(10, 20));
```

Обычно type argument выводится компилятором автоматически.

#### Bounded type parameter

Иногда любой `T` слишком широк.

Например:

```java
static <T extends Number> double doubleValue(T value) {
    return value.doubleValue();
}
```

Теперь допустимы:

```java
doubleValue(10);
doubleValue(10L);
doubleValue(2.5);
```

но не:

```java
// doubleValue("10"); // compile error
```

Здесь `extends` означает **upper bound**, а не только наследование класса в обычном смысле. Bound может быть и interface.

Несколько bounds:

```java
static <T extends Number & Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}
```

Если есть class bound, он должен стоять первым, после него могут идти interface bounds.

#### Generics invariant

Очень важное правило:

```text
Integer extends Number

НО

List<Integer> НЕ extends List<Number>
```

То есть Java generics по умолчанию **invariant**.

Почему это необходимо?

Представим, что такое присваивание было бы разрешено:

```java
List<Integer> integers = new ArrayList<>();

// воображаем, что это разрешено:
List<Number> numbers = integers;

numbers.add(3.14);
```

Тогда через `List<Number>` мы добавили бы `Double` в объект, который должен быть `List<Integer>`.

Поэтому:

```java
List<Integer> integers = new ArrayList<>();

// List<Number> numbers = integers; // compile error
```

#### Wildcard `?`

Wildcard означает некоторый неизвестный тип:

```java
List<?> values;
```

Например:

```java
static void printAll(List<?> values) {
    for (Object value : values) {
        System.out.println(value);
    }
}
```

Методу можно передать:

```java
printAll(List.of("A", "B"));
printAll(List.of(1, 2, 3));
```

Но `List<?>` — это **не** то же самое, что `List<Object>`.

```java
List<Object> objects = new ArrayList<>();
objects.add("text");
objects.add(10);
```

`List<Object>` означает: список именно типа `Object`, куда можно добавлять разные объекты.

`List<?>` означает: список некоторого конкретного, но неизвестного нам типа.

Поэтому:

```java
static void add(List<?> values) {
    // values.add("text"); // compile error
}
```

Безопасно добавить обычное ненулевое значение нельзя, потому что реальный список может оказаться `List<Integer>`, `List<User>` и т. д. (`null` — отдельный допустимый случай, но практической пользы здесь почти нет).

#### Upper-bounded wildcard: `? extends T`

```java
List<? extends Number>
```

означает:

> список некоторого неизвестного типа, который является `Number` или его subtype.

Можно передать:

```java
List<Integer> integers = List.of(1, 2, 3);
List<Double> doubles = List.of(1.5, 2.5);

printNumbers(integers);
printNumbers(doubles);
```

```java
static void printNumbers(List<? extends Number> values) {
    for (Number value : values) {
        System.out.println(value.doubleValue());
    }
}
```

Читать как `Number` безопасно.

Но добавлять конкретный subtype нельзя:

```java
static void broken(List<? extends Number> values) {
    // values.add(10);   // compile error
    // values.add(2.5);  // compile error
}
```

Почему? Компилятор не знает, что реально скрывается за `?`:

```text
List<Integer> ?
List<Double>  ?
List<BigDecimal> ?
```

Добавление `Integer` было бы неправильным, если фактический тип — `Double`.

#### Lower-bounded wildcard: `? super T`

```java
List<? super Integer>
```

означает список некоторого типа, являющегося `Integer` или его supertype.

Например:

```java
static void addIntegers(List<? super Integer> values) {
    values.add(10);
    values.add(20);
}
```

Можно передать:

```java
List<Integer> integers = new ArrayList<>();
List<Number> numbers = new ArrayList<>();
List<Object> objects = new ArrayList<>();

addIntegers(integers);
addIntegers(numbers);
addIntegers(objects);
```

Добавлять `Integer` безопасно.

Но при чтении конкретный тип неизвестен:

```java
Object value = values.get(0);
```

Гарантированно получить можно только `Object`, потому что фактический список может быть `List<Object>`.

#### PECS: Producer Extends, Consumer Super

Главное мнемоническое правило для wildcards:

> **PECS — Producer Extends, Consumer Super.**

Если структура **производит значения T**, используем:

```java
? extends T
```

Если структура **принимает/потребляет T**, используем:

```java
? super T
```

Классический пример копирования:

```java
static <T> void copy(
        List<? extends T> source,
        List<? super T> destination
) {
    for (T value : source) {
        destination.add(value);
    }
}
```

```text
source
? extends T
PRODUCER
    │
    │ read T
    ▼
    T
    │
    │ write T
    ▼
? super T
CONSUMER
destination
```

Пример:

```java
List<Integer> source = List.of(1, 2, 3);
List<Number> destination = new ArrayList<>();

copy(source, destination);
```

Важно: PECS — полезная эвристика для **API, где параметр используется в роли producer/consumer**, а не магическое правило «везде ставить wildcard».

#### `List<T>` или `List<? extends T>`?

Если метод должен работать именно с единым type parameter, который связан с другими аргументами/return type, часто нужен `T`.

Например:

```java
static <T> T first(List<T> values) {
    return values.get(0);
}
```

Если метод просто читает значения как базовый тип:

```java
static double sum(List<? extends Number> values) {
    double result = 0;

    for (Number value : values) {
        result += value.doubleValue();
    }

    return result;
}
```

wildcard делает API гибче.

#### Type erasure

Java generics в основном реализованы через **type erasure**.

Это означает, что generic type information используется компилятором для проверки типов, а после компиляции большая часть параметризации не представлена как отдельные runtime-классы.

Например:

```java
List<String> strings = new ArrayList<>();
List<Integer> integers = new ArrayList<>();

System.out.println(
        strings.getClass() == integers.getClass()
); // true
```

Оба объекта runtime являются `ArrayList`.

Упрощённо:

```java
class Box<T> {
    T value;
}
```

после erasure концептуально близок к:

```java
class Box {
    Object value;
}
```

Если есть bound:

```java
class Box<T extends Number> {
    T value;
}
```

erasure `T` основан на его leftmost bound — здесь `Number`.

Это **упрощённая модель для понимания**, а не буквальный Java-source, который генерирует компилятор: компилятор также вставляет casts и при необходимости создаёт bridge methods для сохранения полиморфизма.

#### Generic signatures всё же могут присутствовать в class file

Фраза «generics полностью исчезают после компиляции» слишком грубая.

Исходный конспект в разделе Metaspace прямо упоминает generic-signatures вроде `Map<Long, Order>` среди метаданных классов. fileciteturn44file0

Class files могут содержать generic metadata в атрибутах вроде `Signature`, поэтому reflection способен получить часть объявленной generic-информации:

```java
Field field = MyClass.class.getDeclaredField("orders");
Type type = field.getGenericType();
```

Но runtime object всё равно обычно не несёт различия вида:

```text
new ArrayList<String>()
vs
new ArrayList<Integer>()
```

как двух разных runtime classes.

#### Почему нельзя `new T()`?

```java
class Factory<T> {

    T create() {
        // return new T(); // compile error
    }
}
```

Из-за erasure JVM не располагает в этом месте конкретным runtime class, который следует создать.

Один из вариантов — передать фабрику:

```java
class Factory<T> {

    private final Supplier<T> supplier;

    Factory(Supplier<T> supplier) {
        this.supplier = supplier;
    }

    T create() {
        return supplier.get();
    }
}
```

```java
Factory<User> factory = new Factory<>(User::new);
```

Или передать `Class<T>`, если задача действительно требует reflection.

#### Почему нельзя создать generic array?

Так нельзя:

```java
// T[] values = new T[10];
```

И:

```java
// List<String>[] lists = new List<String>[10];
```

Arrays в Java **reified**: runtime знает их component type и проверяет присваивания.

Generics, напротив, подвергаются erasure.

Смешивание этих моделей нарушило бы runtime type safety.

Сравним:

```java
Number[] numbers = new Integer[2];

numbers[0] = 1;
// numbers[1] = 2.5; // ArrayStoreException
```

Массив runtime знает, что он реально `Integer[]`.

Для `List<String>` такой runtime-проверки type argument нет.

#### Почему нельзя `instanceof List<String>`?

Так нельзя:

```java
// if (value instanceof List<String>) { }
```

После erasure JVM не может в общем случае проверить type argument `String`.

Можно:

```java
if (value instanceof List<?>) {
    // ...
}
```

Runtime способен проверить сам тип `List`, но не параметризацию `String`.

#### Primitive types в generics

Так нельзя:

```java
// List<int>
```

Type arguments должны быть reference types:

```java
List<Integer> numbers;
```

Поэтому используются wrapper classes и autoboxing, рассмотренные ранее.

Это может иметь performance cost в числовом коде из-за boxing/unboxing и представления объектов.

#### Static field типа `T`

У generic class нельзя сделать:

```java
class Box<T> {
    // static T value; // compile error
}
```

Static member принадлежит самому классу `Box`, а не отдельной параметризации:

```text
Box<String>
Box<Integer>
     │
     └── один runtime class Box
```

Не существовало бы однозначного ответа, какого типа должно быть общее static field.

#### Raw types

Старый код до generics совместим через **raw types**:

```java
List values = new ArrayList();
```

Но raw type отключает часть compile-time type safety:

```java
List<String> strings = new ArrayList<>();

List raw = strings;
raw.add(123);

String value = strings.get(0); // возможен ClassCastException
```

Компилятор обычно выдаёт unchecked warning.

Raw types стоит избегать в новом коде, кроме случаев взаимодействия с legacy API, где это действительно необходимо.

#### Heap pollution

**Heap pollution** возникает, когда переменная параметризованного типа фактически ссылается на объект, нарушающий ожидаемую параметризацию.

Raw types — один из способов получить такую проблему:

```java
List<String> strings = new ArrayList<>();
List raw = strings;

raw.add(42);
```

Ошибка может проявиться значительно позже при автоматически вставленном cast:

```java
String value = strings.get(0); // ClassCastException
```

Поэтому unchecked warnings нельзя автоматически считать безобидными.

#### Wildcard capture

Иногда компилятор описывает ошибку через термин вроде:

```text
capture of ?
```

Например:

```java
static void setFirst(List<?> list) {
    // list.set(0, list.get(0)); // может потребовать helper
}
```

`?` представляет неизвестный, но **конкретный** тип. Компилятор внутренне «захватывает» его как отдельный тип.

Типичный приём — helper method:

```java
static void setFirst(List<?> list) {
    setFirstHelper(list);
}

private static <T> void setFirstHelper(List<T> list) {
    list.set(0, list.get(0));
}
```

Это не самый частый вопрос junior/middle интервью, но помогает понимать сообщения компилятора при сложных wildcard API.

#### Типичные ошибки

**«Если Integer extends Number, то List<Integer> extends List<Number>».**  
Нет. Generics invariant.

**«List<?> — то же самое, что List<Object>».**  
Нет. `List<Object>` имеет известный element type `Object`; у `List<?>` element type неизвестен.

**«Из List<? extends Number> можно добавлять Integer».**  
Нет. Фактический тип может быть `List<Double>`.

**«Type erasure означает, что generic information вообще нигде нет после компиляции».**  
Слишком грубо. Runtime instances не разделяются по type arguments, но class file может сохранять generic signatures для reflection.

**«PECS означает, что extends всегда только читает, а super всегда только пишет».**  
Это мнемоника для проектирования API. Технически читать из `? super T` можно как `Object`, а в `? extends T` можно, например, записать `null`.

#### Что важно запомнить

- Generics дают **compile-time type safety** и уменьшают количество ручных casts.
- `T`, `E`, `K`, `V` — обычные соглашения имён type parameters.
- Java generics **invariant**: `List<Integer>` не является subtype `List<Number>`.
- `? extends T` удобно для producer, `? super T` — для consumer.
- **PECS = Producer Extends, Consumer Super.**
- `List<?>` и `List<Object>` имеют разную семантику.
- Generics реализованы преимущественно через **type erasure**.
- Из-за erasure нельзя напрямую `new T()`, `new T[]` или `instanceof List<String>`.
- Type arguments не могут быть primitives: нужен `Integer`, а не `int`.
- Raw types и unchecked operations могут привести к heap pollution и отложенному `ClassCastException`.

#### На собеседовании

**Почему `List<Integer>` нельзя присвоить `List<Number>`?**

> Потому что Java generics invariant. Если бы такое присваивание разрешалось, через ссылку List<Number> можно было бы добавить Double в фактический List<Integer>, нарушив type safety.

**Что такое PECS?**

> Producer Extends, Consumer Super. Если параметризированная структура в основном отдаёт T, обычно используют ? extends T. Если она принимает T — ? super T. Например, источник копирования может быть List<? extends T>, а destination — List<? super T>.

**Чем `List<?>` отличается от `List<Object>`?**

> List<Object> — список с известным element type Object, поэтому в него можно добавлять Object-значения. List<?> — список некоторого неизвестного типа, поэтому безопасно читать элементы как Object, но добавлять конкретные ненулевые значения нельзя.

**Что такое type erasure?**

> Generic type parameters в основном используются компилятором для проверки типов, а runtime не создаёт отдельные классы для List<String> и List<Integer>. После erasure компилятор использует bounds/Object, вставляет необходимые casts и иногда bridge methods. При этом generic signatures могут сохраняться в class file как metadata и быть доступны через reflection.

**Почему нельзя создать `new T()`?**

> После type erasure в общем случае нет конкретного runtime class, который нужно создать. Обычно constructor/factory передают явно, например Supplier<T> или Class<T>.

#### Источники и уточнения

- Отдельного учебного блока по Generics в найденном исходном конспекте нет; исходник только использует generic types и упоминает generic signatures среди метаданных классов. fileciteturn44file0
- Поэтому invariance, wildcards, PECS, erasure и ограничения generics в этом разделе являются дополнением по спецификации Java, а не пересказом исходника.
- [Java Language Specification — Type Parameters](https://docs.oracle.com/javase/specs/jls/se26/html/jls-4.html#jls-4.4) — type parameters и bounds.
- [Java Language Specification — Parameterized Types](https://docs.oracle.com/javase/specs/jls/se26/html/jls-4.html#jls-4.5) — parameterized types, wildcards и raw types.
- [Java Language Specification — Type Erasure](https://docs.oracle.com/javase/specs/jls/se26/html/jls-4.html#jls-4.6) — правила erasure.
- [Java Tutorials — Guidelines for Wildcard Use](https://docs.oracle.com/javase/tutorial/java/generics/wildcardGuidelines.html) — практическое правило in/out variables и PECS-подход.

### 1.12. Enum и Record

`enum` и `record` — специальные формы объявления классов в Java.

Они решают разные задачи:

```text
enum   → фиксированный набор именованных экземпляров
record → компактное представление data carrier / value-like данных
```

> В исходном конспекте enum встречается главным образом в JPA (`@Enumerated`, `LockModeType`), но отдельного Java Core-разбора enum нет. fileciteturn48file0 fileciteturn48file9 Отдельного материала по records поиском не найдено. Поэтому языковая семантика этого подраздела добавлена по Java Language Specification.

#### Enum — не просто набор числовых констант

Простой enum:

```java
enum OrderStatus {
    NEW,
    PAID,
    CANCELLED
}
```

Использование:

```java
OrderStatus status = OrderStatus.NEW;
```

Каждая enum constant — единственный экземпляр соответствующего enum type.

Поэтому enum намного безопаснее набора строк:

```java
String status = "PAYD"; // опечатка компилируется
```

В enum:

```java
// OrderStatus.PAYD // compile error
```

Допустимые значения ограничены самим типом.

#### Enum может иметь поля, constructor и методы

```java
enum HttpStatus {

    OK(200),
    NOT_FOUND(404),
    INTERNAL_ERROR(500);

    private final int code;

    HttpStatus(int code) {
        this.code = code;
    }

    public int getCode() {
        return code;
    }
}
```

Использование:

```java
HttpStatus status = HttpStatus.NOT_FOUND;

System.out.println(status.getCode()); // 404
```

Constructor enum нельзя вызывать самостоятельно:

```java
// new HttpStatus(200); // нельзя
```

Экземпляры создаются только из enum constants, перечисленных в declaration.

#### Enum наследуется от `java.lang.Enum`

Все enum classes имеют специальную связь с:

```java
java.lang.Enum<E>
```

Поэтому enum не может явно наследоваться от другого класса:

```java
// enum Status extends SomeClass { ... } // нельзя
```

Но enum может реализовывать interfaces:

```java
interface Describable {
    String description();
}

enum Status implements Describable {

    ACTIVE,
    BLOCKED;

    @Override
    public String description() {
        return name().toLowerCase();
    }
}
```

#### Каждая enum constant может иметь своё поведение

```java
enum Operation {

    ADD {
        @Override
        int apply(int a, int b) {
            return a + b;
        }
    },

    MULTIPLY {
        @Override
        int apply(int a, int b) {
            return a * b;
        }
    };

    abstract int apply(int a, int b);
}
```

```java
int result = Operation.ADD.apply(2, 3); // 5
```

Это позволяет использовать полиморфизм вместо большого `switch`, если поведение естественно принадлежит самой enum constant.

#### `values()`

Компилятор предоставляет enum class метод:

```java
OrderStatus[] values = OrderStatus.values();
```

Он возвращает constants в порядке объявления:

```java
for (OrderStatus status : OrderStatus.values()) {
    System.out.println(status);
}
```

Важно: возвращаемый массив можно менять, но это не изменяет сам набор enum constants — вызов возвращает отдельный массив.

#### `valueOf()`

```java
OrderStatus status =
        OrderStatus.valueOf("PAID");
```

Вернёт:

```text
OrderStatus.PAID
```

Имя должно совпадать точно.

```java
OrderStatus.valueOf("paid");
```

приведёт к:

```text
IllegalArgumentException
```

А `null` приводит к `NullPointerException`.

Поэтому данные из внешнего API нельзя бездумно передавать в `valueOf()`, если контракт не гарантирует допустимое значение.

#### `name()`, `toString()` и `ordinal()`

У enum constant есть:

```java
OrderStatus.PAID.name();    // "PAID"
OrderStatus.PAID.ordinal(); // 1
```

`name()` — имя constant, объявленное в исходном коде.

`ordinal()` — позиция, начиная с нуля:

```text
NEW       → 0
PAID      → 1
CANCELLED → 2
```

**Не стоит сохранять `ordinal()` как устойчивый бизнес-идентификатор.**

Если изменить порядок:

```java
enum OrderStatus {
    NEW,
    CANCELLED,
    PAID
}
```

старое число `1` уже означает другое значение.

Именно поэтому при сохранении enum в БД строковое представление обычно устойчивее ordinal к простой перестановке constants. В исходном конспекте эта тема появляется через JPA-аннотацию `@Enumerated`, которая позволяет выбирать `ORDINAL` или `STRING`. fileciteturn48file0 Подробности JPA mapping будут разобраны в главе Hibernate/JPA.

#### Сравнение enum

Enum constants удобно сравнивать через `==`:

```java
if (status == OrderStatus.PAID) {
    // ...
}
```

Для одной enum constant существует один канонический экземпляр, поэтому identity comparison здесь корректен.

Дополнительный плюс:

```java
status == OrderStatus.PAID
```

безопасен даже если `status == null`: результат будет `false`.

#### Enum в `switch`

```java
String message = switch (status) {
    case NEW -> "Created";
    case PAID -> "Paid";
    case CANCELLED -> "Cancelled";
};
```

Для закрытого набора enum constants компилятор может проверять exhaustiveness switch expression.

Это делает enum удобным для конечных наборов состояний, режимов, типов операций и т. п.

#### Когда enum подходит, а когда нет?

Хорошие кандидаты:

```text
OrderStatus
PaymentType
DayOfWeek
LogLevel
Operation
```

То есть набор значений известен и контролируется приложением.

Enum хуже подходит для динамических данных, которые пользователь или администратор должен добавлять без изменения/перекомпиляции кода, например справочник категорий из БД.

#### Record

**Record** — специальная форма класса для компактного описания объектов, основная роль которых — хранить набор данных.

```java
record UserDto(long id, String name) {
}
```

Часть:

```java
(long id, String name)
```

называется **record header**, а `id` и `name` — **record components**.

Для такого record Java предоставляет соответствующие private final fields, public accessor methods, canonical constructor и реализации `equals()`, `hashCode()`, `toString()` согласно семантике records.

Использование:

```java
UserDto user = new UserDto(1L, "Alice");

System.out.println(user.id());   // 1
System.out.println(user.name()); // Alice
```

Обрати внимание: accessor называется:

```java
name()
```

а не автоматически:

```java
getName()
```

#### Что генерирует record?

Для:

```java
record Point(int x, int y) {
}
```

мы получаем поведение, концептуально похожее на data class с:

- private final fields для components;
- accessors `x()` и `y()`;
- canonical constructor `Point(int x, int y)`;
- `equals()`;
- `hashCode()`;
- `toString()`.

Поэтому вместо большого boilerplate:

```java
final class Point {
    // fields
    // constructor
    // getters
    // equals
    // hashCode
    // toString
}
```

часто достаточно:

```java
record Point(int x, int y) {}
```

#### Record и equality

```java
Point first = new Point(10, 20);
Point second = new Point(10, 20);

System.out.println(first == second);      // false
System.out.println(first.equals(second)); // true
```

Records предназначены для представления данных через значения components, поэтому автоматически предоставленный `equals()` сравнивает соответствующие component values по определённому для records контракту, а не identity объекта.

Это делает records удобными для DTO, результатов вычислений, ключей и небольших value-oriented structures.

#### Compact constructor

Record позволяет валидировать входные данные:

```java
record UserDto(long id, String name) {

    UserDto {
        if (id <= 0) {
            throw new IllegalArgumentException("id must be positive");
        }

        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("name is required");
        }
    }
}
```

Это **compact canonical constructor**.

Не нужно повторять список параметров:

```java
UserDto(long id, String name)
```

и не нужно явно писать обычные присваивания components полям в конце compact constructor — они выполняются в рамках специальной семантики record constructor.

#### Можно ли добавлять методы в record?

Да:

```java
record Rectangle(int width, int height) {

    int area() {
        return width * height;
    }
}
```

Можно добавлять static fields и static methods:

```java
record UserDto(long id, String name) {

    static UserDto anonymous() {
        return new UserDto(0, "anonymous");
    }
}
```

То есть record — не просто «структура без логики».

#### Record не имеет дополнительного instance state

Нельзя добавить обычное дополнительное instance field:

```java
record UserDto(long id, String name) {
    // private int cache; // нельзя
}
```

Состояние record определяется его components.

Static fields допустимы, потому что они не являются состоянием конкретного record instance.

#### Record implicitly final

Record нельзя использовать как обычный superclass:

```java
record UserDto(long id, String name) {
}

// class SpecialUserDto extends UserDto { } // нельзя
```

Record class является final.

Сам record также не может явно `extends` произвольный класс: у records специальная модель наследования и базовый `java.lang.Record`.

Но record может реализовывать interfaces:

```java
interface Identifiable {
    long id();
}

record UserDto(long id, String name)
        implements Identifiable {
}
```

#### Record — это shallow immutability

Очень важный нюанс:

```java
record Team(List<String> members) {
}
```

Reference component нельзя переназначить после создания record, но сам объект `List` может оставаться mutable:

```java
List<String> members = new ArrayList<>();
members.add("Alice");

Team team = new Team(members);

members.add("Bob");

System.out.println(team.members());
// [Alice, Bob]
```

То есть:

> record не гарантирует deep immutability.

Упрощённо:

```text
Team
└── final reference ─────► mutable ArrayList
                           ├── Alice
                           └── Bob
```

Если нужна более сильная immutability, можно сделать defensive copy:

```java
record Team(List<String> members) {

    Team {
        members = List.copyOf(members);
    }
}
```

Теперь record хранит собственное неизменяемое представление списка в рамках контракта `List.copyOf` (при условии, что сами элементы не несут отдельно изменяемое состояние, которое требуется глубоко копировать).

#### Можно ли переопределить accessor?

Да, но accessor должен соответствовать правилам record component.

Например:

```java
record User(String name) {

    @Override
    public String name() {
        return name.trim();
    }
}
```

Однако изменять смысл component accessor без серьёзной причины обычно плохая идея: record полезен именно своей прозрачной моделью данных.

#### Record vs обычный class

Record хорош, когда тип по смыслу — **набор данных**:

```java
record Money(BigDecimal amount, Currency currency) {}
record UserResponse(long id, String name) {}
record Coordinates(double latitude, double longitude) {}
```

Обычный class чаще естественнее, когда:

- объект имеет сложный жизненный цикл;
- важна изменяемая внутренняя state machine;
- нужны дополнительные instance fields;
- требуется наследование от другого класса;
- identity объекта важнее набора его component values.

Record — не автоматическая замена всех POJO.

#### Record как DTO

Типичный backend-пример:

```java
record CreateUserRequest(
        String name,
        String email
) {
}

record UserResponse(
        long id,
        String name,
        String email
) {
}
```

Для DTO records часто удобны: меньше boilerplate и сразу виден набор передаваемых данных.

Но совместимость с конкретным framework/library и его версией всё равно нужно проверять отдельно. Наличие record в Java само по себе не гарантирует, что любой старый serializer, ORM или proxy mechanism умеет работать с ним как с обычным mutable JavaBean.

#### Record и JPA Entity — не одно и то же

В исходном конспекте для JPA Entity указаны требования вроде конструктора без аргументов и ограничения, связанные с proxying. fileciteturn48file6

Record по своей модели — final data carrier с canonical construction и не является прямой заменой обычной JPA Entity.

Поэтому практический ориентир:

```text
API DTO / projection / value-like data → record часто удобен
ORM entity с lifecycle/proxying        → проверяем требования JPA/provider
```

Точные требования к entity и особенности Hibernate будут разобраны в соответствующей главе; здесь важно не делать вывод «record лучше обычного класса вообще».

#### Enum vs Record

Это совершенно разные инструменты:

| Enum | Record |
| --- | --- |
| Фиксированный набор экземпляров | Произвольное число экземпляров |
| Constants известны в declaration | Значения задаются constructor arguments |
| Хорош для статусов/режимов | Хорош для data carriers/value-like types |
| Можно сравнивать constants через `==` | Обычно сравниваем через `equals()` |
| Может иметь поведение на constant | Может иметь методы и валидацию |

Пример:

```java
enum Currency {
    EUR,
    USD
}

record Money(
        BigDecimal amount,
        Currency currency
) {
}
```

Здесь `Currency` — конечный набор допустимых значений, а экземпляров `Money` может быть сколько угодно.

#### Типичные ошибки

**«Enum — это просто int constants».**  
Нет. Enum constants — объекты enum type; enum может иметь поля, методы, constructor и реализовывать interfaces.

**«Можно хранить ordinal enum в БД без риска».**  
Технически можно, но перестановка constants изменяет ordinals. Для устойчивого внешнего представления нужен осознанный контракт.

**«Record автоматически глубоко immutable».**  
Нет. References в components не переназначаются, но объект, на который они указывают, может быть mutable.

**«Record — это просто Lombok @Data».**  
Нет. Record имеет собственную семантику языка, ограничения на состояние и наследование, а также определённый контракт generated members.

**«Record нельзя содержать методы».**  
Можно. Нельзя добавлять произвольные дополнительные instance fields, но методы и static members допустимы.

#### Что важно запомнить

- Enum описывает **фиксированный набор именованных экземпляров**.
- Enum может иметь fields, constructors, methods и реализовывать interfaces.
- `values()` возвращает constants, `valueOf()` ищет по точному имени.
- `ordinal()` — позиция constant, а не хороший устойчивый бизнес-ID.
- Enum constants корректно сравнивать через `==`.
- Record предназначен прежде всего для компактного представления данных.
- Record предоставляет canonical constructor, component accessors, `equals/hashCode/toString`.
- Record implicitly final и не может иметь произвольное дополнительное instance state.
- Record даёт **shallow**, а не deep immutability.
- Для mutable components при необходимости используют defensive copies.
- Record может реализовывать interfaces и содержать собственные методы.

#### На собеседовании

**Чем enum в Java отличается от набора констант?**

> Enum — полноценный специальный тип класса с фиксированным набором экземпляров. Он может иметь поля, constructor, методы и реализовывать interfaces. Каждая enum constant имеет тип самого enum, поэтому компилятор контролирует допустимые значения.

**Почему опасно использовать `ordinal()` как значение в БД?**

> Ordinal зависит от порядка объявления constants. Если переставить или вставить enum constant, числовые значения существующих элементов могут измениться. Поэтому ordinal не стоит считать стабильным внешним идентификатором.

**Что автоматически даёт record?**

> Record объявляет набор components и предоставляет соответствующие final-поля, accessors, canonical constructor, а также equals, hashCode и toString по семантике record. Это уменьшает boilerplate для data carrier типов.

**Record immutable?**

> На уровне своих component references record shallow immutable: эти поля нельзя переназначить после создания. Но если component ссылается на mutable объект, например ArrayList, его содержимое всё ещё можно изменить. Для более сильной иммутабельности нужны defensive copies и immutable components.

### 1.13. Аннотации и Reflection

**Аннотация (annotation)** — metadata, которую можно прикрепить к элементу программы: классу, методу, полю, параметру и т. д.

Сама по себе аннотация обычно **не выполняет действие**. Её смысл появляется, когда metadata читает компилятор, JVM, annotation processor или framework.

```java
@Override
public String toString() {
    return "User";
}
```

**Reflection** — API, позволяющий во время выполнения исследовать структуру загруженных классов и выполнять некоторые операции динамически: получать методы/поля/constructors, читать runtime-аннотации, создавать объекты и вызывать методы.

Связка выглядит так:

```text
annotation
    │
    │ metadata
    ▼
class file / runtime representation
    │
    ▼
Reflection / framework
    │
    ▼
решение на основе metadata
```

> Исходный конспект прямо связывает runtime-аннотации с reflection: metadata класса включает поля, методы, сигнатуры и аннотации, а аннотации с `Retention.RUNTIME` доступны через reflection. fileciteturn52file7 Также исходник показывает практическое использование аннотаций в Spring DI, lifecycle и AOP. fileciteturn52file0 fileciteturn52file3

#### Встроенные аннотации Java

Одна из самых известных:

```java
@Override
```

Она говорит компилятору, что метод должен переопределять/реализовывать метод supertype:

```java
class User {

    @Override
    public String toString() {
        return "User";
    }
}
```

Если ошибиться в сигнатуре, компилятор обнаружит проблему.

```@Deprecated`` помечает API как устаревший:

```java
@Deprecated
void oldMethod() {
}
```

```@SuppressWarnings`` подавляет выбранные compiler warnings:

```java
@SuppressWarnings("unchecked")
void legacyCode() {
    // ...
}
```

Её стоит применять локально и осознанно, а не скрывать предупреждения на большом участке кода без понимания причины.

```@FunctionalInterface`` сообщает, что interface должен оставаться functional interface:

```java
@FunctionalInterface
interface Converter<T, R> {
    R convert(T value);
}
```

Это полезная compile-time проверка контракта.

#### Собственная annotation

```java
@interface Audited {
}
```

Использование:

```java
@Audited
class PaymentService {
}
```

Но для реального применения обычно нужно указать, **где** annotation допустима и **как долго** она существует.

Для этого используются meta-annotations.

#### `@Target`

`@Target` ограничивает элементы программы, на которых можно использовать annotation.

```java
@Target(ElementType.METHOD)
@interface Audited {
}
```

Теперь:

```java
class PaymentService {

    @Audited
    void pay() {
    }
}
```

допустимо, а применение к классу — нет.

Часто используемые `ElementType`:

```text
TYPE             → class/interface/enum/record
METHOD           → метод
FIELD            → поле
PARAMETER        → параметр
CONSTRUCTOR      → constructor
LOCAL_VARIABLE   → local variable
ANNOTATION_TYPE  → другая annotation declaration
TYPE_USE         → использование типа
RECORD_COMPONENT → record component
```

Можно разрешить несколько targets:

```java
@Target({
        ElementType.TYPE,
        ElementType.METHOD
})
@interface Audited {
}
```

#### `@Retention`

`@Retention` определяет, до какого этапа сохраняется annotation.

```java
@Retention(RetentionPolicy.RUNTIME)
@interface Audited {
}
```

Три политики:

| Retention | Смысл |
| --- | --- |
| `SOURCE` | annotation существует только в source и не сохраняется в class file |
| `CLASS` | сохраняется в class file, но не обязана быть доступна через обычный reflection во время выполнения |
| `RUNTIME` | сохраняется и доступна runtime через Reflection API |

Если annotation должна читаться framework во время работы приложения:

```java
clazz.isAnnotationPresent(Audited.class)
```

обычно нужна:

```java
@Retention(RetentionPolicy.RUNTIME)
```

Это ровно тот случай, который отдельно упоминает исходный конспект. fileciteturn52file7

#### `@Documented`

```java
@Documented
@interface Audited {
}
```

Указывает, что использование annotation должно включаться инструментами вроде Javadoc в документируемый API.

Это не меняет бизнес-поведение программы.

#### `@Inherited`

```java
@Inherited
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface Audited {
}
```

Если annotation стоит на superclass:

```java
@Audited
class Parent {
}

class Child extends Parent {
}
```

то определённые reflection-операции над `Child` могут видеть inherited annotation.

Важная ловушка: `@Inherited` относится к **class inheritance**. Она не означает автоматическое наследование annotation с методов, полей или interfaces.

#### Annotation может иметь параметры

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Retry {

    int attempts() default 3;

    String reason() default "";
}
```

Использование:

```java
@Retry(attempts = 5, reason = "remote API")
void sendRequest() {
}
```

Если элемент называется `value`, имя можно опустить:

```java
@interface Role {
    String value();
}

@Role("ADMIN")
class AdminService {
}
```

#### Annotation — metadata, а не «магический вызов»

Рассмотрим:

```java
@Audited
void pay() {
}
```

Java сама по себе не начинает логировать вызов только потому, что мы написали `@Audited`.

Нужен механизм, который:

1. обнаружит annotation;
2. прочитает metadata;
3. выполнит соответствующую логику.

Например, framework может просканировать методы и построить proxy/interceptor.

Исходный конспект показывает этот подход в Spring AOP: pointcut может матчить методы по annotation, а proxy добавляет advice вокруг вызова. fileciteturn52file3

---

#### Что такое Reflection

Базовая точка входа — объект `Class<?>`.

Получить его можно несколькими способами:

```java
Class<User> first = User.class;

User user = new User();
Class<?> second = user.getClass();

Class<?> third = Class.forName("com.example.User");
```

`Class` содержит runtime-представление типа и позволяет исследовать его metadata.

Например:

```java
System.out.println(first.getName());
System.out.println(first.getSuperclass());
System.out.println(Arrays.toString(first.getInterfaces()));
```

#### Получение методов

```java
Method method =
        User.class.getDeclaredMethod("setName", String.class);
```

`getDeclaredMethod()` ищет method, объявленный непосредственно в данном class/interface, включая non-public members.

```java
getMethod(...)
```

работает с public method и учитывает соответствующее наследование public members.

Аналогичная идея есть у:

```java
getDeclaredMethods()
getMethods()
```

Это частая ловушка: `declared` не означает «все методы объекта вместе с inherited».

#### Динамический вызов метода

```java
User user = new User();

Method method =
        User.class.getDeclaredMethod(
                "setName",
                String.class
        );

method.invoke(user, "Alice");
```

Здесь compiler не делает обычный статически типизированный вызов:

```java
user.setName("Alice");
```

Метод выбирается через runtime metadata.

`Method.invoke()` также оборачивает исключение, выброшенное самим вызываемым методом, в `InvocationTargetException`, поэтому reflection-код требует отдельной обработки ошибок.

#### Работа с fields

```java
Field field =
        User.class.getDeclaredField("name");
```

Можно исследовать:

```java
field.getName();
field.getType();
field.getModifiers();
field.getAnnotations();
```

И при наличии доступа — читать/изменять значение через reflection API.

Но сам факт наличия Reflection API **не означает**, что любой private member всегда можно беспрепятственно открыть. На доступ влияют Java access control, module boundaries и правила конкретной версии/runtime configuration.

#### Constructors

```java
Constructor<User> constructor =
        User.class.getDeclaredConstructor(String.class);

User user = constructor.newInstance("Alice");
```

Так framework может создавать экземпляры, когда конкретный class известен только во время выполнения.

Это одна из причин, почему reflection исторически широко применялся в DI containers, serializers и ORM.

#### Чтение annotation через reflection

Создадим runtime annotation:

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Audited {
    String value() default "";
}
```

Используем:

```java
class PaymentService {

    @Audited("payment")
    public void pay() {
    }
}
```

Читаем:

```java
Method method =
        PaymentService.class.getDeclaredMethod("pay");

Audited audited =
        method.getAnnotation(Audited.class);

if (audited != null) {
    System.out.println(audited.value());
}
```

Упрощённо framework делает похожую концептуальную работу:

```text
Class
  │
  ├── methods
  │     │
  │     └── @Audited
  │            │
  ▼            ▼
scan metadata → build configuration/proxy/handler
```

Реальные frameworks могут использовать не только core Reflection API, но и bytecode generation, indexes, annotation processors, method handles, generated code и собственные metadata abstractions.

#### Пример: мини-обработчик annotation

```java
static void invokeAuditedMethods(Object target)
        throws Exception {

    for (Method method
            : target.getClass().getDeclaredMethods()) {

        if (method.isAnnotationPresent(Audited.class)) {
            System.out.println(
                    "Before: " + method.getName()
            );

            method.invoke(target);
        }
    }
}
```

Это сильно упрощённый пример, но он показывает ключевую идею:

```text
annotation описывает
       +
reflection обнаруживает
       +
код интерпретирует
       =
динамическое поведение
```

#### Как это связано со Spring

В исходном конспекте Spring использует большое количество declarative metadata:

```java
@Component
@Autowired
@Configuration
@Bean
@Transactional
@Cacheable
@Async
```

Например, исходник описывает `@Autowired` как способ автоматического внедрения зависимости контейнером. fileciteturn52file6

Но важно не свести весь Spring к фразе:

> «Spring работает на reflection».

Это слишком грубо.

Spring использует совокупность механизмов: metadata scanning, Reflection API, BeanDefinition, post-processors, proxies, generated bytecode и другие средства в зависимости от конкретной функции.

Например, исходный материал отдельно описывает создание `BeanDefinition`, работу `BeanFactoryPostProcessor`, создание beans и последующий `BeanPostProcessor`. fileciteturn52file2

А транзакции, caching и некоторые другие cross-cutting функции в Spring часто реализуются через proxy-based AOP. fileciteturn52file3

#### Reflection и Hibernate/JPA

ORM должен понимать структуру entity:

```java
@Entity
class User {

    @Id
    private Long id;

    @Column(name = "user_name")
    private String name;
}
```

Framework обрабатывает mapping metadata, чтобы связать Java-модель с таблицами/колонками.

Reflection — один из механизмов, позволяющих динамически исследовать members и metadata, но конкретный ORM может также применять bytecode enhancement, generated accessors/proxies и другие оптимизации.

Подробно это будет разобрано в Hibernate/JPA.

#### Цена Reflection

Обычный вызов:

```java
service.process();
```

проще для статического анализа и оптимизаций, чем динамическая схема:

```java
method.invoke(service);
```

Reflection добавляет:

- динамическое разрешение metadata и дополнительные проверки;
- более сложную обработку ошибок;
- меньшую compile-time type safety;
- более сложный рефакторинг и навигацию;
- возможные ограничения доступа/modules;
- потенциальный performance overhead относительно обычного прямого вызова.

Но фраза:

> «Reflection всегда очень медленный»

слишком абсолютна.

Стоимость зависит от операции, JVM, частоты вызовов и архитектуры. Framework обычно сканирует metadata ограниченное число раз, кэширует результаты или генерирует более быстрые пути доступа.

Практический вывод:

> Не стоит заменять обычный типобезопасный Java-код reflection без причины, но для framework/infrastructure задач динамичность reflection оправдана.

#### Reflection ломает инкапсуляцию?

Reflection способен работать с non-public metadata и в некоторых разрешённых условиях получать доступ к non-public members.

Но современная Java имеет дополнительные границы, особенно **Java Platform Module System (JPMS)**.

Поэтому старый совет:

```java
field.setAccessible(true);
```

не следует понимать как универсальное «теперь можно получить доступ ко всему». Strong encapsulation и module openness могут ограничить reflective access.

#### Reflection и compile-time type safety

Обычный код:

```java
user.setName("Alice");
```

компилятор проверяет заранее.

Reflection:

```java
method.invoke(user, 123);
```

может обнаружить несовместимость только во время выполнения.

Поэтому reflection переносит часть ошибок из compile time в runtime.

#### Аннотации не обязательно обрабатываются runtime

Важно не связывать annotations исключительно с reflection.

Например, annotation может иметь:

```java
@Retention(RetentionPolicy.SOURCE)
```

и использоваться compiler/tooling.

Другой вариант — **annotation processing** во время компиляции: processor читает annotations и генерирует код/metadata.

Следовательно:

```text
annotations
├── compiler checks
├── compile-time processors
├── tooling/documentation
└── runtime frameworks / reflection
```

Reflection — только один из способов использования annotation metadata.

#### Типичные ошибки

**«Аннотация сама выполняет код».**  
Нет. Annotation — metadata. Нужен компилятор, processor, runtime/framework или другой механизм, который её интерпретирует.

**«Все annotations доступны через reflection».**  
Нет. Для обычного runtime reflection важна retention policy; `SOURCE` и `CLASS` не эквивалентны `RUNTIME`.

**«@Inherited наследует annotation везде».**  
Нет. Её семантика относится к annotations на class declarations и наследованию классов, а не автоматически к methods/interfaces.

**«getDeclaredMethods() возвращает вообще все методы, включая inherited».**  
Нет. Он ориентирован на methods, объявленные непосредственно в данном типе.

**«setAccessible(true) гарантированно открывает любой private member».**  
Нет. В современной Java reflective access может быть ограничен module boundaries и strong encapsulation.

**«Spring = reflection».**  
Нет. Reflection важен для многих infrastructure-сценариев, но Spring также использует metadata models, processors, proxies и другие механизмы.

#### Что важно запомнить

- Annotation — **metadata**, а не исполняемое действие само по себе.
- `@Target` определяет допустимые места применения.
- `@Retention` определяет жизненный цикл annotation: `SOURCE`, `CLASS`, `RUNTIME`.
- Runtime annotation можно читать через Reflection API.
- `Class` — основная точка входа для runtime metadata типа.
- `Method`, `Field`, `Constructor` позволяют исследовать соответствующие members.
- `Method.invoke()` выполняет динамический вызов и теряет часть compile-time type safety.
- Reflection полезен для frameworks, DI, ORM, serialization и infrastructure-кода.
- Reflection не гарантирует обход всех access/module restrictions.
- Не все annotations обрабатываются reflection: возможна compile-time processing.

#### На собеседовании

**Что такое annotation в Java?**

> Annotation — это metadata, которую можно прикрепить к классу, методу, полю и другим элементам. Сама annotation обычно ничего не выполняет: её читает компилятор, annotation processor или runtime-framework. @Target ограничивает место применения, а @Retention определяет, сохраняется ли annotation только в source, в class file или доступна runtime.

**Что такое Reflection?**

> Reflection API позволяет во время выполнения исследовать структуру загруженного типа через Class: получать методы, поля, constructors и runtime-аннотации, а также динамически создавать объекты или вызывать методы. Это полезно для framework-кода, но уменьшает compile-time type safety и может иметь дополнительные накладные расходы и ограничения доступа.

**Чем `getMethods()` отличается от `getDeclaredMethods()`?**

> getMethods() возвращает public methods с учётом унаследованных public methods. getDeclaredMethods() возвращает methods, непосредственно объявленные в данном class/interface, независимо от их visibility, но не является способом получить всю inherited hierarchy.

**Как Spring использует annotations и reflection?**

> Spring читает declarative metadata вроде @Component или @Autowired и на её основе строит конфигурацию контейнера. Reflection участвует в части динамического анализа и доступа, но Spring не сводится к reflection: используются BeanDefinition, post-processors, proxies, bytecode generation и другие механизмы.

#### Источники и уточнения

- Исходный конспект прямо указывает, что metadata класса включает поля, методы, сигнатуры и annotations, а `Retention.RUNTIME` делает annotation доступной через reflection. fileciteturn52file7
- В Spring-разделе исходника annotations используются для DI и lifecycle, например `@Autowired`, `@PostConstruct` и `@PreDestroy`. fileciteturn52file0
- В AOP-разделе исходника показано использование annotation metadata в pointcuts и proxy-based механика `@Transactional`, `@Async`, caching и security. fileciteturn52file3
- [Java Language Specification — Annotations](https://docs.oracle.com/javase/specs/jls/se26/html/jls-9.html#jls-9.6) — annotation interfaces и правила annotations.
- [Java API — java.lang.annotation](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/lang/annotation/package-summary.html) — meta-annotations и retention/target.

### 1.14. Nested, Inner, Local и Anonymous classes

Java позволяет объявлять класс не только на верхнем уровне файла, но и **внутри другого класса или внутри блока кода**.

Основные варианты:

```text
nested classes
├── static nested class
└── inner classes
    ├── member inner class
    ├── local class
    └── anonymous class
```

Главный вопрос на собеседовании обычно не в названиях, а в понимании:

> Есть ли у вложенного объекта неявная связь с экземпляром внешнего класса?

Для **static nested class** — нет.  
Для обычного **inner class** — да.

> В исходном конспекте отдельного объяснения nested/inner/local/anonymous classes поиском не найдено. Есть только упоминание вложенных классов как части metadata класса в JVM. fileciteturn56file0 Поэтому языковые правила этого подраздела добавлены как Java Core база по JLS.

#### Static nested class

```java
class Order {

    private long id;

    static class Validator {

        boolean isValid(Order order) {
            return order.id > 0;
        }
    }
}
```

Создание:

```java
Order.Validator validator =
        new Order.Validator();
```

Для создания `Validator` экземпляр `Order` не нужен.

Упрощённо:

```text
Order
└── static nested Validator

validator ──X──► конкретный Order
```

Static nested class логически находится внутри `Order`, но его экземпляр **не хранит обязательную enclosing-instance связь** с конкретным объектом `Order`.

#### Доступ static nested class к outer members

Как и другой static context, он не может просто обратиться к instance member внешнего класса:

```java
class Order {

    private long id;

    static class Validator {

        boolean isValid() {
            // return id > 0; // compile error
            return true;
        }
    }
}
```

Нужен объект:

```java
boolean isValid(Order order) {
    return order.id > 0;
}
```

При этом nested class может обращаться к private members внешнего класса через обычные правила языка для nested declarations — `private` не означает, что два вложенных друг в друга типа полностью изолированы друг от друга.

#### Member inner class

Если вложенный class объявлен без `static`, это **inner class**:

```java
class Order {

    private long id;

    class Printer {

        void print() {
            System.out.println(id);
        }
    }
}
```

Экземпляр `Printer` связан с конкретным экземпляром `Order`.

Создание снаружи:

```java
Order order = new Order();

Order.Printer printer =
        order.new Printer();
```

Модель:

```text
order ───────────────► Order
                         ▲
                         │ enclosing instance
                         │
printer ─────────────► Printer
```

Поэтому внутри `Printer` доступно состояние конкретного outer object.

#### `OuterClass.this`

Если имена совпадают:

```java
class User {

    private String name = "outer";

    class Profile {

        private String name = "inner";

        void print() {
            System.out.println(name);
            System.out.println(User.this.name);
        }
    }
}
```

```text
name           → Profile.name
User.this.name → поле конкретного outer User
```

`User.this` явно обращается к enclosing instance.

#### Inner object может удерживать outer object

Поскольку non-static inner instance связан с outer instance, эта связь влияет на lifetime объектов.

Например, если где-то долго хранится inner object:

```java
someLongLivedCollection.add(
        order.new Printer()
);
```

он может косвенно удерживать `order` достижимым для GC.

Это не означает, что inner classes «вызывают memory leak» сами по себе. Но неявную ссылку на enclosing instance важно учитывать в долгоживущих callbacks/listeners/tasks.

Если связь с outer instance не нужна, **static nested class обычно проще и безопаснее по модели владения**.

#### Может ли inner class иметь static members?

Старое правило «inner class вообще не может содержать static members кроме constants» больше нельзя использовать как универсальное правило современной Java.

В актуальных версиях Java inner classes могут объявлять static members в соответствии с современными правилами языка.

На собеседовании важнее помнить фундаментальное отличие:

```text
static nested instance → не требует outer instance
inner instance         → связан с enclosing outer instance
```

А не опираться на устаревшие ограничения старых версий Java.

#### Local class

Класс можно объявить внутри метода или другого блока:

```java
class ReportService {

    void generate(String title) {

        class Formatter {

            String format() {
                return "Report: " + title;
            }
        }

        Formatter formatter = new Formatter();
        System.out.println(formatter.format());
    }
}
```

`Formatter` существует как declaration только внутри соответствующей области видимости.

Снаружи метода написать:

```java
// new Formatter()
```

нельзя.

Local classes полезны, когда небольшой вспомогательный тип нужен только внутри одного алгоритма и не должен становиться частью API класса.

На практике используются значительно реже, чем обычные classes, lambdas и static nested classes.

#### Захват local variables

В примере local class использует:

```java
title
```

из enclosing method.

Такая local variable должна быть `final` или **effectively final**:

```java
void generate() {

    String prefix = "Report: ";

    class Formatter {
        String format(String value) {
            return prefix + value;
        }
    }
}
```

Допустимо, потому что `prefix` не переназначается.

Но:

```java
String prefix = "Report: ";
prefix = "Document: ";

class Formatter {
    String format(String value) {
        // return prefix + value; // compile error
    }
}
```

После переназначения `prefix` перестал быть effectively final.

Это связано с тем же правилом захвата local variables, которое мы уже встречали при обсуждении lambdas.

#### Изменение объекта всё ещё возможно

Как и раньше, effectively final относится к **самой переменной**, а не к глубокой неизменяемости объекта.

```java
List<String> values = new ArrayList<>();

class Collector {
    void add(String value) {
        values.add(value);
    }
}
```

Это допустимо, пока:

```java
values = anotherList;
```

не переназначается.

#### Anonymous class

**Anonymous class** — класс без собственного объявленного имени, экземпляр которого создаётся прямо в expression.

```java
Runnable task = new Runnable() {

    @Override
    public void run() {
        System.out.println("Running");
    }
};
```

Здесь одновременно:

1. создаётся anonymous subclass/implementation;
2. определяется его body;
3. создаётся экземпляр.

Синтаксис выглядит как `new Runnable()`, но интерфейс напрямую не инстанцируется — создаётся объект анонимного класса, реализующего `Runnable`.

#### Anonymous class от обычного класса

Можно создать anonymous subclass:

```java
class Handler {
    void handle() {
        System.out.println("default");
    }
}
```

```java
Handler handler = new Handler() {

    @Override
    void handle() {
        System.out.println("custom");
    }
};
```

Это удобно для одноразового локального переопределения поведения.

#### Anonymous class может иметь собственные members

```java
Runnable task = new Runnable() {

    private int count;

    private void log() {
        System.out.println(count);
    }

    @Override
    public void run() {
        count++;
        log();
    }
};
```

Но обращаться к специфическим members через переменную типа `Runnable` нельзя:

```java
task.run();
// task.log(); // Runnable не знает о log()
```

Anonymous class имеет реальный runtime class, просто у него нет обычного source-level имени, которое мы объявили бы как `class MyTask`.

#### Anonymous class и constructor

У anonymous class нельзя объявить обычный именованный constructor — у класса нет собственного имени.

Но можно использовать instance initializer:

```java
Runnable task = new Runnable() {

    {
        System.out.println("initialized");
    }

    @Override
    public void run() {
    }
};
```

Если anonymous class наследуется от класса, аргументы в `new Parent(...)` передаются соответствующему superclass constructor.

#### Anonymous class vs lambda

Для functional interface:

```java
Runnable task = new Runnable() {
    @Override
    public void run() {
        System.out.println("run");
    }
};
```

часто можно написать:

```java
Runnable task =
        () -> System.out.println("run");
```

Но lambda и anonymous class — **не одно и то же**.

Ключевое различие — `this`.

В anonymous class:

```java
Runnable task = new Runnable() {
    @Override
    public void run() {
        System.out.println(this.getClass());
    }
};
```

`this` относится к экземпляру anonymous class.

В lambda `this` не создаёт новый контекст объекта; если lambda находится в instance context, `this` относится к enclosing instance:

```java
class Service {

    Runnable task() {
        return () -> System.out.println(this);
    }
}
```

Здесь `this` — `Service`.

Кроме того, anonymous class может:

- иметь собственные fields/methods;
- наследоваться от class;
- реализовать interface через anonymous implementation.

Lambda предназначена для реализации **functional interface** и имеет другую языковую семантику.

Поэтому:

> lambda — не просто сокращённая запись anonymous class, хотя во многих callback-сценариях заменяет её.

#### Захват переменных anonymous class и lambda

Обе конструкции могут захватывать local variables только если они final/effectively final:

```java
String message = "Hello";

Runnable anonymous = new Runnable() {
    @Override
    public void run() {
        System.out.println(message);
    }
};

Runnable lambda =
        () -> System.out.println(message);
```

Если потом сделать:

```java
// message = "Bye";
```

захват перестанет удовлетворять правилу effectively final.

#### Когда какой вариант использовать?

Если helper тесно связан с outer class, но не требует его экземпляра:

```text
static nested class
```

обычно хороший выбор.

Если helper действительно должен работать с состоянием конкретного outer object:

```text
member inner class
```

может быть естественным.

Если тип нужен только внутри одного блока:

```text
local class
```

Если нужна одноразовая реализация/подкласс с собственным body:

```text
anonymous class
```

Если нужен короткий callback для functional interface:

```text
lambda
```

обычно читается проще anonymous class.

#### Практический пример: Builder

Static nested class часто используется для Builder:

```java
class User {

    private final String name;
    private final int age;

    private User(Builder builder) {
        this.name = builder.name;
        this.age = builder.age;
    }

    static class Builder {

        private String name;
        private int age;

        Builder name(String name) {
            this.name = name;
            return this;
        }

        Builder age(int age) {
            this.age = age;
            return this;
        }

        User build() {
            return new User(this);
        }
    }
}
```

Использование:

```java
User user = new User.Builder()
        .name("Alice")
        .age(30)
        .build();
```

Builder логически относится к `User`, но для своей работы ему не нужен уже существующий экземпляр `User`. Поэтому static nested class здесь подходит лучше inner class.

#### Типичные ошибки

**«Любой вложенный class называется inner class».**  
Нет. Static nested class — nested, но не inner class. Inner classes связаны с enclosing instance.

**«Чтобы создать static nested class, сначала нужен объект outer class».**  
Нет. `new Outer.Nested()` не требует `new Outer()`.

**«Inner class неявно независим от outer object».**  
Нет. Member inner instance связан с конкретным enclosing instance.

**«Effectively final означает immutable object».**  
Нет. Ограничение относится к переназначению захваченной local variable.

**«Lambda — просто синтаксический сахар для anonymous class».**  
Это слишком грубо и приводит к ошибкам, например при понимании `this`. У них различная языковая семантика.

**«Inner class всегда приводит к memory leak».**  
Нет. Но ссылка inner instance на outer instance может продлить его достижимость, если inner object живёт дольше ожидаемого.

#### Что важно запомнить

- **Nested class** — общий термин для класса, объявленного внутри другого класса/interface.
- **Static nested class** не требует экземпляр outer class.
- **Inner class** связан с конкретным enclosing instance и может обращаться к его instance state.
- `Outer.this` позволяет явно обратиться к enclosing instance.
- Local class объявляется внутри блока и виден только в соответствующей scope.
- Local и anonymous classes могут захватывать только final/effectively final local variables.
- Anonymous class создаёт одноразовую реализацию/подкласс без source-level имени.
- Lambda и anonymous class не эквивалентны; в частности, у них различается смысл `this`.
- Если связь с outer instance не нужна, обычно стоит предпочесть static nested class.

#### На собеседовании

**Чем static nested class отличается от inner class?**

> Static nested class не связан с конкретным экземпляром внешнего класса и создаётся как new Outer.Nested(). Member inner class имеет enclosing instance и снаружи создаётся через outer.new Inner(); поэтому он может напрямую работать с instance state этого outer object.

**Почему local/anonymous class может использовать только final или effectively final local variables?**

> Захватываемая local variable не должна переназначаться после инициализации. Это ограничение относится к самой переменной; mutable объект, на который она ссылается, всё ещё может изменяться.

**Чем anonymous class отличается от lambda?**

> Anonymous class создаёт экземпляр отдельного анонимного класса и может иметь собственные fields/methods; внутри него this относится к этому объекту. Lambda реализует functional interface и не вводит новый this-контекст: this относится к enclosing instance.

#### Источники и уточнения

- В найденном исходном конспекте отдельного объяснения nested/inner/local/anonymous classes нет; вложенные классы упоминаются только как часть metadata загруженного класса. fileciteturn56file0
- Поэтому основной материал подраздела добавлен по спецификации Java как необходимая база Java Core.
- [Java Language Specification — Nested Classes](https://docs.oracle.com/javase/specs/jls/se26/html/jls-8.html#jls-8.1.3) — inner/static nested classes и enclosing instances.
- [Java Language Specification — Local and Anonymous Classes](https://docs.oracle.com/javase/specs/jls/se26/html/jls-14.html#jls-14.3) — local class declarations.
- [Java Language Specification — Class Instance Creation Expressions](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.9) — anonymous class creation.
- [Java Language Specification — Lambda Expressions](https://docs.oracle.com/javase/specs/jls/se26/html/jls-15.html#jls-15.27) — lambda semantics и захват local variables.

### 1.15. Модификаторы доступа и packages

Модификаторы доступа определяют, **из какого кода разрешено обращаться к типу или member**.

Для members класса основные уровни:

| Modifier | Тот же class | Тот же package | Subclass в другом package | Остальной код |
| --- | --- | --- | --- | --- |
| `private` | да | нет | нет | нет |
| package-private | да | да | нет | нет |
| `protected` | да | да | да, но с важным ограничением | нет |
| `public` | да | да | да | да |

Package-private — это **отсутствие явного access modifier**:

```java
class UserService {

    void validate() {
    }
}
```

> В найденных разделах исходного конспекта нет отдельного объяснения access modifiers. Они встречаются в примерах и metadata классов (`public`, `private final`), а в JPA-разделе упоминается требование public/protected no-arg constructor для entity. fileciteturn60file0 fileciteturn60file8 Поэтому языковые правила ниже добавлены как необходимая Java Core база по JLS.

#### `private`

`private` — самый узкий доступ для member:

```java
class BankAccount {

    private BigDecimal balance;

    public BigDecimal getBalance() {
        return balance;
    }
}
```

Код другого top-level class не может напрямую сделать:

```java
// account.balance
```

Это помогает скрывать детали реализации и защищать инварианты объекта.

Но важно:

> `private` сам по себе не делает класс хорошо инкапсулированным.

Например, бессмысленный setter:

```java
public void setBalance(BigDecimal balance) {
    this.balance = balance;
}
```

может фактически открыть состояние почти так же широко. Инкапсуляция — это контроль допустимых операций, а не просто набор private fields.

#### `public`

`public` member доступен из любого кода, **если доступен сам тип**, которому он принадлежит.

Например:

```java
package app.service;

public class UserService {

    public void createUser() {
    }
}
```

Из другого package:

```java
import app.service.UserService;

UserService service = new UserService();
service.createUser();
```

Но если enclosing/top-level type недоступен, наличие public member не делает его магически доступным снаружи.

#### Package-private

Если modifier отсутствует:

```java
class InternalValidator {

    boolean isValid(String value) {
        return value != null;
    }
}
```

и class, и method здесь package-private.

Код из того же package может их использовать, а код из другого package — нет.

Это удобно для внутренних деталей реализации package:

```text
com.example.payment
├── PaymentService.java        public API
├── PaymentRepository.java     package-private implementation detail
└── PaymentValidator.java      package-private implementation detail
```

Не всё в приложении обязано быть `public`.

#### Package — часть модели доступа

Два класса в одном package получают package-level access независимо от того, лежат ли source-файлы физически рядом на диске.

Например:

```java
package com.example.payment;
```

именно package declaration участвует в правилах языка.

Package также создаёт namespace:

```text
com.shop.user.User
com.shop.admin.User
```

Это разные fully qualified class names.

#### Top-level types

Для обычного top-level class/interface основные варианты доступа — `public` или package-private.

```java
public class ApiService {
}
```

или:

```java
class InternalService {
}
```

Так нельзя:

```java
// private class Service { }
// protected class Service { }
```

на top level.

`private` и `protected` применимы, например, к member classes внутри другого class.

---

#### `protected`: главное правило

`protected` часто запоминают слишком упрощённо:

> «доступно в package и наследникам».

Это почти верно, но скрывает главную ловушку.

В **том же package** protected member доступен примерно как package-level member:

```java
package a;

public class Parent {
    protected int value;
}
```

```java
package a;

class Helper {

    void test(Parent parent) {
        parent.value = 10; // OK
    }
}
```

`Helper` даже не обязан быть subclass.

#### Subclass в другом package

Теперь:

```java
package a;

public class Parent {
    protected int value;
}
```

Subclass:

```java
package b;

import a.Parent;

public class Child extends Parent {

    void test() {
        value = 10;       // OK
        this.value = 20;  // OK
    }
}
```

Subclass получает protected access через **наследование**.

Но отсюда не следует, что он может обращаться к protected member через любой объект `Parent`.

#### Главная ловушка `protected`

В другом package:

```java
package b;

import a.Parent;

public class Child extends Parent {

    void test(Parent parent) {
        // parent.value = 10; // compile error
    }
}
```

Почему?

Потому что межпакетный protected access дан subclass в контексте его **наследуемой части**, а не как универсальное право читать protected member любого экземпляра superclass.

Допустим:

```java
void test(Child child) {
    child.value = 10; // OK
}
```

Упрощённое правило для собеседования:

> В другом package subclass может обращаться к protected instance member через `this`/унаследованный member или через reference, тип которой является этим subclass (или его subtype), но не через произвольную reference типа superclass.

Это один из наиболее частых вопросов-ловушек по access modifiers.

#### Пример с двумя subclasses

```java
package b;

import a.Parent;

class Child extends Parent {

    void copy(Child other) {
        this.value = other.value; // OK
    }

    void copy(Parent other) {
        // this.value = other.value; // compile error
    }
}
```

Разница не в runtime object, а в правилах compile-time access через qualifying expression.

#### `protected static`

Для static protected members также действует special protected access между packages, но здесь нет instance state.

На практике для понимания интервью важнее уверенно объяснять instance-case выше, потому что именно он обычно вызывает ошибки.

---

#### Access modifier и overriding

При overriding нельзя **сузить** доступ метода.

Например:

```java
class Parent {

    protected void process() {
    }
}
```

Так можно:

```java
class Child extends Parent {

    @Override
    public void process() {
    }
}
```

Доступ расширился:

```text
protected → public
```

Но так нельзя:

```java
class Child extends Parent {

    // compile error:
    // @Override
    // private void process() {}
}
```

Иначе объект `Child` перестал бы удовлетворять доступному контракту `Parent`.

#### Private method и overriding

`private` method не наследуется subclass как доступный member, поэтому subclass не override его в обычном полиморфном смысле.

```java
class Parent {

    private void print() {
    }
}

class Child extends Parent {

    void print() {
    }
}
```

`Child.print()` — новый method, а не override `Parent.print()`.

Поэтому `@Override` здесь не скомпилируется.

#### Package-private method и другой package

Похожая ловушка:

```java
package a;

public class Parent {

    void process() {
    }
}
```

```java
package b;

public class Child extends Parent {

    public void process() {
    }
}
```

`Parent.process()` недоступен subclass из другого package и не наследуется там как overridable member в требуемом смысле. Метод с тем же signature в `Child` не становится overriding этого package-private метода только из-за совпадения имени/signature.

---

#### Constructor access

Access modifiers constructors определяют, **кто может создавать объект через этот constructor**.

```java
public class User {

    private User() {
    }
}
```

Внешний код не может:

```java
// new User();
```

Это используется, например, в static factory methods:

```java
public class User {

    private User() {
    }

    public static User create() {
        return new User();
    }
}
```

`protected` constructor часто нужен, когда создание должно быть доступно наследникам/framework, но не произвольному клиентскому коду.

В исходном JPA-разделе именно поэтому важно требование конструктора entity с подходящей visibility: там указано, что no-arg constructor должен быть `public` или `protected`. fileciteturn60file8 Точные требования JPA разберём отдельно в Hibernate/JPA.

#### `private` constructor и наследование

Если у superclass доступны только private constructors:

```java
class Parent {

    private Parent() {
    }
}
```

обычный внешний subclass не сможет вызвать constructor superclass:

```java
// class Child extends Parent { } // compile error
```

Constructor не наследуется, но constructor subclass обязан в конечном счёте вызвать доступный superclass constructor.

---

#### Imports не меняют access

```java
import com.example.InternalService;
```

не делает package-private class доступным из другого package.

`import` лишь позволяет использовать короткое имя вместо fully qualified name.

То есть:

```text
import ≠ access permission
```

Сначала member/type должен быть доступен по правилам языка.

#### Package и module — разные уровни

Начиная с Java 9 существует JPMS — module system.

Даже `public` class из package может быть недоступен коду другого module, если package не экспортируется module descriptor:

```java
module app.core {
    exports com.example.api;
}
```

Поэтому в modular application:

```text
public
  +
exported package
  +
module readability
  =
доступ между modules
```

Это дополнительный уровень поверх обычных access modifiers.

Для большинства backend-собеседований достаточно сначала уверенно знать `private/package-private/protected/public`, а JPMS рассматривать как отдельный нюанс.

#### Доступ и Reflection

Access modifiers — правила языка/runtime access control, но Reflection API может предоставлять механизмы reflective access.

Однако, как отмечалось в предыдущем разделе, нельзя считать:

```java
setAccessible(true)
```

универсальным способом обойти любую границу. JPMS и strong encapsulation могут ограничивать deep reflection.

Это не меняет обычные compile-time правила access modifiers.

#### Что выбирать на практике?

Полезный принцип:

> Давайте минимально необходимую visibility.

Если member нужен только самому class:

```text
private
```

Если implementation detail должен быть доступен соседним classes одного package:

```text
package-private
```

Если extension point действительно предназначен для subclasses:

```text
protected
```

Если это часть внешнего API:

```text
public
```

Не стоит делать всё `public` «на всякий случай»: публичный API сложнее менять без влияния на вызывающий код.

#### Типичные ошибки

**«Default access modifier — это protected».**  
Нет. Отсутствие modifier означает package-private.

**«protected доступен только наследникам».**  
Нет. В том же package он доступен и не-subclass коду.

**«Subclass из другого package может читать protected field у любого Parent».**  
Нет. Для межпакетного protected instance access есть ограничение на qualifying reference.

**«private method можно override».**  
Нет. Method с тем же signature в subclass является другим method.

**«import открывает доступ к package-private class».**  
Нет. Import влияет на разрешение имён, а не на visibility.

**«public всегда означает доступен отовсюду».**  
Не полностью: должен быть доступен enclosing type, а в JPMS дополнительно имеют значение exports/readability.

#### Что важно запомнить

- `private` — доступ внутри соответствующего top-level/nest контекста по правилам языка; для обычного использования думай как о скрытом member реализации.
- package-private — отсутствие modifier, доступ внутри package.
- `protected` = package access + специальный доступ subclasses.
- Между packages protected instance member нельзя использовать через произвольную reference типа superclass.
- `public` — самый широкий language-level access, но type/module тоже должны быть доступны.
- Top-level class обычно может быть `public` или package-private, но не `private/protected`.
- При overriding можно сохранить или расширить visibility, но нельзя её сузить.
- Private method не override-ится.
- Import не меняет правила доступа.
- Хороший API обычно использует **минимально необходимую visibility**.

#### На собеседовании

**Какие access modifiers есть в Java?**

> Для members есть private, package-private, protected и public. Private ограничивает доступ, package-private доступен внутри package, protected добавляет возможность доступа наследникам, а public даёт самый широкий доступ. При этом protected между разными packages имеет дополнительное правило для доступа через экземпляр.

**В чём ловушка protected между packages?**

> Subclass из другого package получает protected member через наследование, но не может обращаться к нему через произвольную ссылку типа superclass. Например, внутри Child extends Parent выражение this.value допустимо, child.value для Child тоже допустимо, а parent.value через Parent reference — нет.

**Можно ли при overriding сделать public method protected?**

> Нет, overriding method не может сужать visibility inherited method. Можно сохранить уровень доступа или расширить его, например protected → public.

**Чем package-private отличается от protected?**

> Package-private доступен только внутри package. Protected внутри того же package тоже доступен, но дополнительно предоставляет специальный доступ subclasses из других packages.

#### Источники и уточнения

- В исходном конспекте access modifiers встречаются как часть metadata класса: упоминаются `public` class и `private final` fields, но отдельной теории visibility нет. fileciteturn60file0
- В JPA-разделе исходник отдельно указывает public/protected no-arg constructor как требование entity. fileciteturn60file8
- Поэтому правила package-private/protected, overriding visibility и package boundaries дополнены по JLS.
- [Java Language Specification — Access Control](https://docs.oracle.com/javase/specs/jls/se26/html/jls-6.html#jls-6.6) — правила `public/protected/package/private`.
- [Java Language Specification — Overriding](https://docs.oracle.com/javase/specs/jls/se26/html/jls-8.html#jls-8.4.8.3) — требования к access при overriding.
- [Java Language Specification — Packages](https://docs.oracle.com/javase/specs/jls/se26/html/jls-7.html) — packages, imports и top-level declarations.
